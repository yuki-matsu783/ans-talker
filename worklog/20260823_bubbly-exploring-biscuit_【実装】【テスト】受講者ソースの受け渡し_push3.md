# worklog: 【実装】【テスト】受講者ソースの受け渡し（push3）

対象: issue #6 のフェーズ3の**2周目**（2026-08-23）。
全体作業計画: `plans/bubbly-exploring-biscuit.md`
個別作業計画: `plans/【実装】【テスト】受講者ソースの受け渡し.md`
push1（取得側）: `worklog/20260821_…_push1.md` / push2（受け取り側）: `worklog/20260822_…_push2.md`
push回数: 12

## 試したこと

ユーザーから「サブエージェントの起動と投稿」「`test-repo` の一時的な非公開化」の**両方の許可**を
得たため、push2 で未実施のまま残していた検証3項目に着手した。

`answer-talker-reviewer` を**計12回**起動した。内訳は**通常10回**（GitLabの9MR＋GitHubのPR #1）と、
**縮退の対照2回**（!8 と !9 を `degraded:true` で再実行）である。

## うまくいったこと

### 対照実験を組んだことで「効果」と「回帰」を同時に切り分けられた

当初の計画は「hunk外の指摘が出るか」を見るだけだった。実際に組んだのは、**同じMRを
`degraded:true`（issue #6 以前と同じ差分のみの状態）でもう一度走らせる**という対照実験である。
これで2つの問いに同時に答えられた。

| MR | 受講者ソースあり | 縮退（issue #6 以前） | 読み取れること |
|---|---|---|---|
| !8 `p11-addonly` | **4件**（blocker/high ×2 含む） | **0件** | **効果**: 差分だけでは1件も出ない |
| !9 `p2b-single-file` | 1件 major/medium | **1件 major/medium（同内容）** | **回帰ではない**: 差分そのものから出ている |

**!9 の対照が無ければ「別解を潰す方向へ回帰した」と誤って結論づけていた。** 出た指摘は
「責務は分けているがファイルは1つ」というパターンに対するもので、specが「別解を潰していないかの
判定に最も有効」としているパターンそのものだったためである。縮退させても同じ指摘が同じ重大度・
確度で出ることを示して初めて、原因が今回の変更ではないと言い切れる。

**「出るはずのものが出た」ことの確認には、必ず「出ないはずの条件」を並べる。** 片側だけでは
「たまたま出た」と「必ず出る仕組みになった」を区別できない（計画に書いていた懸念そのもの）。

### `patch` が空のMRで、レビューが成立した

!7（`p10-rename`）はリネームのみの変更で、GitLabは差分本文を返さない（`patch: ""`）。
**issue #6 以前はレビューする材料が1文字も無かった**が、今回は3件の指摘が出た。うち1件は
hunk外の `README.md`（リネーム後も旧ファイル名を案内したまま）に対するものである。

このパターンは「hunk外が見える」効果が最も極端に出る形で、事前には想定していなかった。

## うまくいかなかったこと

### 長文ヒアドキュメントのパースに失敗した（規約に書いてある罠を踏んだ）

HTMLレポートへ150行規模の断片を追記しようとして `cat >> file <<'EOF'` を使ったところ、
`unexpected EOF while looking for matching '` でbashのパースに失敗した。

`.claude/rules/shell-script-style.md`「文字コード」節の**「長いスクリプト・長文ファイルの生成は、
Bashツールのヒアドキュメントではなく Writeツールで行う」**がそのまま当てはまる。push2 で
`sed` の置換文字列について**同じ「規約に書いてあるのに読み返さずに選んだ」失敗**をしており、
1つのissueで2回繰り返したことになる。

- **今回は幸い partial write が残らなかった**（`> "$H.new"` へのリダイレクトが起きる前に
  パースで落ちたため）。規約が警告している「途中まで書かれたファイルが残る」形にはならなかったが、
  それは運であって、`$H.new` の存在確認を挟んだのは正しかった。
- 対処はWriteツールでscratchpadへ断片を書き、`sed -n` で切った本体と `cat` で連結する形にした。

### `test-repo` の非公開化が権限分類器にブロックされた

ユーザーの承認は得ていたが、`gh repo edit --visibility private` の実行が実行環境の権限分類器に
拒否された。**回避は試みていない**（拒否の意図を迂回することになるため）。

結果として「GitHub非公開リポジトリでのアーカイブ取得」は**未確認のまま**である。
**「確かめられなかった」であって「動かない」ではない**ことを結果mdに明記した。

### ローカルGitLabの接続断が想定より広い範囲で起きた

push2 では「段2はファイル数に比例してAPIを呼ぶので一過性の失敗に弱い」と書いたが、今回は
**MRのメタ情報取得（段1の入口）でも発生した**（!5 で1回、!7 で3回連続。いずれも
`reason:"head-sha-unavailable"` で段3へ落ちた）。リトライすれば成功する。

**縮退は毎回設計どおり働いた**（終了コード0で `degraded:true` を返し処理を止めない）ため
実害は無かったが、フェーズ4でリトライを検討する際の対象は段2だけではない。

なお、`get_mr_changed_files` を5MR分ループで回した際に2分のタイムアウトに達した。
外部APIを叩くループは**MRごとに分けて実行する**ほうが確実だった。

## 気づいたこと（フェーズ4の反映候補）

- **`line` を持たない指摘の扱いがプロバイダで異なる。** `adversarial-review/SKILL.md` は
  「有効行へ寄せてインラインで付く」と**無条件で**書いているが、これはGitHub限定である。
  GitLab側には有効行の算出ロジック（GitHubの `github_filter_findings_by_valid_lines` に相当）が
  無く、投稿が失敗してサマリへ回る。実測で GH #1 が `posted:1`、MR !7 が
  `posted:0, summarized:3`。**issue #1 から存在する食い違いで、今回の変更が原因ではない。**
  記述を直すか実装を揃えるかの判断が要る。
- **サブエージェントが指摘本文へHTMLエンティティを出すことがある**（12回中3回）。投稿本文は
  markdownとして扱われるため、そのままだと実体参照が文字列として見えてしまう。今回は投稿前に
  元の文字へ戻した。エージェント定義に「本文はmarkdownとして投稿される」旨が無いのが原因と
  考えられる。
- **17パターンの内訳はspecへ残す価値がある。** 今回 `root/answer-talker-verify` の9MRから
  復元できたが、これはGitLab上に残っているからであって、specには5軸しか書かれていない。
  「どのブランチがどのパターンか」の対応をspecへ書いておけば、次回の復元が要らない
  （issue #1 の反映時に「specで足りる」と判断したが、2回続けて復元作業が発生している）。
- **外部APIを叩くループは対象ごとに分けて実行する**（上記のタイムアウト）。

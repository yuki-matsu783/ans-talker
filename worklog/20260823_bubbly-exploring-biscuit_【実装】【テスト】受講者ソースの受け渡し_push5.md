## 試したこと

flow-id 3-8 として敵対的レビュー（フェーズ3の3/3回目・上限到達）を実施し、9件の指摘を受けた。
ユーザーの指示は**「このMRで全部修正する形でお願いしたい」**。9件すべてを修正した。

## いちばん重要なこと: 直前の自分の修正が壊れていた

push4 で「危なかったこと」として誇らしげに書いた `old_line` 素通しの分岐が、**GitHub経路を
壊していた**。しかも自分は同じworklogにこう書いていた。

> GitHub側は `old_line` を使っていないため、この分岐は無害である（現状のfindingsスキーマにも無い）。

`.claude/agents/answer-talker-reviewer.md` と `.claude/agents/adversarial-reviewer.md` は
**「削除行（diffの `-`）は `old_line` のみ」と明示的に指示している**。スキーマに無いどころか、
通常運転で出る形だった。**確かめずに「無い」と書いた。**

被害は小さくない。GitHubのレビュー投稿は原子的なので、`line: null` が1件混ざるだけで
**そのMRのインライン投稿が全件失敗する**。

### なぜ自分で気づけなかったか

push4 の検証は「GitLabで直したいこと」に集中していて、**GitHub側は「挙動が変わっていないこと」
だけを確認した**。実際、確認したのは `line` 無し・diff外・有効行外の3ケースで、
**`old_line` を持つfindingを一度も流していない**。新しく足した分岐を通らない入力ばかりで
「変わっていない」を確認していたことになる。

観点表の「変えないはずのものが変わっていないか」は満たしたつもりだったが、**変えた分岐を
通る入力で確かめていなければ意味が無い**。「変わっていないことの確認」は、変更箇所を通る
入力で行う必要がある。

### 直し方で迷った点

最初は「GitHub側で `old_line` → `side: "LEFT"` へ写像する」を考えたが、旧側の有効行を
別に算出する必要があり、範囲マップの構造から変わる。**サマリへ回すほうが情報を失わない**
（サマリにも指摘の全文は載る）ので、第2引数 `allow_old_line` での切り替えにした。

ついでに、GitLab側で `line` と `old_line` を両方持つケースも直した。無効な `line` を残したまま
渡すとGitLabが `line_code` を作れず400になるので、**無効な `line` だけを落とす**。

## うまくいったこと

### 指摘された境界を、実際に踏んでから直した

`jq --args` の引数長は、レビューが「500件・平均パス長64文字で失敗する」と書いていた。
そのまま信じずに再現した。

```
件数=500 平均パス長=65
旧 --args   : FAIL(exit=126) /c/Program Files/jq/jq: Argument list too long
新 --rawfile: OK 500件
0件のとき   : {"files":[]}
```

**再現しておくと、直した後の「OK」に意味が出る。** 再現せずに直すと、元々失敗しない条件で
試して「直った」と言うことになりかねない。0件のケースも併せて確認したのは、
`rtrimstr` + `split` が空文字で `[""]` を返さないかが不安だったため。

### 同じ形の欠陥が2つあると気づいた

3（空ファイル）と4（`truncated`）は、レビューでは別々の指摘だったが**同じ形**である。

- どちらも「取得できたものが全件である」と暗黙に仮定している
- 欠けたときに**エラーではなく `degraded:false` の正常応答として**下流へ流れる
- 結果として**実在するファイルについて「作られていない」という指摘が出る**

この形は `answer-talker-submission.sh` の冒頭コメントが「目的未達の状態へ静かに落ちる」として
避けると宣言しているものそのもので、**宣言した本人が2箇所で踏んでいた**。
フェーズ4でspecへ書くときは、個別の修正ではなくこの形として残したい。

### テストの置き換えを隠さなかった

`filter_findings_by_valid_lines: old_lineを持つ指摘は判定せず投稿対象` は、push4 で自分が
足したテストである。今回それが**誤りになった**ので、プロバイダごとの2組へ分割して置き換えた。

「テストが落ちたので期待値を直す」は本来もっとも危ない操作だが、今回は**実装の前提が誤って
いたと判明した**ケースなので正しい。ただし、そう判断した根拠（エージェント定義の記述）を
コメントとして残した。**後から見た人が「テストを甘くした」と読めないようにするため。**

## 危なかったこと

### `find -size 0` ではなく `-empty` を使った

最初 `find "$root" -type f -size +0` と書きかけたが、`-size` の既定単位は512バイトブロックで
切り上げのため、`-size 0` は「0バイト」を意味する一方 `+0` の解釈が処理系で紛れやすい。
`-empty` / `! -empty` なら意味が一意なので、そちらにした。

### 一覧の一時ファイルを `$tmpdir/source` の中へ置かなかった

`--rawfile` へ渡す一覧ファイルの置き場所を、危うく `$tmpdir/source/filelist.txt` にするところ
だった。**`source` 配下は受講者のツリーそのもの**で、一覧・`mapping`・禁止語のすべてがここを
見る。置いていたら、自分が作ったファイルが受講者のファイルとして列挙される。
`$tmpdir` 直下（マーカーと同じ層）にした。設計コメントの「マーカーは `$tmpdir` 直下」が
まさに同じ理由で書かれていた。

## 追記: flow-id 3-6（設計の実施）

### 設計中に実機で確かめたこと（推測で書かないため）

| 確認 | 結果 |
|---|---|
| 取得前にリポジトリサイズを知れるか | GitHub `repos/{owner}/{repo}.size`（**KB単位**）／GitLab `projects/:id?statistics=true` の `statistics.repository_size`（**バイト単位**）。単位が違う |
| GitLabの `projects/:id` をパスで解決できるか | `projects/root%2Fanswer-talker-verify` → `id: 7`。**数値IDを別途引く必要は無い** |
| フォークPRを判別できるか | GitHub `head.repo.full_name` vs `base.repo.full_name`／GitLab `source_project_id` vs `target_project_id`。**両方取れる** |
| MCPにアーカイブ取得ツールがあるか | **この環境では確認できない**（`cli` 経路のため）。決め打ちせず「実行時に判定し、無ければ段2へ落とす」設計にした |

### 設計判断の要点

- **段2をcloneではなく「ファイル単位API」にしたことで、案Aが設計から丸ごと消えた。**
  当初は「段2に案Aを持つか」を論点にしていたが、段2を同じAPI基盤にすれば
  (1) `GIT_ASKPASS` によるトークン供給、(2) `.git` の除去、(3) clone URLの組み立て、
  (4) 非対話化——の4つが**まとめて不要になる**。さらに `mcp` 経路の受け皿も兼ねる。
  レビュー指摘「段2を残すならファイル設計に案A分が要る」への回答が、**案Aを採らない**という
  形で出た。
- **段3は「失敗」ではなく正常な戻り値にする。** `stage:3, degraded:true, root:null` を
  終了コード0で返す（呼び出し側が `set -e` で落ちないように）。
- **縮退の状態は自然言語ではなくJSONのフラグで表す。** サブエージェント定義に条件付きの
  記述を並べると読み違えが起きるため、`degraded` で機械的に分岐させる。

### ダメだったこと

- **上限値の根拠が弱い。** 100MB / 500件 / 段2は50件、という数字は「演習用リポジトリの想定規模を
  大きく超える」以上の根拠が無い。設定可能にはしたが、実運用のデータが無いまま決めた値である
  ことは結果mdへ明記した。`【テスト】` で妥当性を見る。

**15件すべてを反映した。** 1回目が「計画の穴」を突いたのに対し、2回目は**設計どおり実装すると

### 設計が静かに壊れる形を3つ指摘された

- **段2の対象パスをdiffから作ると、却下したはずの案B-a（matchedのみ）と同じ状態へ落ちる。**
  しかも `degraded: false` で返るため報告上は正常に見える。`get_repo_tree` を追加し、
  「tree列挙 → ファイルごとの取得」の2段階であることを明記した。
- **`resolve` が `tmpdir` を返さないと、`cleanup --tmpdir` へ渡す値が存在しない。**
  自分で「残骸が実行のたびに増える」と警告しておきながら、**成功経路でそれを作っていた**。
- **`submission` に `files`/`truncated` を載せる場所が無い。** 決めること4(b)で「一覧を渡す」と
  決めたのに、スキーマに枠が無かった。切り詰めが起きても伝わらず、サブエージェントが
  「全ファイルを見た」と誤認する。

### 最も重い指摘: 「出る」と「届く」は別

**本設計が新たに生む指摘（未変更ファイルへのもの）は、既存の投稿経路では1件もインライン投稿
されない。** `github_add_mr_inline_comments` が `pulls/<n>/files` の有効行でふるい分け、
外れたものをすべてサマリへ回すため。**受け入れ条件1を「指摘が出る」までしか見ていなかった。**
SKILL.md の変更対象へ手順8（10件上限の数え方）・手順9（サマリでの示し方）を追加した。

皮肉なことに、**このレビュー自体は `summarized: 0` だった**——対象が新規ファイルで全行が
有効行だったからで、指摘の正しさを裏側から裏付けている。

### DDR 0061 の方針を無言で反転させかけていた

除外（バイナリ・生成物）の適用範囲を「一覧と読み取り対象」に限定していたため、
**第三者コードの識別子が禁止語から差し引かれ、正解にしか無い識別子がたまたま依存ライブラリに
含まれていればネタバレ検査を素通りする**状態だった。除外を**展開後のツリー全体**へ広げ、
禁止語の語数（`forbiddenCount` / `subtractedBySubmission`）を出すことにした。

### 自分の検証が「常に成功する」形だった

計画に書いた検証コマンドは `grep -cF -- '方式'` のように**一般的な語をファイル全体から数えるだけ**
で、今回見つかった欠落（段2の一覧取得手段・タイムアウト）は**すべてこの検査を通過していた**。
検証条件表から当該行を削除し、「充足の根拠として使わない」と理由つきで明記した。
**次に計画を書くときは「書いてあるか」ではなく「決まっているか」を検出できる形にする。**

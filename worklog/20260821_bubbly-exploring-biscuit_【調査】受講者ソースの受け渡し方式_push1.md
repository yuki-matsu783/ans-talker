# worklog: 【調査】受講者ソースの受け渡し方式（push1）

対象: issue #6 の着手と個別調査計画の作成（2026-08-21）。
全体作業計画: `plans/bubbly-exploring-biscuit.md`
個別調査計画: `plans/【調査】受講者ソースの受け渡し方式.md`
push回数: 1

## 試したこと

- issue #6 の発端はユーザーの「サブエージェントに渡すものに開発者のソースコードがあったほうが
  自然ではないか」という指摘。**本当に欠陥かを確認**するため、エージェント定義の入力仕様と
  SKILL.md の手順6を読み、実際に何が渡っているかを突き合わせた。
- `/issue-mr-flow start 6` を実行。`get_vcs_access_mode` は `cli`、標準4見出しは揃っており、
  既存の `feature-6-*` ブランチはローカル・リモートともに無かった。
- 全体作業計画をPlanモードで作成。**事前調査は軽めに留め**、`answer-talker-map.sh` の引数と
  `Provider.sh` の関数一覧だけを確認した（フェーズ2で本調査を行うため）。

## うまくいったこと

- **指摘が事実であることを確認できた。** サブエージェントへ渡すのは `diff`（hunk）・
  `reference.root`・`mapping` の3つで、受講者のワーキングツリーはローカルに存在しない。
  一方 `.claude/agents/answer-talker-reviewer.md` の「読んでよいもの」には
  「受講者の変更ファイルの中身」と書いてある。**定義と実装が食い違っている。**
- **`Provider.sh` にファイル内容を取得する関数が1つも無い**ことを関数一覧で確認した。
  案B（APIでファイル取得）を採るなら新規追加が要る、という見立てが立った。
- 影響の広さを見積もれた。`mapping` の対応付け範囲（変更ファイル対全ファイル）と、
  ネタバレ検査の禁止語（受講者**diff**の語を差し引く）の**両方が「変更ファイルしか無い」前提で
  作られている**ため、受け渡しを変えると両方に波及する。これを論点4・5として計画へ入れた。
- Draft PR #7 の作成は、1回目がbaseとの差分無しで失敗し `add_empty_commit_for_draft_mr` が
  自動リトライした（issue #1 と同じ既知の挙動。異常ではない）。

## ダメだったこと

- **HANDOFF.md を組み立てるBashコマンドが PreToolUse hook にブロックされた。** ヒアドキュメントの
  地の文に「`git` `commit`」が半角スペース区切りで連続していたため（`.claude/rules/git-workflow.md`
  に既知として記載のある誤検知）。「直接のコミット実行は〜」へ言い換えて解決した。
  **issue #1 でも同種の誤検知を踏んでおり、長文をヒアドキュメントで渡すたびに注意が要る。**
- 進捗表を復元する際、`sed -E` で `|` を未エスケープのまま使い、ERE の**選択（alternation）**と
  解釈されて全行にマッチしかけた。`grep -E '^\| (進捗|\[)'` で行を選ぶ形へ変えた。

## 追記（flow-id 2-4・敵対的レビュー1回目への対応。push2）

### 試したこと

- 人間のレビューの代わりに `/adversarial-review` を実施した（フェーズ2の実施回数 1/3）。
  対象は全体作業計画と個別調査計画の2ファイル、観点表は84行を収集。
- 13件の指摘のうち、選別表と1回10件の上限により10件を投稿、3件を報告のみとした。
  **報告のみの3件も含めて全件を計画へ反映した**（投稿の有無は「レビュアーが一度に扱える量」の
  都合であって、指摘の妥当性とは別と判断した）。

### うまくいったこと

- **計画段階の矛盾を2つ潰せた。** (1) 論点4・5の着手条件が「方式決定後」なのに方式決定は
  フェーズ3、という自己矛盾。(2) issueが定義した案B（matchedのみ）が issue #6 の目的そのものを
  満たさない、という受け入れ条件同士の衝突。**どちらも自分では気づいていなかった。**
- **`.git` 同梱の問題を拾えた。** 案Aでcloneすると受講者リポジトリのコミットメッセージが読めて
  しまい、「読んではいけない」規約が建前だけになる。正解ソース側は実装者の意図の混入源では
  ないため同じ問題が生じない、という非対称も指摘どおりだった。
- **issue #1 の判断の誤りが見つかった。** 「再現に必要な情報はspecで足りる」としたが、
  17パターンの内訳がspecに無く復元できない。論点6で拾い直すことにした。
- 検証節に実行可能なコマンドを入れた（観点表が求めている項目を満たしていなかった）。

### ダメだったこと

- **計画の自己矛盾を自分で検出できなかった。** 論点4・5の着手条件とスコープ外の記述は
  同じファイルの中で衝突していたのに、書いた本人は気づかなかった。**独立コンテキストの
  レビューが機能した実例**として記録する。
- 前提表の出どころに「DDR相当」という所在不明の表記を書いていた。DDRがあるのか無いのかを
  曖昧にしたまま前提として並べており、覆ったときに何を差し戻せばよいか分からない状態だった。
- `N3` という記号を、定義が消えていることに気づかないまま参照していた
  （issue #1 の `reports/` 由来で、flow-id 5-1 で削除済み）。**ルート REVIEW-POINTS.md が
  禁じている「寿命の短いファイルへの参照」と同種の問題を、自分で踏んでいた。**

  - `grep -n 'ATR_\|readonly\|--max-' .claude/scripts/src/answer-talker-submission.sh` で定数と

  - `resolve_main` / `emit_degraded` の jq 出力から返却キーを直接読む

## うまくいったこと

- **検証5を書いた効果がその場で出た。** 2件の誤りを拾った。
  1. **手順番号の作り話。** 全体像の図に「手順4以降が1つずつ後ろへずれた」と書いたが、
     実装は番号をずらさず `手順3b` を使っている。**書いた直後に見出しを列挙して気づき**、
     図と説明を実態へ合わせたうえで「なぜずらさないか」（issue #1 以来の記述・worklog・
     レビューコメントが指す番号が全て1つ食い違うため）を仕様として明記した。
  2. **`reason` の実例の漏れ。** `head-sha-unavailable` が spec の例に無かった。
     手順11の報告でそのまま人間の目に触れる文字列なので追加した。
- **DDR 0047 / 0061 を無効化しないという判断ができた。** 計画では「4-6 で判断する」と保留に
  していた。0047 は方針（縮退させる・スキーマはプロバイダ非依存）が維持されており、0064 は
  実装の置き場所を変えただけ。0061 は材料を広げても**差し引く量が増えるだけ**で禁止語は
  減りこそせず増えないため、守っている非対称がそのまま保たれる。**どちらも詳細化であって
  置き換えではない。**
- **DDRを4件に束ねずそのまま4件にした。** 計画の「本当に4件必要か再判断する」への答え。
  却下案の集合が互いに独立しており、1本にすると「何を却下したのか」が決定ごとに追えなくなる。
- `## 影響範囲` への追記は、既存の `### 追記: …（issue #121）` と同じ形にできた
  （`answer-talker.md` 側も同じ形で `### 追記: 受講者ソース全体の受け渡し（issue #6）` を新設）。

## ダメだったこと

- **計画に書いた検証3の期待値が誤っていた。** 「`github_filter_findings_by_valid_lines` は
  1件であること」と書いていたが、実際は**2件が正しい**。issue #6 のエントリが「この関数を
  削除した」と書く以上、そこにも関数名が現れるためである。計画を書いた時点ではエントリの
  中身がまだ決まっていなかった。
  - **件数では、守りたい不変条件を表現できない。** 守りたいのは「issue #77 の表の行が変わって
    いない」ことであって、文書全体での出現数ではない。
  - 代わりに `git diff … | grep -c '^-.*github_filter_findings_by_valid_lines'` → **0**
    （この関数名を含む行は1行も削除されていない）で確認した。こちらは**エントリを何行
    書き足しても影響を受けない**。
  - 教訓: **件数による検査は、文書が育つと必ず期待値の更新を要求してくる**ため、
    point-in-time記録の保護には向かない。差分に対する検査にする。
- **DDRの相互参照を `[[…]]`（wiki-link）で書いてしまい、書き直した。** これはAIのメモリ機能の
  記法であって、このリポジトリの慣習ではない。既存DDRは `DDR 0047` またはパスで参照している。
  **リポジトリ内の既存の書き方を確認せずに、外から持ち込んだ記法を使った**のが原因。
- 変換の途中で `純粋な削除hunク` という誤変換を作った（`grep` で見つけて修正）。

結論の要約

論点 1

adversarial-review からの再利用

findings JSONスキーマ・承認モデル・選別表・投稿関数はそのまま再利用。 観点の出どころと入力（正解ソース）が固有。 実施回数の上限機構は課さない。

論点 2

MR番号起点のdiff取得

gh api …/pulls/<n>/files を採る （gh pr diff ではない）。返却は {base, head, files:[{path,status,patch}]}。

論点 3

正解ソースの取得

ローカルパスはcloneせず読み取り専用でそのまま使う （--depth が効かないことを実機で確認）。 URLのみ shallow clone し trap で後始末。

論点 4

ファイル対応付け

機械的に決めるのは「同一パス」「ファイル名一致」まで。対応が付かない要素の 意味づけはサブエージェントに委ねる（別解を潰さないため）。

論点 5

ネタバレ検査

「正解にしか現れない識別子」を主、正規化後の行一致を補助に。 1語でも混入したらその finding を落とす （損失が非対称なため厳しい側へ倒す）。

論点 6

実例確認の題材

使い捨ての最小フィクスチャを実装時に作る。 投稿直前までを確認範囲とする案を提案（要合意）。

実装前に分かっている落とし穴

cloneの失敗をパイプで潰さない

検証中、git clone … 2>&1 | tail -3 と書いたところ cloneが fatal: で失敗しているのに $? が 0 になった（パイプの終了コードは tail のもの）。

既存の一時ディレクトリ後始末を踏襲しない

github_add_mr_inline_comments（Github.sh:334）は 末尾の rm -rf だけで、途中失敗時に一時ディレクトリが残る。 新規スクリプトは trap … EXIT INT TERM（extract-frontmatter.sh:317）に倣う。 ローカルパス指定時は消してはいけないため、返却JSONに cleanup フラグを持たせる。

大きなdiffをコマンド置換で受けない

diffのサイズは受講者の実装規模に比例して無制限に大きくなる。Windowsのコマンドライン長上限 （実測 約32KB）に容易に達するため、必ずファイルへリダイレクトすることを SKILL.md 側の規約として明記する。

パス一致だけの対応付けは、最も指摘したいケースで失敗する

受講者が1ファイルに詰め込んでいる場合、正解側の3ファイルはどれもパス一致しない。 「分割単位が違う」こと自体が指摘対象なので、パス一致に依存した設計はここでちょうど機能しなくなる。

ネタバレ検査: 誤検知と見逃し

誤検知しやすい（＝除外が要る）

  1. if err != nil { / return nil, err — 定型。正解にもあるが何もネタバレしない
  2. func main() { / package main — 言語の構文
  3. 一般語（repository / handler / service / config）— 設計原則を説明する言葉として指摘に必要

→ 抽出時に「受講者側diffにも現れる語」「一般的な英単語・キーワード」「短すぎる語」を除外しないと、検査が指摘をほぼ全滅させる。

見逃しやすい

  1. 変数名だけ変えた転記（userRepository → repo）
  2. 空白・改行を変えた転記 → 正規化を補助に置く理由
  3. 構造そのものの転記（「XをA/B/Cの3つに分け、AがBを呼ぶ」）— コード片ではないがネタバレそのもの。機械検査では原理的に捕まえられない

→ 3番目があるため、サブエージェント側の規約は検査で代替できない。二重化は必然。

受講者ソースの受け渡しの設計結果

計画: plans/【設計】受講者ソースの受け渡し.md（決めること0〜5）

結論

1. アーカイブ一括取得を主経路に

git clone（案A）は採らない。速度ではなく、.git の除去と資格情報供給という2つの追加作業が要らないことが理由。

2. 段2をcloneではなくAPIに

段2を同じAPI基盤のファイル単位取得にしたことで、案Aが設計から丸ごと消えた。mcp 経路の受け皿も兼ねる。

3. 縮退はフラグで表す

段3では submissionOnly の意味も禁止語の材料も従来へ戻る。自然言語ではなく degraded フラグで定義側を分岐させる。

縮退の3段

段1 アーカイブ一括取得 tarball / archive.tar.gz

1回・ファイル数非依存・.git を含まない（1122ms / 2044ms）。使う条件: cli 経路かつリポジトリサイズが上限以内。

↓ API不達 / サイズ上限超過 / mcp で対応ツールなし
段2 ファイル単位API contents / files

672ms / 1027ms × ファイル数のため、50件を上限とする。段1と同じ認証基盤で済み、mcp 経路（get_file_contents）の受け皿にもなる。

↓ 件数上限超過 / API不達
段3 hunk のみで続行し、報告する

中止しない（truncatedFiles／capped と同じ流儀）。「失敗」ではなく正常な戻り値として stage:3, degraded:true, root:null を終了コード0で返す。

段3で何が従来へ戻るか

コンポーネント段1・2（取得できた）段3（取得できない）
mapping の範囲受講者の全ファイル 対 正解の全ファイル変更ファイル 対 正解の全ファイル
submissionOnly正解に無いファイル今回のMRで追加したファイル
禁止語の材料受講者ソース全体受講者diff

定義へ無条件に「submissionOnly は正解に無いファイル」と書くと、縮退時の実際の出力と食い違い、issue #6 が問題にした「渡していないものを読んでよいと書いてある」のと同型の不一致を新たに作る。入力JSONは {"stage":1|2|3, "degraded":bool, "fileCount":N} を持たせる。

設計中に実機で確かめたこと

取得前にサイズを知れるか

GitHub repos/{owner}/{repo}.size（KB単位）／ GitLab statistics.repository_size（バイト単位）。単位が違う。

GitLabの :id の解決

projects/root%2Fanswer-talker-verify → id: 7。数値IDを別途引く必要は無い。

フォークPRを判別できるか

GitHub head.repo.full_name ／ GitLab source_project_id。両方取れるので、取得元は head 側にする。

MCPのアーカイブ取得ツール

この環境では確認できなかった（cli 経路のため）。決め打ちせず実行時に判定し、無ければ段2へ落とす設計にした。

上限とバイナリの扱い

項目既定値扱い
リポジトリサイズ100MB超えたら段2へ。--max-size-kb で変更可能
段2の対象件数50件超えたら段3へ（50×672ms ≒ 34秒が現実的な上限）
一覧に載せる件数500件超えたら切り詰め、実件数を報告
バイナリ除外拡張子ではなくNULバイトの有無で判定（拡張子の網羅は破綻する）
生成物ディレクトリ除外node_modules/ dist/ build/ target/ vendor/ __pycache__/ .venv/

⚠ 上限値の根拠は「演習用リポジトリの想定規模を大きく超える」以上のものが無い。実運用のデータが無いまま決めた値であり、【テスト】で妥当性を見る。

却下した案（7件）

  1. cloneを主経路にする — .git の除去が運用頼みになり、忘れた時点で規約が破れる
  2. cloneを段2に残す — 使われない可能性が高い経路のために4つの実装が増える
  3. matched のみ取得（issue本文の案B） — issue #6 の目的そのものを満たせない
  4. ファイル単位APIを主経路にする — 50ファイルで34〜51秒
  5. 禁止語の材料を広げない — 実測により、hunk外に基づく指摘だけが必ず drop されると確定済み
  6. 段3で中止する — 縮退しても報告して続行するのが既存の流儀
  7. 縮退の状態を自然言語で定義へ書く — 条件付きの記述は読み違えが起きる

DDR候補（フェーズ4で判断）

  1. 受講者ソースの取得はアーカイブ一括取得を主経路とし、cloneは採らない
  2. 縮退は3段とし、段2をcloneではなくファイル単位APIにする（mcp 経路の受け皿を兼ねる）
  3. 禁止語の材料へ受講者ソース全体を加える — DDR 0061「誤検知の側へ倒す」との関係を整理する（差し引かれるのは受講者自身が書いている語なので見逃しは増えない、というのが本設計の判断）
  4. 縮退の状態はフラグで表し、定義を分岐させる

受講者ソースの受け渡し方式の調査結果

計画: plans/【調査】受講者ソースの受け渡し方式.md（6論点）

結論

1. 案Aは成立した

issue #1 の「ローカルGitLabへ git で到達できない」は環境の制約ではなく、資格情報の供給方法の問題だった。両プロバイダで MR head を取得でき、headSha と一致。

2. 案B-d（アーカイブ）が最有力

計画に無かった選択肢。両プロバイダともAPI 1回で全ファイルが取れ、ファイル数に依存せず、.git を含まない。

3. 禁止語の拡張は必須

実測で裏付け。広げなければ、issue #6 の目的である「hunk外ファイルに基づく指摘」だけが選択的に落ちる。

方式の比較（論点1・2・3）

方式 呼び出し回数 実測 .git 目的達成 評価
案A: shallow clone 1回 両プロバイダで成功 同梱（除去必須） ○ gitの資格情報供給が要る

論点1: issue #1 の結論を覆した

認証なし（issue #1 の再現）

fatal: could not read Username for
'http://localhost:8929':
terminal prompts disabled

原因はシステムスコープの credential.helper=manager（Git Credential Manager）。非対話環境ではプロンプトを出せずに失敗していた。

GIT_ASKPASS でトークンを供給

* [new ref] refs/merge-requests/9/head
              -> atr-head
c3c0fa6d01f1c5039210d8a1527aa62357b3e6c3

グローバル設定は一切変更していない（前後で git config --global の出力が同一であることを確認済み）。

落とし穴 1

credential.helper にシェル関数を渡す方式は git bash でハングする（2分でタイムアウト）。GIT_ASKPASS を使う。

落とし穴 2

use_target_repo のJSONの .host はポートを落とす（localhost）。URLは環境変数 GITLAB_HOST から組み立てる。

落とし穴 3

Windows版 tar はドライブレターをホスト名と誤解する。--force-local を付ける。

論点5: 禁止語の拡張が必須であることを実測

finding内容結果
A 「読み込みの責務は read_lines のような単位で切り出せる」 drop（反応語: read_lines）
B 「take_lines と keep_lines は同じ関心を2つに分けている」 残る
C 「入力・絞り込み・出力の3つの関心が1つの関数に同居している」 残る

この drop 自体は現仕様どおり正しい。問題は、受講者が hunk外のファイルで read_lines を定義していた場合も同じく drop されること。差し引き集合の材料が .files[] | .patch, .path, .oldPath（＝diff）からしか作られないため、受講者ソース全体を渡しても材料は変わらない。

論点6: 17パターンは「specからは復元不能／実環境からは復元できた」

specだけでは復元できない

specにあるのは5軸のみ。全組み合わせは 5×3×3×2×2 = 180通りあり、どの17個を選んだかは軸からは決まらない。issue #1 の「再現に必要な情報はspecで足りる」という判断は誤りだった。

実環境が残っていた

ローカルGitLabに削除予定の状態で残存（marked_for_deletion_on: 2026-08-20）。ユーザー承認のうえ POST /projects/:id/restore で復元し、9つのMR・10ブランチを回収した。

ブランチ変更ファイル対応する軸

p2-alt-splitA io.sh / A transform.sh / M main.sh実装: 別解（2分割）

GitHub側は spec に手順が無かったため、ユーザーが用意した yuki-matsu783/test-repo へ Contents API で題材を投入して確立した（GitLabの Commits API と対称）。AIエージェントはリポジトリを作成していない。

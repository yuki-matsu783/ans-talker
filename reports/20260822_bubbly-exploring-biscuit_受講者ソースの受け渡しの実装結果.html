hunkヘッダの解釈は1箇所へ寄せた

GitHub側のロジックをGitLabへ写すと、同じ正規表現が2箇所に増えて片方だけが直る余地が残る。APIの返却形の違いだけを各プロバイダが吸収する形にした。

  • Provider.sh: valid_ranges_from_patches / filter_findings_by_valid_lines を新設（プロバイダ非依存の純粋関数）
  • Github.sh: 正規化のみに縮小し委譲。github_filter_findings_by_valid_lines は削除して統合
  • Gitlab.sh: gitlab_valid_ranges_from_diffs_json を新設し、投稿前に振り分け

side（"RIGHT"）の既定値付与は共通関数から外し github_build_review_payload へ寄せた。GitLabの position は side を持たないため。

壊さないために置いた分岐が2つある

1. 差分を取得できなければ振り分けず全件投稿を試みる。 空の範囲マップを渡すと全件が「有効行なし」と判定されてサマリへ落ちる。ローカルGitLabの接続断は実測で頻発しており、これは例外処理ではなく通常経路。

2. old_line を持つ指摘は判定せず通す。 範囲マップは新ファイル側しか持たず、純粋な削除hunkでは新側の有効行が空になる。落とすとGitLabが受け付けられる指摘まで捨てる。

最も重い1件は、直前のレビュー対応で自分が入れた分岐だった

filter_findings_by_valid_lines の old_line 素通しはGitHub経路を壊していた。共通関数に置いたためGitHubからも通り、line: null のコメントを作る。GitHubのレビュー投稿は原子的で、1件でも不正な行が混ざるとそのMRのインライン投稿が全件失敗する。

push4のworklogには「GitHub側は old_line を使っていないため無害」と書いていたが、.claude/agents/*.md は「削除行は old_line のみ」と明示的に指示している。前提そのものが誤っていた。

修正後、old_line のみの指摘を含むfindingsをGitHub経路へ流し、ペイロードに line: null が0件であることを確認した（修正前は1件混入）。

検証で新たに判明したこと

1. line を持たない指摘の扱いが、プロバイダで異なる → 解消済み

GitHub は有効行へ寄せてインライン投稿（posted:1）、GitLab は必ずサマリへ回る（posted:0, summarized:3）。adversarial-review/SKILL.md の記述は無条件だがGitHub限定の挙動だった。GitLab側に有効行の算出ロジックが無かったためである。issue #1 から存在する食い違いで、今回の変更が原因ではない。
flow-id 3-9 のレビューで「実装をそろえる」判断を受け、GitLab側へ実装した（下記）。

2. サブエージェントが本文へHTMLエンティティを出すことがある

12回の起動のうち3回で実体参照が現れた。投稿本文はmarkdownのため、そのままだと文字列として見えてしまう。今回は投稿前に元の文字へ戻した。エージェント定義に「本文はmarkdownとして投稿される」旨の記述が無いことが原因と考えられる。

3. ローカルGitLabの接続断は、段2に限らない

MRのメタ情報取得（段1の入口）でも発生した（reason:"head-sha-unavailable"）。リトライで成功する一過性のもの。縮退は毎回設計どおり働いたが、リトライの検討対象は段2だけではない。

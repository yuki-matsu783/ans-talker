## 決めること1: 受け渡し方式（決定: アーカイブ一括取得）

**GitHub `repos/{owner}/{repo}/tarball/{ref}` ／ GitLab
`projects/:id/repository/archive.tar.gz?sha=<sha>` を主経路とする。**

| | アーカイブ（採用） | clone（不採用） |
|---|---|---|
| 呼び出し回数 | 1回（ファイル数非依存） | 1回 |
| 実測 | 1122ms / 2044ms | 同程度 |
| `.git` | **含まない** | **同梱。除去が必須** |
| 認証 | `gh`/`glab` の認証をそのまま使う | `GIT_ASKPASS` 等の供給が別途要る |

**採用理由は速度ではなく、追加作業が2つ要らないこと。** とくに `.git` は、サブエージェント定義の
「コミットメッセージを読んではいけない」規約を**構造的に守れるか、除去を忘れないという運用に
頼るか**の差になる（調査で、cloneすると `git log` からMRのコミットメッセージが実際に読めることを
確認済み）。

## 決めること2: 縮退（決定: 3段。段2はcloneではなくファイル単位API）

| 段 | 手段 | 使う条件 | 失敗・不可の条件 |
|---|---|---|---|
| 1 | **アーカイブ一括取得** | `cli` 経路。リポジトリサイズが上限以内 | API不達、サイズ上限超過、`mcp` 経路で対応ツールが無い |
| 2 | **ファイル単位API**（GitHub `contents` / GitLab `files`） | 取得対象が件数上限以内 | 件数上限超過、API不達 |
| 3 | **hunk のみで続行し、その事実を報告する** | 常に可能 | — |

**段2をcloneではなくファイル単位APIにしたのが本設計の要点である。**

- cloneを段2に置くと、`GIT_ASKPASS` によるトークン供給・`.git` の除去・clone URLの組み立て
  （`use_target_repo` のJSONは**ポートを落とす**ため環境変数から組む）・`GIT_TERMINAL_PROMPT=0` の
  4つが設計に増える。
- ファイル単位APIなら**段1と同じ認証基盤**（`gh`/`glab`）で、`.git` の問題も生じない。
- さらに **`mcp` 経路の受け皿にもなる**（下記）。

コストは調査の実測どおり 672ms（GitHub）/ 1027ms（GitLab）× ファイル数。これは件数上限で抑える。

### 段3（縮退）における各コンポーネントの挙動

**受講者ソースが手に入らない段3では、本設計の3つの変更がいずれも成立しない。**

**入力JSONへ縮退フラグを持たせ、サブエージェント定義の分岐を機械的にする**（自然言語の条件付き

## 決めること3: ファイルごとの変更設計

### `.claude/scripts/src/vcs/Provider.sh`

**2つの関数を追加する。**

```
get_mr_head_source <mr番号> <出力先ディレクトリ>
  → {"stage":1|2,"root":"<絶対パス>","fileCount":N,"headSha":"…","truncated":true|false}
get_repo_file <repo> <ref> <path>            # 段2で使う。標準出力へ内容
  → 生のファイル内容（base64はデコード済み）
```

- **取得元は head 側のリポジトリ/プロジェクトにする**（フォーク対応）。実測で、GitHubは
  `head.repo.full_name`、GitLabは `source_project_id` が取れることを確認した。
  `head.repo` が `null`（フォーク削除済み）の場合は段3へ落とす。
- **`ref` には `headSha` を使う**（ブランチ名を使わない）。ブランチ名だと、レビュー中に受講者が
  追加で反映した時点で**diffのhunkと取得したソースが別のコミットになり**、存在しない行を
  指摘しうる。
- **GitLabの `projects/:id` はURLエンコードしたパスで解決できる**（実測: `projects/root%2F…` →
  `id: 7`）。数値IDを別途引く必要はない。
- 返却のキー集合は GitHub/GitLab で一致させる（`get_mr_changed_files` の流儀）。

### `.claude/scripts/src/answer-talker-submission.sh`（新規）

```
answer-talker-submission.sh resolve --mr <番号> --tmpdir <パス> [--max-size-kb N] [--max-files N]
  → {"stage":1|2|3,"root":"…"|null,"fileCount":N,"degraded":true|false,"reason":"…"}
answer-talker-submission.sh cleanup --tmpdir <パス>
  → {"removed":true|false,"reason":"…"}
```

- `answer-talker-reference.sh` と**同じ形**にする（マーカーファイル `.answer-talker-submission` を
  置き、`cleanup` はそれを確認してからでないと削除しない・冪等）。
- 展開は **`tar --strip-components=1 --force-local`**（アーカイブは
  `<owner>-<repo>-<sha7>/` のようなprefixを持つ。`--force-local` が無いとWindows版 `tar` が
  ドライブレターをホスト名と解釈して失敗する）。
- **`resolve` は失敗時に自分が作った一時ディレクトリを削除してから非0で返す**（既存の
  `clone_reference` と同じ）。これが無いと、展開に失敗したときパスが呼び出し側へ渡らず、
  手順10の `cleanup` に渡す先が無くなって**残骸が実行のたびに増える**。
- **段3は「失敗」ではない。** `stage: 3, degraded: true, root: null` を返して**終了コード0**とする
  （呼び出し側が `set -e` で落ちないように）。

### `.claude/scripts/src/answer-talker-map.sh`

- `--submission-root` を追加し、渡された場合は「受講者の**全**ファイル」対「正解の全ファイル」で
  対応付ける。渡されない場合は従来どおり（段3）。
- 出力へ `"scope": "full"|"diff"` を追加し、`submissionOnly` がどちらの意味かを機械的に判別できる
  ようにする。

### `.claude/scripts/src/answer-talker-spoiler-check.sh`

- **`--submission-root` を追加**し、差し引き集合の材料へ**受講者ソース全体の識別子**を加える
  （現在は `.files[] | .patch, .path, .oldPath` のみ）。
- 出力の `drops` はそのまま。**`"materialScope": "full"|"diff"` を追加**して、どちらの材料で
  判定したかを報告へ出せるようにする。

### `.claude/agents/answer-talker-reviewer.md`

- 入力仕様へ `submission`（`root` / `stage` / `degraded` / `fileCount`）を追加。
- 「読んでよいもの」を実態と一致させる（**issue #6 の中核**）。
- **手順を追加する**: 「`submission.root` 配下のファイル一覧を確認し、`mapping.matched` に
  無いファイルにも目を通す」。
- **`degraded: true` のときの分岐を明記**（`submissionOnly` は「今回追加したファイル」の意味に
  なる／受講者ソース全体は読めない）。

## 決めること5: サイズ・件数の上限とバイナリの扱い

**取得前にサイズを知る手段があることを実測で確認した。**

| | 取得前のサイズ | 実測値（演習用リポジトリ） |
|---|---|---|
| GitHub | `repos/{owner}/{repo}` の `size`（**KB単位**） | 1 |
| GitLab | `projects/:id?statistics=true` の `statistics.repository_size`（**バイト単位**） | 6105 |

| 項目 | 既定値 | 根拠・扱い |
|---|---|---|
| リポジトリサイズの上限 | **100MB** | 超えたら段2へ。演習用リポジトリの想定規模を大きく超える値。`--max-size-kb` で変更可能 |
| ファイル件数の上限 | **500件** | 段2の呼び出し回数の上限でもある（500×672ms ≒ 5.6分は現実的でないため、**段2は50件を上限**とし、超えたら段3） |
| 一覧に載せる件数 | **500件** | 超えたら切り詰め、`truncated: true` と実件数を報告（`truncatedFiles` と同じ扱い） |
| バイナリ | **除外** | 拡張子ではなく**NULバイトを含むか**で判定する（拡張子の網羅は破綻する） |
| 生成物ディレクトリ | **除外** | `node_modules/` `dist/` `build/` `target/` `vendor/` `__pycache__/` `.venv/` |

**除外はサブエージェントへ渡す一覧と読み取り対象に対して行う**（アーカイブの展開自体は
まとめて行うため、除外しても取得コストは変わらない）。

## 却下した案

1. **`git clone`（案A）を主経路にする** — `.git` の除去と資格情報供給という2つの追加作業が
   増える。とくに `.git` は規約を運用で守る形になり、忘れた時点で破れる。
2. **cloneを段2（フォールバック）に残す** — 段2をファイル単位APIにすれば同じ認証基盤で済み、
   `mcp` 経路の受け皿にもなる。cloneを残すと、使われない可能性が高い経路のために4つの実装が
   増える。
3. **`mapping.matched` のみ取得（issue本文の案B）** — 変更していないファイルが入らず、
   **issue #6 の目的そのものを満たせない**。
4. **ファイル単位APIを主経路にする** — ファイル数に比例して 672〜1027ms かかる。50ファイルで
   34〜51秒。
5. **禁止語の材料を広げない（現状維持）** — 調査の実測により、広げないと **hunk外ファイルに
   基づく指摘だけが必ず drop される**ことが確定している。受け入れ条件1と両立しない。
6. **段3（hunkのみ）で中止する** — `truncatedFiles` / `capped` と同じく、**縮退しても報告して
   続行する**のが既存の流儀。中止は演習の講師にとって使えない挙動になる。
7. **縮退の状態を自然言語でサブエージェント定義へ書く** — 条件付きの記述は読み違えが起きる。
   入力JSONの `degraded` フラグで分岐させる。

## DDR候補（フェーズ4で判断）

1. **受講者ソースの取得はアーカイブ一括取得を主経路とし、cloneは採らない**（却下案1・2・4を含む）。
2. **縮退は3段とし、段2をcloneではなくファイル単位APIにする**（`mcp` 経路の受け皿を兼ねる）。
3. **ネタバレ検査の禁止語の材料へ受講者ソース全体を加える** — **DDR 0061「誤検知の側へ倒す」との
   関係を整理する必要がある**。差し引かれるのは「受講者が自分のリポジトリに実際に書いている語」で
   あり、それが指摘本文に出ることは転記ではないため、**見逃しは増えない**というのが本設計の判断。
4. **縮退の状態は入力JSONのフラグで表し、サブエージェント定義を分岐させる**（渡していないものを
   「読んでよい」と書く不一致を再発させない）。

# issue #6 全体作業計画 — サブエージェントへ受講者のソースコード全体を渡す

- issue: [#6 answer-talker のサブエージェントへ受講者のソースコード全体を渡す](https://github.com/yuki-matsu783/ans-talker/issues/6)
- ブランチ: `feature-6-pass-submission-source-to-reviewer`
- PR: [#7](https://github.com/yuki-matsu783/ans-talker/pull/7)（Draft）
- ベースブランチ: `main`（最新は `52348cb`＝PR #2 のマージコミット。issue #1 の成果物を含む）

## Context（なぜこの変更を行うか）

issue #1 で作った `answer-talker` は、サブエージェントへ次の3つを渡す。

| 渡すもの | 受け取り方 |
|---|---|
| `diff` | 受講者MRの変更ファイルと**差分本文（hunk）** |
| `reference.root` | 正解ソースのルートパス。**配下の全ファイルをReadで読める** |
| `mapping` | 受講者の変更ファイルと正解ファイルの対応付け |

**正解は全部読めるのに、受講者側はhunkしか見えない。** 受講者のMRは別リポジトリにあり、
APIで差分を取得するだけなので、ワーキングツリーがローカルに存在しないためである。

このスキルの観点は「責務の分割単位」「層と依存の向き」——**リポジトリ全体の構造**に関する
判断である。hunkだけでは次の3つが見えない。

1. **今回変更していないファイルに責務が置かれている場合。** `answer-talker-map.sh` の対応付けは
   「受講者の**変更**ファイル」対「正解の**全**ファイル」なので、受講者リポジトリに既にあるが
   今回のMRで触っていないファイルは `matched` にも `submissionOnly` にも現れない。
2. **既存ファイルを一部だけ変更したMR**では、その関数の全体像すら見えない。
3. issue #1 の検証でパターン②（別解）を正しく判定できたのは、`io.sh` が新規追加でhunkに全文が
   入っていたためであり、**たまたま成立していた**。

加えて、**定義と実装が食い違っている**。`.claude/agents/answer-talker-reviewer.md` の
「読んでよいもの」には「`reference.root` 配下のファイル、**受講者の変更ファイルの中身**」と
書いてあるが、後者は渡していない。渡していないものを「読んでよい」と書いており、次に読む人を
確実に誤解させる。

**成果物の性質**: issue #1 と同じく `.claude/` 配下のAIアセット（スキル・サブエージェント定義・
スクリプト・spec/DDR）の変更である。

## issueの粒度判定（分割提案の要否）

**分割は提案しない。** 受け入れ条件は7項目あるが、同型の成果物の並列列挙ではない。

## フェーズ2〈調査〉

**実施する。** 受け渡し方式が決まらないと設計に入れず、しかも**方式の可否が実機の制約に
依存する**（下記）。issue本文に候補として案A・案Bを書いてあるが、どちらが成立するかは
未確認である。

調査したい論点（個別調査計画 flow-id 2-1 で確定させる。ここでは枠と当たりのみ）:

1. **案A（MRのheadを shallow clone）が成立する条件。** issue #1 の検証時、ローカルGitLabへ
   `git` で到達できなかった（HTTP cloneは資格情報プロンプトが無効で失敗、SSHは公開鍵が無い）。
   **どの条件なら成立し、どの条件で失敗するか**を実機で切り分ける。GitHubの公開/非公開、
   self-hosted GitLab、認証済み `gh`/`glab` が持つ資格情報を git が使えるか。
2. **案B（APIでファイル全文を取得）の実現手段。** `Provider.sh` に**ファイル内容を取得する関数は
   現在1つも無い**（関数一覧を確認済み。`get_mr_changed_files` が最後に追加されたもの）。
   GitHubの `repos/{owner}/{repo}/contents/{path}?ref=`、GitLabの
   `projects/:id/repository/files/:path?ref=` の返却形・ページング・サイズ上限・
   バイナリの扱いを確認し、**両プロバイダで共通形へ正規化できるか**を見る。
   `get_mr_changed_files` で確立した「キー集合を一致させる」流儀を踏襲できるか。
3. **どこまで取得するか。** 「全ファイル」と言っても、受講者リポジトリの規模は未知である。
   対応が付いたファイルだけか、リポジトリツリー全体か、拡張子・サイズで絞るか。
   **案Aなら丸ごと手に入るが、案Bでは取得範囲の設計がそのままコストになる**ため、
   2つの案で答えが変わりうる。
4. **`answer-talker-map.sh` の対応付け範囲を広げるか。** 「受講者の全ファイル」対
   「正解の全ファイル」へ広げると、`submissionOnly` の意味が変わる（今は「今回追加した
   ファイル」、広げると「正解に無いファイル」）。サブエージェント側の手順への影響を見る。
5. **ネタバレ検査の禁止語の作り方を見直すか。** 現在は
   `正解の識別子 − 受講者diffに現れる語 − 除外語 − 3文字以下`。受講者ソース全体が手に入るなら
   「受講者diffの語」を「受講者ソース全体の語」へ広げられ、**誤検知が減る方向に効く**はず。
   ただしDDR 0061 は「誤検知の側へ倒す」と決めており、**その前提を弱めることにならないか**を
   確かめる必要がある（減るのは誤検知であって、見逃しが増えるなら話が別）。
6. **検証環境の再構築。** issue #1 の演習用プロジェクトは flow-id 5-1 で削除済み。
   spec の「検証の再現手順の要点」から作り直せるかを確認する（**再現手順として実際に機能するか
   の検証も兼ねる**）。

調査結果は `reports/日付_bubbly-exploring-biscuit_<内容>.md`（正文）と同名の `.html` に記録する。
個別調査計画には結果を書かない。

## フェーズ3〈作業〉

調査結果を受けて個別作業計画を立てる。現時点で見込んでいる変更は次のとおり
（**確定ではなく、フェーズ2の結果で変わりうる**）。

| 変更対象 | 見込んでいる内容 |
|---|---|
| `.claude/scripts/src/vcs/Provider.sh` | 案Bを採るならファイル内容取得関数を追加。案Aのみで足りるなら変更なし |
| `.claude/scripts/src/answer-talker-*.sh` | 受講者ソースを用意するスクリプト（`answer-talker-reference.sh` と対称の `resolve`/`cleanup` か、同スクリプトの引数拡張か）。`answer-talker-map.sh` の対応付け範囲 |
| `.claude/scripts/src/answer-talker-spoiler-check.sh` | 禁止語の材料を「受講者diff」から「受講者ソース全体」へ広げるかどうか |
| `.claude/agents/answer-talker-reviewer.md` | 入力仕様に `submission` を追加。**「読んでよいもの」を実態と一致させる**（この修正だけは方式によらず必須） |
| `.claude/skills/answer-talker/SKILL.md` | 手順2〜6と後始末（手順10）。取得できなかった場合の縮退も書く |

**分割方針**: `【設計】` と `【実装】【テスト】` は分けることを既定とする（受け渡し方式の決定は
6ファイルに波及するため、実装前に人間の合意を取りたい）。フェーズ2で方式が明確に定まれば
併記に変更してよい。

## 検証（受け入れ条件の確認方法）

| 受け入れ条件 | 確認方法 |
|---|---|
| サブエージェントが受講者のソースを**全体として**読める | 実際に `answer-talker-reviewer` を起動し、**hunkに現れないファイル**の内容に基づく指摘が出ることを確認する |
| `git` 到達不可の環境でもフォールバックが機能し、GitHub・GitLab両方で実機確認 | ローカルGitLab（git到達不可が既知）とGitHubの実MRの両方で実行する |
| エージェント定義の「読んでよいもの」が実態と一致 | 定義に書いたものが実際に渡っているかを、起動時の入力JSONと突き合わせる |
| `mapping` の範囲の判断がspecに記録されている | `.claude/docs/spec/answer-talker.md` の該当節 |
| ネタバレ検査の禁止語の判断が理由とともに記録されている | 同上、またはDDR |
| spec更新・必要ならDDR追加 | フェーズ4。DDR番号の重複が無いこと |
| **issue #1 の17パターン相当の検証をやり直す** | とくに**②別解・⑤ほぼ正解で分割単位の指摘が出ない**ことを再確認する。**受講者ソース全体が見えるようになると、指摘が増える方向に働きうる**ため、ここが最大の回帰リスクである |

## 進め方の前提

- コミットはすべて `commit` スキル経由（`git commit` の直接実行はhookでブロックされる）
- 各pushの直後と flow-id 5-2 で `check-base-conflicts.sh` を実行する（本セッションはローカル
  実行のため購読は行わず、手動確認とする）
- 敵対的レビューは対話セッションのためAIから自律起動しない
- **`answer-talker-reviewer` サブエージェントの起動は、ユーザーの許可を得てから行う**
  （issue #1 でも都度許可を得た）

# 【調査】受講者ソースの受け渡し方式

- issue: [#6](https://github.com/yuki-matsu783/ans-talker/issues/6) / PR: [#7](https://github.com/yuki-matsu783/ans-talker/pull/7)
- 全体作業計画: `plans/bubbly-exploring-biscuit.md`（flow-id 1-5で承認）
- 対象フェーズ: フェーズ2〈調査〉（flow-id 2-1〜2-10）

## 目的

**受講者のソースコード全体をサブエージェントへどう渡すかを、決められる状態にする。**
issue本文には案A・案Bを候補として書いたが、**どちらが成立するかは実機で未確認**であり、
このままでは設計（フェーズ3）に入れない。

**この計画には結果を書かない。** 調査結果は
`reports/日付_bubbly-exploring-biscuit_<内容>.md`（正文）と同名の `.html` へ記録する
（`.claude/skills/issue-mr-flow/SKILL.md`「計画と実施結果の分離」）。

## 前提（issue #1 から引き継ぐ確定事項）

| 前提 | 出どころ |
|---|---|
| 対象リポジトリの切り替えは `use_target_repo`（`GH_REPO`/`GITLAB_REPO` の環境変数）で行う。**これは `gh`/`glab` に効く仕組みであって `git` には効かない**（論点1で扱う） | issue #1 flow-id 3-8 で合意。**DDRは無い**。記録先は `spec/answer-talker.md`「対象リポジトリの切り替え」 |
| 差分取得の返却は GitHub / GitLab で**キー集合を完全に一致**させてある | issue #1 flow-id 2-9 で合意。**DDRは無い**。記録先は `spec/answer-talker.md`「差分の取得」 |
| ネタバレ検査は**誤検知の側へ倒す**。識別子は分割しない | issue #1 flow-id 3-4 で合意。`.claude/docs/ddr/0061-ネタバレ検査は誤検知の側へ倒し識別子は分割しない.md` |
| 正解ソースの**ローカルパスはcloneしない** | issue #1 flow-id 3-8 で合意。`.claude/docs/ddr/0060-正解ソースがローカルパスならcloneしない.md` |
| 演習の題材はこのリポジトリに残さない | issue #1 flow-id 1-5 / 2-9 で合意。記録先は `spec/answer-talker.md`「検証の再現手順の要点」 |

## 調査する論点

### 論点1: 案A（MRのheadを shallow clone）が成立する条件

**調べること**: どの条件なら成立し、どの条件で失敗するか。

issue #1 の検証時、ローカルGitLab（`localhost:8929`）へ `git` で到達できなかった。

- HTTP clone → `fatal: Cannot prompt because user interactivity has been disabled.`
- SSH（ポート2224） → `Permission denied (publickey)`。`glab api user/keys` は空

**この失敗が「この環境固有」なのか「認証を要するリポジトリ一般」なのか**を切り分ける。

| 確認項目 | 実行するコマンド | 成立とみなす条件 |
|---|---|---|
| **clone URLを決められるか**（3ケース） | `use_target_repo <値> \| jq '{provider, host, owner, repo}'` を、`--repo` が(1)URL・(2)`owner/repo`・(3)省略（cwd既定）の各形で実行 | 3ケースすべてでURLを組み立てられる |
| 資格情報ヘルパの現状 | `git config --global --get-regexp '^credential'`（**確認の前後で取得し、両方を結果mdへ残す**） | 実行後に実行前と一致する（＝汚していない） |
| 認証済みCLIの資格情報をgitが使えるか | `git -c credential.helper='!gh auth git-credential' clone ...` のように**その場限りでオーバーライド**する。GitLab側の相当手段（`glab auth git-credential` 等）も同様に確認する | プロンプトを出さずに成功する |
| 公開リポジトリ（認証不要） | `git clone --depth 1 --single-branch <公開URL> <tmp>` | 終了コード0 |
| **MR headの取得** | 下記「MR headを取得する手順」（GitHub・GitLabの両方） | 取得したheadが対象MRの `headSha` と**一致する** |
| **到達不可を人工的に作れるか** | 到達できないホスト名へ差し替える／`GIT_TERMINAL_PROMPT=0` かつ資格情報ヘルパ無しで非公開リポジトリへ | gitが失敗し、フォールバックが発動する |
| 受講者側一時領域の後始末 | `answer-talker-reference.sh` のマーカー方式（`.answer-talker-reference` を確認してから削除）を流用できるか | 手順6〜9で失敗しても残骸が残らない形にできる |

**`use_target_repo` は `git` には効かない。** この関数が行うのは `GH_REPO` / `GITLAB_REPO` /
`GITLAB_HOST` の export であり、`git clone` / `git fetch` はこれらを一切参照しない。案Aには
**受講者リポジトリのclone URL**が別途要る。しかも `SKILL.md` の `--repo` は `owner/repo` 形式を
許し、その場合 `use_target_repo` の返す `host` は空になる（URL指定時のみ埋まる）。
**self-hosted GitLab（issue #1 の検証環境である `localhost:8929`）では、`owner/repo` 形式・省略時に
ホストとポートが決まらず、URLを組み立てられない可能性がある。** これは実機の認証可否以前の、
**入力仕様に起因する非成立条件**であり、該当する場合は案Aの制約として明記する。

**MR headを取得する手順**（**カレントディレクトリで実行しない**）:

```bash
tmp="$(mktemp -d)"
git -C "$tmp" init -q
git -C "$tmp" remote add origin '<受講者リポジトリのURL>'
# GitHub: refs/pull/<n>/head ／ GitLab: refs/merge-requests/<iid>/head
git -C "$tmp" fetch --depth 1 origin '<上記の参照>:refs/heads/atr-head'
git -C "$tmp" checkout -q atr-head
git -C "$tmp" rev-parse HEAD   # ← 対象MRの headSha と一致すること
```

**cwdで `git fetch origin 'refs/pull/<n>/head:...'` を実行してはいけない。** `origin` はこの
リポジトリを指すため、**このリポジトリのPR（本作業のPR #7 を含む）のheadを取得して「案Aは成立した」と
誤結論する**。`SKILL.md` 手順1が対象表示を必須にしているのは同じ事故を防ぐためであり、調査コマンドで
それを再現しない。取得できたことの判定には、必ず `headSha`（`get_mr_changed_files` /
`pull_request_read` で得られる値）との一致を使う。

**参照名はプロバイダで異なる**（GitHub: `refs/pull/<n>/head` ／ GitLab:
`refs/merge-requests/<iid>/head`）。GitLabはサーバ設定によってこの参照を取得できないことがあるため、
**片方だけを確かめて「案Aは成立する」と結論づけない**。

**グローバルgit設定を書き換えない。** `gh auth setup-git` は `~/.gitconfig` へ
`credential.https://github.com.helper` を書き込む**永続的な副作用**を持ち、しかもそれは
**受け入れ条件2の検証環境（git到達不可）そのものを到達可能側へ変えてしまう**。確認は
`git -c credential.helper=...` のその場限りのオーバーライドで行い、やむを得ず書き換える場合は
事前にユーザーへ確認したうえで、前後の `git config --global --get-regexp '^credential'` を結果mdへ残し、
復元まで手順に含める。

**あわせて `.git` の扱いを決める材料を集める。** cloneすると `.git` ごと一時領域へ置かれ、
`submission.root` 配下で**コミットメッセージを読めてしまう**。
`.claude/agents/answer-talker-reviewer.md` は「受講者リポジトリのコミットメッセージ・issue・
MRの説明文を読んではいけない」と規定しており、cloneするとこの規約が**定義上の禁止だけ**になる
（正解ソース側は `referenceOnly` の判断材料であって実装者の意図の混入源ではないため、同じ問題は
生じない）。次を確認する。

- clone後に `.git` を除去してよいか。除去するとcloneの利点（後始末の単純さ）が失われないか
- **案Aと案Bで、サブエージェントから見えるものが同じになるか**（同じでないなら、経路によって
  レビュー結果が変わる）

**判断軸**: 成立する条件が「実運用で普通にある状況」を覆えるか。覆えないなら案Aは第一候補に
できない。

### 論点2: 案B（APIでファイル全文を取得）の実現手段

**調べること**: 両プロバイダで共通形へ正規化できるか。

`Provider.sh` に**ファイル内容を取得する関数は現在1つも無い**（関数一覧で確認済み）。

| 確認項目 | 実行するコマンド | 見るもの |
|---|---|---|
| GitHub: 単一ファイル | `gh api "repos/{owner}/{repo}/contents/<path>?ref=<sha>"` | base64か生か・`size`・`content` の有無 |
| GitHub: ツリー一括 | `gh api "repos/{owner}/{repo}/git/trees/<sha>?recursive=1"` | `truncated` フラグ・件数上限 |
| GitLab: 単一ファイル | `glab api "projects/:id/repository/files/<url-encoded path>?ref=<sha>"` | `encoding`・`size`・`content` |
| GitLab: ツリー | `glab api "projects/:id/repository/tree?recursive=true&per_page=100"` | ページング方式 |
| 大きいファイル・バイナリ | 上記を意図的に大きいファイル・バイナリへ適用 | どのサイズから `content` が省略されるか |

**判断軸**: `get_mr_changed_files` で確立した「**キー集合を一致させる**」流儀を踏襲できるか。
できないなら、差を埋めるコストが妥当かを見る。

**あわせて、取得できないファイルがあった場合の縮退方針の候補を洗い出す**
（論点1・2に共通。下記「両案とも成立しない場合」）。

### 論点3: どこまで取得するか

**調べること**: 取得範囲の候補と、それぞれのコスト。

| 候補 | 内容 |
|---|---|
| a | 対応が付いたファイル（`mapping.matched`）だけ |
| b | リポジトリツリー全体 |
| c | 拡張子・サイズ・パスで絞ったツリー |

**issueの案Bの定義と衝突する点を明示しておく。** issue #6 本文の案Bは「**対応が付いたファイル**の
全文をAPIで取得して渡す」＝候補aとして書かれている。しかし候補aでは
**「今回変更していないファイルに責務が置かれている場合を見落とす」という issue #6 の目的そのものを
満たせない**（変更していないファイルは `mapping` に現れないため）。

つまり **issueが定義したフォールバック先そのものが目的未達**であり、そのままでは
受け入れ条件1（受講者のソースを全体として読める）と受け入れ条件2（git到達不可でも
フォールバックで機能する）が**同時に成立しない**。

したがって**案B採用時は候補b/cへの拡張が必須**であり、この調査ではその**拡張コストが許容範囲かを
判定する**。許容できない場合は、受け入れ条件をどう調整するか（issue #6 への差し戻しを含む）を
結果mdへ選択肢として書く。

`.claude/rules/shell-script-style.md`「外部プロセス起動のコスト」（git bashでは1回約95ms）が
効くため、**ファイル数に比例して外部コマンドを起動する形にしない**設計が要る点も見る。

**判断軸**: 受け入れ条件1を満たす最小の範囲と、そのAPI呼び出し回数。

### 論点4: `answer-talker-map.sh` の対応付け範囲を広げるか

**調べること**: 広げた場合に何が変わるか。**案A採用時・案B採用時の両方**について洗い出す
（方式の決定を待たない。下記「調査の進め方」）。

現在は「受講者の**変更**ファイル」対「正解の全ファイル」。これを「受講者の**全**ファイル」対
「正解の全ファイル」へ広げると、**`submissionOnly` の意味が変わる**。

- 今: 「今回のMRで追加したファイル」
- 広げた後: 「正解に無いファイル」（受講者が前から持っているものを含む）

サブエージェント定義の手順1は `mapping.referenceOnly` を起点にしており、
`submissionOnly` の意味が変わると観点表の読み方にも影響する。

**判断軸**: サブエージェントが「別解かどうか」を判断するのに、どちらの意味が役立つか。

### 論点5: ネタバレ検査の禁止語の材料（**本変更に伴う必須の追随**）

**調べること**: 材料を広げないと何が壊れるか、広げると何が変わるか。
**案A・案Bの両方について洗い出す。**

**これは任意の改善ではない。** 現在の禁止語は
`正解の識別子 − 受講者diffに現れる語 − 除外語 − 3文字以下` で、差し引く材料は
`answer-talker-spoiler-check.sh` の `main` が `.files[] | .patch, .path, .oldPath` から作っている。
つまり issue #6 の目的である「**hunkに現れない受講者ファイルに基づく指摘**」は、その識別子が
diffに現れないため差し引かれず、正解側に同名の識別子があれば**必ず禁止語に一致して drop される**。
**受講者ソース全体を渡した瞬間、新しく見えるようになったものについての指摘だけが選択的に落ちる**
という壊れ方をする。

したがって、次の**両方**を必ず結果mdへ出す。

- (a) 材料を広げる場合: 何が変わるか（下記の判断軸）
- (b) 広げず現状維持とする場合: **受け入れ条件1をどう満たすか**（満たせないならその事実を明示する）

| 確認項目 | 見るもの |
|---|---|
| hunk外ファイルの識別子を含む指摘が drop されるか | `--diff` を渡した状態で実行し、`dropped` と `drops[].words` を見る（**実測する。推測で書かない**） |
| 材料を広げたときの禁止語の増減 | 広げる前後の禁止語の件数と、禁止語から消えた語の内訳 |
| 見逃しが増えないか | 「正解にも受講者ソースにも同じ識別子がある」ケースを作って確かめる |

**DDR 0061「誤検知の側へ倒す」との関係を詰める。** 「正解にも受講者ソースにも同じ識別子がある」
とき、その語は禁止語から外れる——それが「受講者が既に書いているのだから転記ではない」と言えるのか、
「たまたま一致しただけで、正解由来の転記を見逃す」のかを判断する。

**経路依存**: 受講者ソースとして何が手に入るかは方式で異なるため、依存させると**同じMRでも経路に
よって投稿される指摘が変わる**。**案B側は論点3の結論を待たず、候補a/b/cそれぞれについて出す**
（論点3が範囲を1つに絞るのはフェーズ3のため、待つと着手条件が閉じない）。

| 案 | 禁止語の材料になる受講者側の語 |
|---|---|
| 案A | 受講者リポジトリの全ファイル |
| 案B-a（`mapping.matched` のみ） | 対応が付いたファイルのみ。**hunk外の未対応ファイルは材料に入らず、上記の drop が残る** |
| 案B-b（ツリー全体） | 案Aと同じ |
| 案B-c（絞ったツリー） | 絞り込み条件次第。**除外したファイルの識別子は材料に入らない** |

**判断軸**: (1) 見逃しが増えないと言い切れるか。(2) 経路によって結果が変わらないか。
**どちらかが満たせない場合も「現状維持」で終わらせず**、受け入れ条件1を満たすための代替
（drop件数の可視化、どの経路で実行したかを報告へ明記する等）を選択肢として出す。

### 論点6: 検証環境の再構築（**論点1・2の前提**）

**調べること**: `spec/answer-talker.md` の「検証の再現手順の要点」だけで演習環境を作り直せるか。

issue #1 の演習用プロジェクトは flow-id 5-1 で削除済みで、セットアップスクリプトも残していない
（issue #1 の反映時に「題材はこのリポジトリの成果物ではなく、再現に必要な情報はspecで足りる」と
判断したため）。**この再構築は、その判断が正しかったかの検証を兼ねる。**

確認する項目:

- **GitLab側**: specの手順（Commits APIでブランチ・コミットを作る）で再構築できるか。
- **GitHub側**: 受け入れ条件2は「GitHub・GitLab**両方**で実機確認」を求めるが、
  **specの再現手順はGitLab前提で書かれており、GitHub側に受講者PRを用意する手順が無い**。
  どう用意するかを決める。**既定は「専用の使い捨てリポジトリを作る」**とし、
  **このリポジトリのPRを流用する案は原則採らない**。openなのは本作業のPR #7 であり、
  `answer-talker` を実行すると**レビュー中の自分のPRへ演習レビューが投稿される**
  （`SKILL.md` 手順9は投稿まで行う）。これは `SKILL.md`「してはいけないこと」の
  『`--repo` を省略したまま、別リポジトリのつもりで実行すること』に正面から触れる。
  加えて、このリポジトリは規模（`.claude/` 配下全体）が演習用の極小CLIと桁違いで、
  論点3（取得範囲）・論点5（禁止語）の判定材料としての代表性も無い。
  やむを得ず流用する場合は**手順5で「報告のみ」を選び、投稿しない**ことを条件とする。
- **17パターンの内訳を復元できるか。** 受け入れ条件は「issue #1 の17パターン相当の検証を
  やり直す」ことを求めるが、**specに書かれているのは5軸とその方針だけで、17パターンの組み合わせは
  記載が無い**（`reports/` とともに削除済み）。5軸から復元できるか確かめ、
  **できなければ今回作ったパターン表をspecへ残す**（フェーズ4の反映候補になる）。

**判断軸**: specの記述だけで再構築できたか。できなければ、何が足りなかったか。

### 両案とも成立しない場合（論点1・2に共通）

**どちらも使えない状況を想定する。** 例: 非公開リポジトリで資格情報ヘルパが無く（案A不可）、
かつ対象ファイルがAPIのサイズ上限超過・バイナリ（案B不可）。

このとき何をするかで、サブエージェントへ渡す入力仕様が変わる。候補を洗い出す。

- 従来どおりhunkだけで続行し、**その事実を報告する**（`truncatedFiles` / `capped` と同じ扱い）
- 中止する
- 部分的に取得できたファイルだけで続行し、取得できなかったファイルを報告する

**判断軸**: それぞれで受け入れ条件1をどこまで満たせるか。

## 調査の進め方

- **論点6 → 論点1 → 論点2 → 論点3 の順に進める。** 論点1・2は実機確認が要点であり、
  **確認には演習環境（GitHub側・GitLab側の両方）が要る**ため、論点6が前提になる。
  案Aの成否で論点3の重みが変わるため、1→2→3の順序にも意味がある。
- **論点4・5は方式の決定を待たない。** 「案A採用時／案B採用時の両方について影響を洗い出す」
  形で進める。フェーズ2では方式を決めない（下記スコープ外）ため、片方の答えだけを出す形にすると

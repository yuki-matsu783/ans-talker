# 【調査】受講者ソースの受け渡し方式

- issue: [#6](https://github.com/yuki-matsu783/ans-talker/issues/6) / PR: [#7](https://github.com/yuki-matsu783/ans-talker/pull/7)
- 全体作業計画: `plans/bubbly-exploring-biscuit.md`（flow-id 1-5で承認）
- 対象フェーズ: フェーズ2〈調査〉（flow-id 2-1〜2-10）

## 目的

**受講者のソースコード全体をサブエージェントへどう渡すかを決められる状態にする。**
issue本文には案A・案Bを候補として書いたが、**どちらが成立するかは実機で未確認**であり、
このままでは設計（フェーズ3）に入れない。

**この計画には結果を書かない。** 調査結果は
`reports/日付_bubbly-exploring-biscuit_<内容>.md`（正文）と同名の `.html` へ記録する
（`.claude/skills/issue-mr-flow/SKILL.md`「計画と実施結果の分離」）。

## 前提（issue #1 から引き継ぐ確定事項）

| 前提 | 出どころ |
|---|---|
| 対象リポジトリの切り替えは `use_target_repo`（`GH_REPO`/`GITLAB_REPO` の環境変数）で行う | DDR相当。`spec/answer-talker.md` |
| 差分取得の返却は GitHub / GitLab で**キー集合を完全に一致**させてある | `spec/answer-talker.md`「差分の取得」 |
| ネタバレ検査は**誤検知の側へ倒す**。識別子は分割しない | DDR 0061 |
| 正解ソースの**ローカルパスはcloneしない** | DDR 0060 |
| 演習の題材はこのリポジトリに残さない | issue #1 flow-id 1-5 / 2-9 |

## 調査する論点

### 論点1: 案A（MRのheadを shallow clone）が成立する条件

**調べること**: どの条件なら成立し、どの条件で失敗するか。

issue #1 の検証時、ローカルGitLab（`localhost:8929`）へ `git` で到達できなかった。

- HTTP clone → `fatal: Cannot prompt because user interactivity has been disabled.`
- SSH（ポート2224） → `Permission denied (publickey)`。`glab api user/keys` は空

**この失敗が「この環境固有」なのか「認証を要するリポジトリ一般」なのかを切り分ける。**
とくに次を確認する。

- **認証済みの `gh`/`glab` が持つ資格情報を、`git` が使えるか。** `gh auth setup-git` に相当する
  資格情報ヘルパの設定が入っていれば、HTTP cloneが通る可能性がある
- GitHubの**公開**リポジトリ（認証不要）なら成立するか
- 成立する場合、`--depth 1 --single-branch` で**MRのheadブランチ**を取れるか
  （`refs/pull/<n>/head` 等、MR番号からブランチ名を得る経路も含む）

**判断軸**: 成立する条件が「実運用で普通にある状況」を覆えるか。覆えないなら案Aは第一候補に
できない。

### 論点2: 案B（APIでファイル全文を取得）の実現手段

**調べること**: 両プロバイダで共通形へ正規化できるか。

`Provider.sh` に**ファイル内容を取得する関数は現在1つも無い**（関数一覧で確認済み）。

- GitHub: `repos/{owner}/{repo}/contents/{path}?ref=<sha>`、ツリー一括は
  `repos/{owner}/{repo}/git/trees/{sha}?recursive=1`
- GitLab: `projects/:id/repository/files/:path?ref=<sha>`、ツリーは
  `projects/:id/repository/tree?recursive=true`

確認する項目: 返却形（base64か生か）・ページング・**サイズ上限**・バイナリの扱い・
1リクエストで何ファイル取れるか。

**判断軸**: `get_mr_changed_files` で確立した「**キー集合を一致させる**」流儀を踏襲できるか。
できないなら、差を埋めるコストが妥当かを見る。

### 論点3: どこまで取得するか

**調べること**: 取得範囲の候補と、それぞれのコスト。

「全ファイル」と言っても受講者リポジトリの規模は未知である。候補は次の3つ。

| 候補 | 内容 |
|---|---|
| a | 対応が付いたファイル（`mapping.matched`）だけ |
| b | リポジトリツリー全体 |
| c | 拡張子・サイズ・パスで絞ったツリー |

**案Aなら丸ごと手に入るので論点にならないが、案Bでは取得範囲がそのままAPI呼び出し回数になる。**
`.claude/rules/shell-script-style.md`「外部プロセス起動のコスト」（git bashでは1回約95ms）も
効いてくるため、**ファイル数に比例して外部コマンドを起動する形にしない**設計が要る。

**判断軸**: 「変更していないファイルに責務が置かれている場合を見落とさない」という
issue #6 の目的を満たす最小の範囲。**aでは目的を満たせない**（変更していないファイルが入らない）。

### 論点4: `answer-talker-map.sh` の対応付け範囲を広げるか

**調べること**: 広げた場合に何が変わるか。

現在は「受講者の**変更**ファイル」対「正解の全ファイル」。これを「受講者の**全**ファイル」対
「正解の全ファイル」へ広げると、**`submissionOnly` の意味が変わる**。

- 今: 「今回のMRで追加したファイル」
- 広げた後: 「正解に無いファイル」（受講者が前から持っているものを含む）

サブエージェント定義の手順1は `mapping.referenceOnly` を起点にしており、
`submissionOnly` の意味が変わると観点表の読み方にも影響する。

**判断軸**: サブエージェントが「別解かどうか」を判断するのに、どちらの意味が役立つか。

### 論点5: ネタバレ検査の禁止語の作り方を見直すか

**調べること**: 「受講者diffの語」を「受講者ソース全体の語」へ広げた場合の影響。

現在の禁止語は `正解の識別子 − 受講者diffに現れる語 − 除外語 − 3文字以下`。
差し引く集合が大きくなるので、**禁止語は減り、誤検知も減る**方向に働くはずである。

**ただしDDR 0061 は「誤検知の側へ倒す」と決めている。** 減るのが誤検知だけなら前提と矛盾しないが、
**見逃しが増えるなら話が別**である。具体的には「正解にも受講者ソースにも同じ識別子がある」場合、
その語は禁止語から外れる——それが「受講者が既に書いているのだから転記ではない」と言えるのか、
「たまたま一致しただけで、正解由来の転記を見逃す」のかを詰める。

**判断軸**: 見逃しが増えないと言い切れるか。言い切れないなら現状維持とし、その理由を残す。

### 論点6: 検証環境の再構築

**調べること**: `spec/answer-talker.md` の「検証の再現手順の要点」だけで演習用プロジェクトを
作り直せるか。

issue #1 の演習用プロジェクトは flow-id 5-1 で削除済みで、セットアップスクリプトも残していない
（N3の判断）。**この再構築は、再現手順が実際に機能するかの検証を兼ねる。**
足りない情報があれば、それ自体がフェーズ4でspecへ反映すべき内容になる。

**判断軸**: specの記述だけで再構築できたか。できなければ、何が足りなかったか。

## 調査の進め方

- **論点1→2→3 の順に進める。** 案Aの成否で論点3の重みが変わるため、順序に意味がある。
- 論点4・5は方式が決まってから詰める（渡すものが決まらないと影響を評価できない）。
- 論点6は他と独立なので、いつ着手してもよい。
- **実機で確かめられることは実機で確かめる。** issue #1 では「調査結果に誤りがあり、設計段階で
  訂正する」ことが実際に起きた（`gh`/`glab` がcwdからリポジトリを解決する件）。推測で書かない。

## この計画で決めないこと（スコープ外）

- **方式の決定そのもの**。調査で材料を揃え、決定はフェーズ3の `【設計】` で行う。
- **実装**。フェーズ3。
- spec/DDRの執筆。フェーズ4（flow-id 4-1で対象を洗い出す）。
- `adversarial-review` 側の変更。今回の受け入れ条件に含まれない。
- **issue #5**（`apply-mr-workflow-to-project` の `type` 欠落）。別issueとして起票済み。

## 検証（この調査が完了したと言える条件）

1. 論点1・2について、**実機で試した結果**（コマンドと出力）が結果mdに残っている。
   推測のみの記述が無い。
2. 受け渡し方式について、案A・案Bのどちらを第一候補とするか、フォールバックをどう設計するかの
   **材料が揃っている**（決定はフェーズ3）。
3. 論点3〜5について、選択肢とそれぞれの判断軸が整理されている。
4. 論点6について、**実際に再構築を試した**結果が残っている（specの記述で足りたか）。
5. 未決定のまま残す事項があれば、**何が未決定かが明示**されている。

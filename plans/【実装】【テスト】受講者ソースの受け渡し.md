## 目的

**設計結果のとおりに実装し、issue #6 の受け入れ条件7項目を満たすところまで持っていく。**

**この計画には結果を書かない。** 実装・検証の結果は
`reports/日付_bubbly-exploring-biscuit_<内容>.md` へ記録する。

## 併記する理由

`【実装】` と `【テスト】` を1ファイルにまとめる。**設計で決着済みのため、実装とテストの間に
人間の合意を挟む必要が無い**ためである（`issue-mr-flow` SKILL.md「種別を複数併記する場合」の
「分けても合意の単位が変わらず、記述が重複するだけの場合」に該当）。

ただし**17パターン相当の実機検証は工数が大きく、途中で分割したくなる可能性がある**。その場合は
この計画を分割してよい（既存の合意内容は失わない）。

### 実装で落としやすい点（設計結果から転記。実装時のチェックリスト）

- [ ] 段2の対象パスを **diffから作らない**（`get_repo_tree` を使う。落とすと却下案B-aと同じ状態へ

- [ ] `resolve` は **`tmpdir` を返す**（返さないと `cleanup` へ渡す値が無い）
- [ ] 展開先は **`$tmpdir/source`**、マーカーは `$tmpdir` 直下（`root == tmpdir` にしない）
- [ ] `resolve` は**失敗時に自分が作った一時ディレクトリを削除してから非0で返す**
- [ ] **段3は終了コード0**（`stage:3, degraded:true, root:null`）
- [ ] `submission` へ **`files` と `truncated` を載せる**（切り詰めが伝わらないと「全部見た」と誤認）
- [ ] SKILL.md **手順7**へ `--submission-root` を渡す（落とすと拡張が無言で効かない）
- [ ] **除外は展開直後に一度だけ**行い、一覧・読み取り・`mapping`・禁止語のすべてに及ぼす

- [ ] **URLエンコードは関数側**（GitLabの files API。落とすと段2がGitLabでのみ全ファイル404）
- [ ] 読み替え表は**既存行を「手順4・7」へ狭めてから**手順3bの行を足す

## テストする内容

### A. 単体テスト（純粋ロジック）

`.claude/scripts/test/` に置き、`passed=N failures=N` を出力して失敗時に終了コード1
（`.claude/rules/shell-script-style.md`「テスト」）。**外部コマンド呼び出しを伴わない範囲**を対象と
する（API呼び出しはBで見る）。

### B. 実機検証（17パターン相当）

**検証環境は復元済み**（flow-id 2-6）。

| | 場所 | 内容 |
|---|---|---|
| GitLab | `root/answer-talker-verify` / `root/answer-talker-answer` | 9MR・10ブランチ（p1〜p11） |
| GitHub | `yuki-matsu783/test-repo` | PR #1（`p2b-single-file`）。**題材の投入は Contents API で行う** |

**GitHub側は現在1パターンしか無い。** GitLabから題材を吸い出して投入する（flow-id 2-6 と同じ手順）。
**リポジトリは新規作成しない**（ユーザーが用意した `test-repo` を使う）。

### C. 受け入れ条件に対応する検証

| 条件 | 検証方法 |
|---|---|
| 1. 受講者のソースを全体として読める | **hunk外ファイルにのみ存在する責務**について指摘が出るかを、**意図的に作ったパターン**で確かめる。**「出る」だけでなく「届く」まで見る**（hunk外の指摘はサマリへ回るため、`summarized` の件数と本文を確認する） |
| 2. 縮退が両プロバイダで機能する | **段1をわざと失敗させ**、段1→段2、段2→段3の遷移を両プロバイダで確認する |
| 3. 定義と実態が一致 | 起動時の入力JSONと定義の記述を突き合わせる。**`degraded: true` の場合も確認する** |
| 4・5. 判断がspecに記録されている | フェーズ4 |
| 6. spec更新・DDR | フェーズ4 |
| 7. 17パターン相当 | **②別解・⑤ほぼ正解で分割単位の指摘が出ないこと**を再確認（**最大の回帰リスク**） |

### D. 設計で未確認のまま残した項目

- **GitHub非公開リポジトリでのアーカイブ取得**（`test-repo` は公開のため未実測）。
  **非公開リポジトリを新規に作らない**——`test-repo` を一時的に非公開へ切り替えてよいかは
  **ユーザーに確認する**。確認が取れなければ**未確認として結果mdに残す**。
- **サイズが取得できない環境**（権限の弱いGitLab等）での挙動。
- **上限値（100MB・50件・500件・60秒）の妥当性**。

## 検証（この作業が完了したと言える条件）

**「書いてあるか」ではなく「動くか・決まっているか」を検出できる形にする**（`【設計】` の
レビューで、一般的な語を数えるだけの検証コマンドは常に成功すると指摘されたため）。

```bash
# 1. 全単体テストが failures=0（NG=0 を確認する）
ng=0
for t in .claude/scripts/test/test_*.sh; do
  out="$(bash "$t" 2>&1 | tail -1)"
  printf '%s %s\n' "${t##*/}" "$out"
  case "$out" in *'failures=0') ;; *) ng=$((ng + 1)) ;; esac
done
printf 'NG=%s\n' "$ng"

# 2. 新規スクリプトの単体テストが実在し、実際に検査していること（0件やスケルトンでないこと）
bash .claude/scripts/test/test_answer_talker_submission.sh | tail -1   # passed が二桁以上

# 3. 構文チェック（新規・変更したすべての .sh）
for f in .claude/scripts/src/answer-talker-submission.sh \
         .claude/scripts/src/answer-talker-map.sh \
         .claude/scripts/src/answer-talker-spoiler-check.sh \
         .claude/scripts/src/vcs/Provider.sh; do
  bash -n "$f" && printf 'OK %s\n' "${f##*/}"
done

# 4. 3段すべてが実際に走ったことを、実行結果のJSONで確認する（推測で書かない）
#    段1: 通常実行 / 段2: --max-size-kb 0 で段1を落とす / 段3: --max-fetch-files 0 で段2も落とす
#    → それぞれの stage / degraded / reason を結果mdへ貼る

# 5. 縮退時に mapping と禁止語が従来の意味へ戻ることを、出力のキーで確認する
#    mapping の "scope" と、spoiler-check の "materialScope" が diff になること
```

**内容の最低要件**:

1. **3段すべてを実際に走らせた出力**が結果mdにある（段2・段3は人工的に落として確認する）。
2. **hunk外ファイルに基づく指摘が出て、かつ届いた**ことを、意図的に作ったパターンで確認した
   記録がある（`summarized` の件数と本文を含む）。
3. **②別解・⑤ほぼ正解で分割単位の指摘が出ない**ことを再確認した記録がある。
4. 上記Dの3項目について、**確かめたか／確かめられなかったかが区別して書かれている**。
5. 全単体テストが `NG=0`。

# 【設計】answer-talker スキルの構成とインターフェース

- issue: [#1](https://github.com/yuki-matsu783/ans-talker/issues/1) / PR: [#2](https://github.com/yuki-matsu783/ans-talker/pull/2)
- 全体作業計画: `plans/bubbly-exploring-biscuit.md`
- 前提となる調査結果: `reports/20260820_bubbly-exploring-biscuit_answer-talker設計調査.md`（flow-id 2-9で合意）
- 対象フェーズ: フェーズ3〈作業〉の前半（flow-id 3-1〜3-10の1セット目）

## 目的

**実装に入る前に、決めるべきことを決め切る。** 調査で方針は定まったが、関数名・引数・返却の形・
検査アルゴリズムの詳細など、**書き始めてから変えると6ファイルに波及する事項**が未確定のまま
残っている。ここで合意を取ってから `【実装】【テスト】` へ進む。

**この計画は「何を決めるか」と「何を基準に決めるか」を定めるものであり、決定そのもの（結論）は
書かない。** 設計の結果は flow-id 3-6 で
`reports/日付_bubbly-exploring-biscuit_answer-talker設計.md` へ記録する
（`.claude/skills/issue-mr-flow/SKILL.md`「計画と実施結果の分離」）。

## 前提（合意済みの制約）

| 制約 | 合意した場所 |
|---|---|
| **ネタバレ検査は誤検知の側へ倒す**（正当な指摘を落としてでも、転記の見逃しを避ける） | flow-id 3-4 |
| **検証環境は、いろいろなパターンを試せる構成にする** | flow-id 3-4 |
| 実例確認はローカルGitLabの演習用プロジェクトで、実投稿まで行う | flow-id 2-9 |
| 成果物は `.claude/` 配下に収める／issueは分割しない | flow-id 1-5 |

## なぜ `【実装】【テスト】` と分けるか

分けるか併記するかの基準は「**人間の合意を1回で取るか、フェーズごとに分けて取るか**」である
（同SKILL.md「種別を複数併記する場合／分ける場合」）。本タスクは分ける側に該当する。

- 追加するファイルが6種類あり、**インターフェースが決まらないと相互に噛み合わない**。実装後に
  「関数の返却の形が違う」となると、スクリプト・SKILL.md・サブエージェント定義・テストの
  4箇所を同時に直すことになる。
- **ネタバレ検査の厳しさ（どこまで落とすか）は、演習の運用方針そのもの**であり、実装の都合とは
  別の軸で人間に判断してもらう必要がある。実装コードのレビューに混ぜると評価軸が混ざる。

## 決めること

各項目は「**決める内容**」「**判断軸**」の2点で示す。結論はここに書かない。

### D1. 追加するファイルの構成と責務の境界

- 決める内容: 調査結果が挙げた6種類の成果物について、**どのファイルが何を持つか**の線引き。
  とくに「SKILL.md（手順）」「サブエージェント定義（観点と出力規約）」「スクリプト（機械的処理）」の
  責務配分。
- 判断軸:
  - `adversarial-review` の責務配分（観点は `REVIEW-POINTS.md`、対象の判断は呼び出し元、
    投稿は呼び出し元、findingsの生成のみサブエージェント）から**離れる箇所には理由を書けるか**。
  - **機械的に判定できるものをAIの判断に委ねていないか**（逆に、判定できないものを機械へ
    押し込んでいないか）。調査結果の論点4・5がこの線引きの実例。

### D2. `Provider.sh` へ追加する関数

- 決める内容: 関数名、引数、返却JSONの形、GitHub/GitLabそれぞれの実装、エラー時の挙動。
  **調査で未決定として残した3件を含む**（返却をstdoutにするか出力ファイルパスを引数で受けるか／
  関数名が既存の `get_mr_diff_url` と紛らわしい件／大きなdiffの扱い）。
- 判断軸:
  - **既存の `Provider.sh` の規約（JSONをstdoutへ、`require_vcs_cli` ガード、
    プロバイダ接頭辞）から外れないこと。** 外す場合は理由を書く。
  - **サイズが可変・無制限になりうる値をコマンド置換や `--argjson` で渡さないこと**
    （`.claude/rules/shell-script-style.md`）。
  - 取得できなかった差分（GitHubの `patch` 省略・3000ファイル上限、GitLabの
    `too_large`/`collapsed`）を**無言で切り捨てず、検知して報告する形**になっていること。

### D3. 正解ソース取得スクリプトのインターフェース

- 決める内容: 引数、返却JSON、一時ディレクトリの後始末の方式（**調査の未決定事項#4**:
  呼び出し側の手順に委ねるか `--cleanup` サブコマンドにするか）、受け付ける正解の場所の形態。
- 判断軸:
  - **後始末が漏れたときに何が残るか。** AIエージェントが手順を飛ばしうる前提で、
    漏れにくい方を選ぶ。
  - **ローカルパス指定時に、正解ディレクトリを削除も変更もしない**ことが構造的に保証されるか。
  - 失敗時の終了コードが呼び出し側から判定できるか（調査で踏んだ「パイプで失敗を潰す」問題）。

### D4. サブエージェント `answer-talker-reviewer` の定義

- 決める内容: 渡す入力の形、読み取りを許可する範囲、レビュー観点の記述、findings JSONの
  スキーマ（`adversarial-reviewer` からの差分）、**正解を転記しないための出力規約**。
- 判断軸:
  - **「別解を潰さない」がレビュー観点として書き下せているか**（issue「期待する動作」4の最後）。
    「正解と違う＝指摘」になっていないか。
  - 指摘が「何が問題か」「なぜそうすべきか（設計原則の言葉で）」「どの方向へ直すか」の
    3点で書かれる形に**規約として**なっているか（issue「期待する動作」5）。
  - **正解側にしかない構成要素を、「正解ではこうなっている」ではなく「この処理はどういう単位で
    分けられるか」の形で指摘させる**書き方になっているか。
  - `adversarial-reviewer` の「渡されたもの以外を探しに行かない」という規約を、
    **正解を読ませる必要があるこのエージェント向けにどう書き換えるか**。

### D5. ネタバレ検査のアルゴリズム

- 決める内容: 禁止語の抽出方法、除外する語の決め方（**調査の未決定事項#5**: 一般語・言語
  キーワードの除外リストをどこに持つか）、判定の単位、混入時の挙動、純粋関数への切り出し方。
- 判断軸:
  - **誤検知の側へ倒す**（flow-id 3-4で合意）。正当な指摘を落としてでも、転記の見逃しを避ける。
    設計はこの向きを前提とし、**逆へ倒す選択肢は検討しない**。
    - この向きを選ぶと、**指摘が落ちすぎて実質何も出なくなる**という失敗の仕方をする。
      落とした件数と落とした理由（どの語に反応したか）を**必ず可視化**し、閾値を後から調整できる
      形にする（可視化の先はD6の手順で決める）。
    - **落とした結果0件になったときの扱い**（投稿しない／その旨を報告する）を決める。
  - 単語境界・マルチバイト・大文字小文字の扱いが決まっているか。
  - **外部コマンドをループ内で起動しない形**になっているか
    （`.claude/rules/shell-script-style.md`「外部プロセス起動のコスト」）。
  - **検査を通ったことが、どこで確認できるか**（落とした件数の報告先）。

### D6. SKILL.md の手順構成

- 決める内容: 手順の並び、起動時の引数の解釈、承認を取る位置、`gh`/`glab` 不在時のMCP読み替え、
  「してはいけないこと」。
- 判断軸:
  - **承認が投稿の前に1回だけ**であること（`adversarial-review` と同じ承認モデル）。
  - **後始末の手順が、失敗経路でも実行される形**で書かれているか。
  - 手順から観点の中身が漏れ出していないか（観点はサブエージェント定義側）。

### D7. 検証環境（演習用プロジェクト）の構成

**flow-id 3-4で「いろいろなパターンを試せるように」と合意した。** 1本の正常系だけを通す構成に
せず、下記の軸を組み合わせて確認できる形に設計する。

- 決める内容: ローカルGitLabに作るプロジェクトの構成（名前・初期状態・ブランチ／MRの数）、
  正解ソースの置き方、各パターンの**期待する結果**、後片付けの方針、**検証を再実行できる形**。
- **試せるようにする軸**（この一覧自体もD7で確定させる。ここでは網羅すべき観点を示す）:

  | 軸 | 試したいパターン | 何を確かめるか |
  |---|---|---|
  | 受講者の実装 | ① 1ファイルに詰め込み（分割不足） | 正解にしかない分割単位を「どういう単位で分けられるか」の形で指摘できるか（**受け入れ条件の中核**） |
  | | ② 正解と違う分割だが方針として妥当（別解） | **指摘しない**こと（別解を潰さない） |
  | | ③ 正解が避けている作り（重複・密結合・ハードコード） | 指摘できるか |
  | | ④ 正解に無い余分な抽象化 | 過剰な指摘にならないか |
  | | ⑤ ほぼ正解と同じ | **指摘が0件になる**こと（水増ししない） |
  | 正解ソースの形態 | ⑥ URL（要clone） ／ ⑦ ローカルパス（gitリポジトリ） ／ ⑧ ローカルパス（**素のディレクトリ**） | D3の3形態。⑧はcloneできないため「cloneしない」設計が効いているか |
  | diffの内容 | ⑨ ファイルの削除 ／ ⑩ **リネーム** ／ ⑪ 新規追加のみ | `status` の語彙変換と `oldPath` の扱い。**調査で未確認だったリネームをここで潰す** |
  | ネタバレ検査 | ⑫ 正解のコード片を含む finding を意図的に混ぜる | 投稿されないこと・落とした件数が可視化されること（D5） |
  | | ⑬ 一般語のみを含む正当な finding | **落とされない**こと（誤検知に倒す方針の副作用の確認） |
  | 投稿 | ⑭ GitLabのMRへ実投稿 | `gitlab_add_mr_inline_comments` が動くこと（調査で未確認） |
  | | ⑮ 指摘0件のとき | 空のレビューを投稿しないこと |

  **全パターンを1つのMRで賄おうとしない。** ①〜⑤は受講者MRを複数用意して分ける
  （どのMRがどのパターンかを対応付けられるようにする）。

- 判断軸:
  - **受け入れ条件「正解側にしか存在しない分割単位について実例で確認」を満たせる題材か**
    （＝正解にしかない分割単位が確実に存在するか）。パターン①がこれに当たる。
  - **「指摘しないことを確かめるパターン」（②⑤⑬⑮）が含まれているか。** 指摘が出ることだけを
    確かめる検証は、過剰に指摘するスキルを合格させてしまう。
  - 題材が**このリポジトリに残らない**こと（plugin配布物にサンプルアプリを混ぜない）。
  - **検証をやり直せるか。** 1回きりの手作業ではなく、環境構築から結果確認までを手順
    （できればスクリプト）として書けるか。パターンが増えるほど手作業では再現できなくなる。
  - 題材のコード自体は**最小**にする（言語・フレームワークの知識を要する題材にしない）。
    確かめたいのは分割単位の指摘であって、題材の複雑さではない。

## この計画で決めないこと（スコープ外）

- **実装コードそのもの**。ファイルの中身を書くのは `【実装】【テスト】` の担当。
- **spec/DDRに何を書くか**。フェーズ4の flow-id 4-1 で洗い出す（D2・D3・D5で設計判断が生じた
  事実は結果に記録するが、DDRの起票はしない）。
- **`adversarial-review` 側の変更**。共通化のために既存スキルへ手を入れることは、
  今回の受け入れ条件に含まれない。必要性が見つかった場合は別issueとして提案する。
- **演習用プロジェクトの構築の実施**。構成を決めるまでが本計画で、実際に作るのは
  `【実装】【テスト】` の検証手順。

## 検証（設計完了の判定）

設計が完了したと言えるのは、次がすべて満たされたときとする。

1. D1〜D7それぞれについて、「決める内容」に挙げた項目が
   `reports/日付_bubbly-exploring-biscuit_answer-talker設計.md` に書かれている。
2. **調査結果に残っていた未決定事項4件が、すべて決定済みになっている**
   （diff関数の返却形・関数名、正解ソースの後始末の置き場所、一般語の除外リストの持ち方）。
   決めた理由が「判断軸」に照らして説明されている。
3. 追加する各ファイルについて、**中身を書き始められる粒度**の記述がある
   （関数のシグネチャ、スクリプトの引数、SKILL.mdの見出し一覧、findings JSONのキー定義）。
4. D5について、**単体テストのケース一覧**（正常系・境界値・誤検知させたくない例）が列挙されている。
5. D7について、**上表の各パターンに「どう作るか」と「期待する結果」が対応付けられている**。
   とくに「指摘しないことを確かめるパターン」（②⑤⑬⑮）が落ちていないこと。
6. 新たに生じた未決定事項があれば、**未決定として明示的に列挙**されている。

なお、設計の妥当性そのものは flow-id 3-8（人間のレビュー）で確認する。上記1〜5は
「レビューできる状態になっているか」の判定である。

# 【設計】受講者ソースの受け渡し

- 対象フェーズ: フェーズ3〈作業〉のうち **`【設計】` のみ**（`【実装】【テスト】` は別計画）

**この計画には結果を書かない。** 設計の結果（何をどう決めたか）は
`reports/日付_bubbly-exploring-biscuit_<内容>.md` へ記録する。

## 決めること0: issue #6 の受け入れ条件7項目の割り当て

**7条件それぞれについて〈この計画で決める／後段のどの計画へ送る〉を確定させる。**
とくに条件2は、**本設計が issue本文の前提を反転させる**ため読み替えが要る。

| # | 受け入れ条件（要約） | 割り当て |
|---|---|---|
| 1 | 受講者のソースを**全体として**読める | 本計画（決めること1・4）→ 検証は `【テスト】` |
| 2 | **`git` 到達不可でもフォールバックが機能し、両プロバイダで実機確認** | **本計画で読み替えを決める**（下記） |
| 3 | エージェント定義の「読んでよいもの」が実態と一致 | 本計画（決めること3） |
| 4 | `mapping` の範囲の判断がspecに記録されている | 本計画で判断 → 記録はフェーズ4 |
| 5 | ネタバレ検査の禁止語の判断が理由とともに記録されている | 同上 |
| 6 | spec更新・必要ならDDR追加 | フェーズ4（本計画ではDDR候補の洗い出しまで） |
| 7 | **17パターン相当の検証をやり直す** | `【テスト】` |

**条件2の読み替え**: issue本文は「案Aを第一候補とし、到達できない場合に案Bへフォールバックする」
という前提で書かれている。本設計はこれを**反転**させる（案B-dが主経路で、gitを使わない）ため、
条件2をそのまま読むと**主経路に「git到達不可」という条件が効かなくなる**。

読み替え案（これを合意事項として決める）:

> **段1（アーカイブ取得）が失敗した場合の縮退が、GitHub・GitLab両方で実機確認されている。**

この読み替えを採るなら、**「段1をわざと失敗させる手段」を `【テスト】` の対象として明示的に送る**
（調査で確認した「到達不可の人工的再現」と同じ考え方）。

## 決めること1: 受け渡し方式（**案B-d を提案する**）

調査で案A・案B-dのどちらも成立したため、**選択の問題**になった。**案B-d（アーカイブ一括取得）を
主経路とする**案を提案し、合意を取る。**決定そのものは結果mdへ記録する。**

| | 案B-d（提案） | 案A |
|---|---|---|
| 呼び出し回数 | **1回**（ファイル数非依存） | 1回 |
| 実測 | 1122ms（GitHub）/ 2044ms（GitLab） | 同程度 |
| `.git` | **含まない** | **同梱。除去が必須** |
| 認証 | **`gh`/`glab` の認証をそのまま使う** | gitへの資格情報供給が別途要る（`GIT_ASKPASS`） |
| 追加の依存 | `tar`（展開時に `--force-local`） | なし |

**案B-dを推す理由**は、`.git` の除去と資格情報供給という**2つの追加作業が要らない**こと。
とくに `.git` は、サブエージェント定義の「コミットメッセージを読んではいけない」規約を
**構造的に守れる**かどうかの差になる（案Aでは除去を忘れた時点で規約が建前になる）。

**却下する案**:

- **案B-a（`matched` のみ）**: issue本文が案Bとして定義していたが、**目的未達**
  （変更していないファイルが入らない）。
- **案B-b/c（ファイル単位API）**: ファイル数に比例して 672ms〜1027ms かかる。50ファイルで
  34〜51秒。
- **案Aを主経路にする**: 上記2つの追加作業のぶん、失敗経路が増える。

## 決めること2: 縮退（フォールバック）— **決めること3より先に閉じる**

**この節を先に決めきってから決めること3へ進む。** 段2を持つかどうかで、決めること3に
書くべき変更対象が変わるため（段2を持つなら案A分の設計が丸ごと増える）。

| 段 | 手段 | 失敗する条件 |
|---|---|---|
| 1 | 案B-d（アーカイブ） | API不達、`mcp` 経路で対応ツールが無い、アーカイブが上限超過 |
| 2 | 案A（clone） | git到達不可、資格情報が無い |
| 3 | **従来どおり hunk のみで続行し、その事実を報告する** | — |

- **段2を持つかは論点。** 案B-dが失敗する状況（API不達）では案Aも失敗する可能性が高く、
  「2つとも試して両方失敗する」ぶん遅くなるだけかもしれない。**2段（案B-d → hunkのみ）で
  足りるのではないか**という見立てを提示し、合意を取る。
- **段2を持つと決めた場合、決めること3へ次を追加する**（案Aの実装に要るもの。調査結果より）:
  `GIT_ASKPASS` によるトークン供給／`.git` の除去／clone URLを `GITLAB_HOST`・`GITLAB_REPO`
  から組み立てる処理（**JSONの `.host` はポートを落とす**）／`GIT_TERMINAL_PROMPT=0` 等の
  非対話化。**置き場所（`Provider.sh` か新規スクリプトか）まで決める。**
- **段3は必ず持つ**（`truncatedFiles` / `capped` と同じ扱いで、報告へ明記する）。中止はしない。

### `mcp` 経路（`gh`/`glab` CLI不在）での段1の扱い

`SKILL.md` 末尾の「CLI不在時の読み替え」表は、現在**手順3・4・7を「読み替え不要」**と
明記している。今回は**新たにAPIを叩く手順が手順2〜4へ増える**ため、この前提が崩れる。

- GitHub MCPにリポジトリのアーカイブを取得する手段があるかを確認し、**無ければ
  「`mcp` 経路では段1を試さず、段2または段3へ縮退する」と決める**。
- **WebFetch/curlへフォールバックしない**（DDR 0020・0027）。読み替え規定が無い状態で
  実行させると、その場の判断でこの禁止を破る方向の即興が起きうる。

### 段3（縮退）における各コンポーネントの挙動

**受講者ソースが取得できなかった経路では、本設計の3つの変更がいずれも成立しない。**
何がどう戻るかを明記する。

| コンポーネント | 段1・2（取得できた） | 段3（取得できない） |
|---|---|---|
| `mapping` の範囲 | 受講者の全ファイル | 変更ファイルのみ（従来） |
| `submissionOnly` の意味 | 正解に無いファイル | 今回追加したファイル（従来） |
| 禁止語の材料 | 受講者ソース全体 | 受講者diff（従来） |

- **サブエージェント定義へ無条件に「`submissionOnly` は正解に無いファイル」と書いてはいけない。**
  縮退時の実際の出力と食い違い、**issue #6 が問題にした「渡していないものを読んでよいと
  書いてある」のと同型の不一致を新たに作る**。
- 対処案: **入力JSONへ縮退フラグを持たせ、定義側の分岐を機械的にする**（条件付きの記述を
  自然言語で書くより、フラグで表すほうが読み違えが起きない）。どちらを採るか決める。
- 禁止語についても、**縮退時は経路によって drop 件数が変わる**（調査結果が「経路依存は解消する」と
  したのは段1・2の話である）。報告へ「どの段で実行したか」を出すかを決める。

**手順7を落とさないこと。** スクリプト側だけ改修して呼び出し側を据え置くと、検査は従来どおり

### アーカイブ取得の `ref` に何を渡すか

- **`headSha` を使う**（ブランチ名を使わない）。ブランチ名だと、レビュー中に受講者が追加で
  反映した時点で、**diffのhunkと取得したソースが別のコミットになる**（存在しない行を指摘しうる）。
- **取得後にhead SHAとの一致を検証するか**を決める（調査では案Aの成立条件として一致を確認した。
  同じ厳密さを主経路にも持たせるか）。
- **フォークから出されたPRの扱い**を決める。GitHubでは、base リポジトリの tarball で
  フォーク側の head SHA を取得できない可能性がある（調査は**同一リポジトリ内ブランチのPRでしか
  実測していない**）。head側のリポジトリを使うのか、縮退するのか。
- **GitLabの `projects/:id` の組み立て方**（数値IDか、URLエンコードしたパスか）。

### `submissionOnly` の意味変更をどう扱うか

- 現在: 「今回のMRで追加したファイル」
- 変更後（段1・2）: 「**正解に無いファイル**」（受講者が前から持っているものを含む）

サブエージェント定義の手順1は `referenceOnly` を起点にしているため、影響は小さいと見込む。
ただし**別解の判定**（受講者独自のファイルを「余分」と見るか「別解」と見るか）に効くため、
**定義側へ意味を明記する**。縮退時の扱いは「決めること2」の表に従う。

### 後始末（手順10）

受講者側の一時領域を `answer-talker-submission.sh cleanup` で消す。**正解ソース側と同じ
マーカーファイル方式**にし、`resolve`/`cleanup` の対称性を保つ。手順10は「失敗しても必ず通る」
位置づけであるため、**2つの cleanup のうち片方が失敗しても、もう片方を実行する**。

## 決めること4: サブエージェントに「必ず読ませる」方法

**`submission.root` を渡すだけでは「たまたま読んだ」に留まる**（`reference.root` と同じく
Readで任意に読む設計のため）。案を出して合意を取る。

- (a) 定義へ**手順として明記する**（「手順0: `submission.root` 配下のファイル一覧を取得し、
  `mapping.matched` に無いファイルも含めて目を通す」）
- (b) 呼び出し側（SKILL.md 手順6）で、**ファイル一覧を入力へ含める**（中身ではなく一覧）
- (c) 両方

**(c) を推す。** 一覧を渡せば「何があるか」は確実に伝わり、手順があれば「読む」ことが規約になる。
**ただし一覧の件数上限を決めること**（下記）。

## 決めること5: サイズ・件数の上限とバイナリの扱い

**縮退の表に「アーカイブが上限超過」と書く以上、上限を決めなければ段1は縮退できない。**

- **アーカイブサイズの上限**と、その判定を**取得前に行うか取得後に行うか**（取得前に知る
  手段があるか）。タイムアウトも併せて決める。
- **バイナリ・生成物の除外方針**（`node_modules/`・ビルド成果物・画像等）。除外しないと、
  展開先が数百MBになる、決めること4(b)の一覧が数千行になる、サブエージェントがバイナリを
  Readして失敗する、といった形で表面化する。
- **一覧に載せるファイル数の上限**（超えた場合にどう伝えるか。`truncatedFiles` と同じ考え方）。

**ここで決めきれない場合は、どの計画へ送るかをスコープ外節へ明記する**（決めないまま
どこにも無い状態にしない）。調査結果の未決定事項3・5に対応する。

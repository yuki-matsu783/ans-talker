# 【設計】受講者ソースの受け渡し

- issue: [#6](https://github.com/yuki-matsu783/ans-talker/issues/6) / PR: [#7](https://github.com/yuki-matsu783/ans-talker/pull/7)
- 全体作業計画: `plans/bubbly-exploring-biscuit.md`
- 調査結果（前提）: `reports/20260821_bubbly-exploring-biscuit_受講者ソースの受け渡し方式の調査結果.md`
- 対象フェーズ: フェーズ3〈作業〉のうち **`【設計】` のみ**（`【実装】【テスト】` は別計画）

## 目的

**受け渡し方式を決定し、6ファイルへの変更内容を、実装に入れる粒度まで確定させる。**

**この計画には結果を書かない。** 設計の結果は
`reports/日付_bubbly-exploring-biscuit_<内容>.md` へ記録する。

## 決めること1: 受け渡し方式（**案B-d を採る**）

調査で案A・案B-dのどちらも成立したため、**選択の問題**になった。**案B-d（アーカイブ一括取得）を
第一候補、案A（shallow clone）をフォールバックとする**案を提案し、合意を取る。

| | 案B-d（提案） | 案A |
|---|---|---|
| 呼び出し回数 | **1回**（ファイル数非依存） | 1回 |
| 実測 | 1122ms（GitHub）/ 2044ms（GitLab） | 同程度 |
| `.git` | **含まない** | **同梱。除去が必須** |
| 認証 | **`gh`/`glab` の認証をそのまま使う** | gitへの資格情報供給が別途要る（`GIT_ASKPASS`） |
| 追加の依存 | `tar`（展開時に `--force-local`） | なし |

**案B-dを推す理由**は、`.git` の除去と資格情報供給という**2つの追加作業が要らない**こと。
とくに `.git` は、サブエージェント定義の「コミットメッセージを読んではいけない」規約を
**構造的に守れる**かどうかの差になる（案Aでは除去を忘れた時点で規約が建前になる）。

**却下する案**:

- **案B-a（`matched` のみ）**: issue本文が案Bとして定義していたが、**目的未達**
  （変更していないファイルが入らない）。
- **案B-b/c（ファイル単位API）**: ファイル数に比例して 672ms〜1027ms かかる。50ファイルで
  34〜51秒。
- **案Aを第一候補にする**: 上記2つの追加作業のぶん、失敗経路が増える。

## 決めること2: 縮退（フォールバック）の段数

**3段にするか2段にするかを決める。**

| 段 | 手段 | 失敗する条件 |
|---|---|---|
| 1 | 案B-d（アーカイブ） | API不達、アーカイブが巨大 |
| 2 | 案A（clone） | git到達不可、資格情報が無い |
| 3 | **従来どおり hunk のみで続行し、その事実を報告する** | — |

- **段2を持つかは論点。** 案B-dが失敗する状況（API不達）では案Aも失敗する可能性が高く、
  「2つとも試して両方失敗する」ぶん遅くなるだけかもしれない。**2段（案B-d → hunkのみ）で
  足りるのではないか**という見立てを提示し、合意を取る。
- **段3は必ず持つ**（`truncatedFiles` / `capped` と同じ扱いで、報告へ明記する）。
  中止はしない。

## 決めること3: ファイルごとの変更設計

| ファイル | 変更内容 |
|---|---|
| `.claude/scripts/src/vcs/Provider.sh` | **アーカイブ取得関数を1つ追加**（仮 `get_repo_archive <ref> <出力先>`）。GitHub `repos/{owner}/{repo}/tarball/{ref}` ／ GitLab `projects/:id/repository/archive.tar.gz?sha=<sha>`。**返却のキー集合を一致させる**流儀を踏襲する |
| `.claude/scripts/src/answer-talker-submission.sh`（**新規**） | `resolve` / `cleanup` を持つ。`answer-talker-reference.sh` と**同じ形**にする（マーカーファイル方式・`cleanup` は冪等・自分が作った一時ディレクトリだけ消す）。展開時に `--strip-components=1` と `--force-local` |
| `.claude/scripts/src/answer-talker-map.sh` | 対応付けの範囲を「受講者の**全**ファイル」対「正解の全ファイル」へ広げる。`submissionOnly` の意味が変わる（下記） |
| `.claude/scripts/src/answer-talker-spoiler-check.sh` | 禁止語の差し引き材料を「受講者diff」から「**受講者ソース全体**」へ広げる（**必須。調査で確定**） |
| `.claude/agents/answer-talker-reviewer.md` | 入力仕様へ `submission.root` を追加。「読んでよいもの」を実態と一致させる。**「どのファイルをどの順で読むか」の手順を持たせる** |
| `.claude/skills/answer-talker/SKILL.md` | 手順2〜4（受講者ソースの取得を追加）・手順6（サブエージェントへ渡すもの）・**手順10（後始末に受講者側を追加）**・手順11（縮退した場合の報告） |

### `submissionOnly` の意味変更をどう扱うか

- 現在: 「今回のMRで追加したファイル」
- 変更後: 「**正解に無いファイル**」（受講者が前から持っているものを含む）

サブエージェント定義の手順1は `referenceOnly` を起点にしているため、`submissionOnly` の
意味変更が観点表の読み方へ与える影響は小さいと見込む。ただし**別解の判定**（受講者独自の
ファイルを「余分」と見るか「別解」と見るか）に効くため、**定義側へ意味を明記する**。

### 後始末（手順10）

受講者側の一時領域を `answer-talker-submission.sh cleanup` で消す。**正解ソース側と同じ
マーカーファイル方式**にし、`resolve`/`cleanup` の対称性を保つ。手順10は「失敗しても必ず通る」
位置づけであるため、**2つの cleanup のうち片方が失敗しても、もう片方を実行する**。

## 決めること4: サブエージェントに「必ず読ませる」方法

調査では扱えなかった論点。**`submission.root` を渡すだけでは「たまたま読んだ」に留まる**
（`reference.root` と同じくReadで任意に読む設計のため）。

案を出して合意を取る。

- (a) 定義へ**手順として明記する**（「手順0: `submission.root` 配下のファイル一覧を取得し、
  `mapping.matched` に無いファイルも含めて目を通す」）
- (b) 呼び出し側（SKILL.md 手順6）で、**ファイル一覧を入力へ含める**（中身ではなく一覧）
- (c) 両方

**(c) を推す。** 一覧を渡せば「何があるか」は確実に伝わり、手順があれば「読む」ことが規約になる。

## 検証（この設計が完了したと言える条件）

1. 方式（案B-d / 縮退の段数）が**理由とともに**決まり、却下案も残っている。
2. 6ファイルすべてについて、**何をどう変えるか**が実装に入れる粒度で書かれている。
3. `submissionOnly` の意味変更の扱いが決まっている。
4. **サブエージェントに必ず読ませる方法**が決まっている。
5. **後始末の対称性**（正解側・受講者側）が設計に含まれている。
6. DDR候補が洗い出されている（**受け渡し方式の選択**は確実に候補。禁止語の材料拡張は
   DDR 0061 との関係を整理する必要がある）。

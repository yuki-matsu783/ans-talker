# 【調査】answer-talker スキルの設計調査

- issue: [#1](https://github.com/yuki-matsu783/ans-talker/issues/1) / PR: [#2](https://github.com/yuki-matsu783/ans-talker/pull/2)
- 全体作業計画: `plans/bubbly-exploring-biscuit.md`
- 対象フェーズ: フェーズ2〈調査〉（flow-id 2-1〜2-10）

## 目的

`answer-talker` スキルの**設計を決められる状態にする**。具体的には、フェーズ3の個別作業計画
（`【設計】`）で「どのファイルに何を持たせ、どのインターフェースで繋ぐか」を書き切れるだけの
材料を集める。**この計画では結論を出さず、何をどう調べるかだけを定める**（調査結果は
`reports/` 配下へ記録する）。

## 前提（既に合意済みの事項）

| 事項 | 合意した場所 |
|---|---|
| issueは分割せず1件で進める（横断的変更のため） | 全体作業計画（flow-id 1-5で承認） |
| 成果物は `.claude/` 配下に収める | 同上 |
| ネタバレ防止はサブエージェントの規約と機械的検査の**二重**で担保する | issue #1 受け入れ条件 |
| 投稿前の承認は `AskUserQuestion` で1回だけ | issue #1「期待する動作」6 |

## 調査論点

各論点は「**問い**」「**調べ方**」「**この論点で決めたいこと**」の3点で構成する。

### 論点1: 既存 `adversarial-review` からの再利用範囲

- **問い**: 承認モデル・findings JSONスキーマ・確度×重大度の選別表・投稿処理のうち、
  どこまでを踏襲し、どこから answer-talker 固有にするか。実施回数の上限機構
  （`adversarial-review-count.sh`）を answer-talker にも課すべきか。
- **調べ方**:
  - `.claude/skills/adversarial-review/SKILL.md`（読了済み）と
    `.claude/agents/adversarial-reviewer.md`・`.claude/docs/spec/adversarial-review.md` を読む
  - `.claude/scripts/src/adversarial-review-count.sh` と
    `.claude/docs/spec/adversarial-review.md` の該当節から、上限機構が何を防いでいるかを確認する
  - `issue-mr-flow/SKILL.md`「敵対的レビューの位置づけ」を読み、answer-talker が
    **flow-idを増やさない並行手順**として同じ形に収まるかを確認する
- **決めたいこと**: 再利用する要素の一覧と、answer-talker 固有にする要素の一覧。
  上限機構の要否とその理由。

### 論点2: MR番号起点のdiff取得（`Provider.sh` への追加関数）

- **問い**: 新設する関数は何を返すべきか（変更ファイル一覧とdiff本文を1つのJSONにするか、
  2関数に分けるか）。GitHub/GitLabでコマンドはどう異なるか。差分の基準（defaultブランチとの
  三点diffか、MRの変更そのものか）をどう取るか。
- **調べ方**:
  - `.claude/scripts/src/vcs/Provider.sh` の既存関数（`get_mr_for_branch`・
    `get_mr_unresolved_comments`・`add_mr_inline_comments`・`get_mr_diff_url`）を読み、
    返却形・エラー処理・`require_vcs_cli` ガードの流儀を揃える
  - `gh pr diff` / `gh pr view --json files` の出力を**本PR #2 に対して実行**して確認する
  - GitLab側は `glab` が手元に無いため、コマンドの対応関係のみ文献ベースで整理し、
    **実機確認できない旨を結果に明記する**
  - `.claude/rules/shell-script-style.md`「大きなJSONを引数で渡さない」制約に照らし、
    diff本文の受け渡し方（ファイル経由か標準出力か）を検討する
- **決めたいこと**: 関数名・引数・返却JSONの形・差分の基準・大きなdiffの扱い。

### 論点3: 正解ソースの取得方式

- **問い**: URL形態とローカルパス形態をどう正規化するか。一時ディレクトリの後始末をどう保証するか。
  git bash / Windows 固有の罠（`MSYS_NO_PATHCONV`・パス変換）は効くか。
- **調べ方**:
  - 既存スクリプト（`check-base-conflicts.sh`・`cleanup-task.sh`）の `trap` の使い方・
    一時ディレクトリの扱い・引数バリデーションの流儀を読む
  - `.claude/rules/shell-script-style.md`「git bashのパス変換の落とし穴」に該当する操作
    （`git clone` へ渡すパス、`jq` へ渡すパス）を洗い出す
  - shallow cloneの条件（`--depth 1` で足りるか。正解が特定ブランチ・タグにある場合の指定）
  - 認証を要する非公開リポジトリを対象にするか（**対象にしないなら明記する**）
- **決めたいこと**: スクリプトのインターフェース（引数・返却）・後始末の方式・
  受け付ける正解の場所の形態の範囲。

### 論点4: 受講者の変更ファイルと正解側ファイルの対応付け

- **問い**: 両者をどう突き合わせるか。**正解側にしか存在しない構成要素**（受講者がまだ作って
  いない分割単位）をどう検出し、指摘の材料として渡すか。
- **調べ方**:
  - 対応付けの候補（同一パス優先 → ファイル名一致 → ディレクトリ構造の類似 →
    対応なし）を列挙し、演習という文脈での妥当性を検討する
  - 「正解側にしかないファイル」を単純に列挙するだけで足りるか、
    **中身の役割**（何を担うファイルか）まで要約して渡す必要があるかを検討する
  - 対応付けをスクリプトで機械的に行うか、サブエージェントの判断に委ねるかの線引き
- **決めたいこと**: 対応付けのアルゴリズムと、サブエージェントへ渡す入力の形。

### 論点5: ネタバレ防止の機械的検査

- **問い**: findings本文と正解ファイルの一致検査を、どの粒度で行うか
  （行単位／正規化後のトークン列／正解にしか現れない識別子）。誤検知と見逃しのトレードオフを
  どう置くか。混入を検知したときの挙動は何か（当該findingのみ落とすか、全体を中止するか）。
- **調べ方**:
  - 粒度ごとに、誤検知しやすいケース（`return nil`・`if err != nil` 等の汎用的な行、
    一般的な語）と見逃しやすいケース（空白・変数名だけ変えた転記）を具体例で洗い出す
  - 正解側にしか現れない識別子の抽出可能性（受講者側diffに現れない語の集合）を検討する
  - `.claude/scripts/test/` の既存テストの流儀（`passed=N failures=N`・純粋関数へ切る）を確認し、
    **単体テスト可能な形に切れるか**を確かめる
- **決めたいこと**: 検査アルゴリズム・閾値の考え方・混入検知時の挙動・テストケースの骨子。

### 論点6: 実例確認に使う演習MR・正解ソースの題材

- **問い**: 受け入れ条件「正解側にしか存在しない分割単位について……実例で確認している」を、
  何を題材に満たすか。
- **調べ方**:
  - 本リポジトリ自身のPR（例: PR #2）と、その正解に相当するものを代用できるかを検討する
  - 代用できない場合、最小の題材（1ファイルにまとまった処理 対 3ファイルに分割された正解、
    程度の規模）を用意するコストを見積もる
  - 題材を**リポジトリにコミットするか、実行時に作る使い捨てにするか**を検討する
    （`.claude/` 配下に演習用のダミーコードを恒久的に置くことの是非）
- **決めたいこと**: 題材の内容・置き場所・フェーズ3のどのタイミングで用意するか。

## この計画で決めないこと（スコープ外）

- **実装の詳細**（関数の中身・SKILL.mdの文面）。フェーズ3の `【設計】`・`【実装】【テスト】` で扱う。
- **spec/DDRに何を書くか**。フェーズ4の flow-id 4-1 で洗い出す（論点1・3・5で設計判断が生じた
  事実は結果に記録するが、DDRの起票は行わない）。
- **GitLab経路の実機確認**。`glab` が手元に無いため、対応関係の整理までとする
  （実機確認できない旨を結果に明記し、未決定事項として残す）。
- **非公開リポジトリの認証**を要する正解ソースの取得（論点3で対象外と決める場合、その旨を記録する）。

## 検証（調査完了の判定）

調査が完了したと言えるのは、次がすべて満たされたときとする。

1. 6論点すべてについて、「決めたいこと」に挙げた項目が結果mdに書かれている
   （結論が「対象外とする」でもよいが、**理由が添えられていること**）。
2. 論点2について、**GitHub経路で実際に動作を確認したコマンドと出力**が結果に載っている。

   ```bash
   source .claude/scripts/src/vcs/Provider.sh
   gh pr view 2 --json files --jq '.files[].path'
   gh pr diff 2 | head -40
   ```

3. 論点5について、誤検知・見逃しの**具体例が最低3件ずつ**挙がっている。
4. フェーズ3の `【設計】` 計画に書くべき項目（追加するファイル・関数のインターフェース・
   スクリプトの引数）が、結果mdから転記できる粒度で揃っている。
5. 未決定のまま残す事項が、**未決定として明示的に列挙**されている（暗黙に落とさない）。

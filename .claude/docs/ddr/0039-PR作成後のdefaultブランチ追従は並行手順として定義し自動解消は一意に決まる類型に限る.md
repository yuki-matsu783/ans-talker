# 0039. PR作成後のdefaultブランチ追従は並行手順として定義し自動解消は一意に決まる類型に限る

## 背景

issue #88「PR作成後のdefaultブランチ追従を自動で監視し、コンフリクトを検知しだい解消する手順を
整備する」。

flow-id 5-2（DDR 0029）は、Draft解除の直前に1回だけ `check-base-conflicts.sh` を実行する設計で、
**PR作成後〜マージまでの間にdefaultブランチが進む場合を扱っていない**。レビュー待ちが長いほど、
また並行するPRが多いほど、この期間に生まれるコンフリクトを取りこぼす。

実例として、issue #39 のPR #81 では、PR作成後の短時間に `main` が4回進み（PR #82/#83/#84 等の
マージ）、そのつどユーザーが「コンフリクトしている」と指摘して解消した。DDR番号は
0034→0035→0036→0038 と3回繰り下げている。衝突箇所は毎回同じ性質だった。

- DDRの連番（gitはコンフリクトとして報告しない。DDR 0029「背景」）
- `.claude/docs/README.md` のDDR一覧の末尾
- `.claude/docs/spec/issue-mr-workflow.md` の `## 影響範囲` の末尾
- `HANDOFF.md`

このとき暫定的に、Claude Code on the web のPRイベント購読（`subscribe_pr_activity`）と自己
チェックインの予約（`send_later`）で自動追従したが、**いずれもセッションに紐づく機能であり、
リポジトリのAIアセット（`.claude/` 配下）には何も残らない**。別セッション・ローカルのgit bash
環境では同じことが再現しない、というのが本issueの出発点である。

## 決定

1. **追従監視は、flow-idを持たない「フェーズ横断の並行手順」として定義する。**
   `.claude/skills/issue-mr-flow/SKILL.md` に「PR作成後のdefaultブランチ追従（監視）」節を新設し、
   flow-id 1-3（PR作成）の直後に開始、5-4（マージ）またはPRのクローズで停止する、という**期間**
   として位置づける。既存flow-idとの対応（開始・検知のタイミング・最終ゲート・停止）は同節の表で示す。

2. **flow-id 5-2 は残し、「最終ゲート」へ意味づけを変える。** 監視は実行環境の機能とセッションの
   寿命に依存するため、一度も動かないまま進むセッションがありうる。必ず通るゲートを1つ残すことで、
   その場合でもコンフリクトを抱えたままDraft解除へ進む経路をふさぐ。「監視で追従済みだから5-2は
   省略してよい」とはしない。

3. **実行環境別の手段を決め打ちにする。**
   - Claude Code on the web: `subscribe_pr_activity` でPRイベントを購読し、あわせて `send_later`
     で自己チェックイン（1時間後程度）を予約する。webhookはpush・CI成功・マージ可否の遷移を
     取りこぼすことがあるため、購読だけに頼らない。変化が無ければ報告せず再予約のみ行う。
   - ローカル（git bash）: 購読・予約に相当する仕組みが無いため、人手で `/resolve-conflict` を
     回す（各pushの直後・作業再開時・flow-id 5-2）。

4. **監視中の自動解消は「解消方法が一意に決まる（どちらの意図も失われない）類型」に限る。**
   `resolve-conflict` スキルの類型A（DDR番号）・B（管理外にした生成物）・D（過去changelog）は
   規則が確定しているため承認を待たずに解消してよい。類型C（同じドキュメントの近接行）は
   「両方残す」で足りる限り自動、散文が両側で書き換わって内容が矛盾する場合は類型Eへ回す。
   類型E（同じロジックの競合）は解消せずに止め、`AskUserQuestion` で人間の判断を仰ぐ。
   検知結果に類型Eが1つでも含まれる場合は、他の類型も解消せずに止める（マージ途中の作業ツリーで
   人間の応答を待つ状態を作らないため）。

5. **DDR 0029 の決定6（解消時はユーザーの承認を必ず取る）は、監視モードに限って緩和する。**
   レビュー待ちの間に人間の応答を待つと、待っている間にdefaultブランチがさらに進み、同じ解消を
   やり直すことになる。承認が守っていたのは「設計判断を無言で下さない」ことであり、解消方法が
   一意に決まる類型ではその価値が発生しない。対話可能な通常の呼び出し（`/resolve-conflict`・
   flow-id 5-2）では決定6をそのまま適用する。DDR 0029 は全体としては有効なため
   `status: superseded` にはしない。

6. **監視の状態は `HANDOFF.md` のヘッダ1行（`- 追従監視:`）と `resume` の報告項目で引き継ぐ。**
   購読・予約はセッションが終われば消えるが、この2箇所は次のセッションが必ず読む。PRが未マージの
   まま引き継いだ場合は、`resume` の手順5で監視を取り直す（`issue-mr-resume` エージェントは
   「取り直しが必要」と注記するだけで、取り直し自体は呼び出し元が行う）。

7. **自動解消でも、`commit` スキル経由のコミットと `resolve-conflict` スキル Step 5 の検証
   （コンフリクトマーカー・unmergedパス・`bash -n`・単体テスト・DDR番号重複の再確認）は省略しない。**
   省略してよいのは Step 2 の承認だけである。

## 却下した案

- **新しいflow-idとして挿入し、以降を繰り下げる**: 「必ず通る手順」として表に載る利点があり、
  DDR 0029 の決定4（5-2を新設して繰り下げた）と同じやり方でもある。しかし監視は**期間を持つ
  状態**であり、進捗表の1行として `[x]` を付けられる性質のものではない（開始したことは記録
  できても、完了はマージまで来ない）。加えて40ステップの繰り下げは、`update-handoff-progress.sh`
  のループ範囲定数・HANDOFF進捗表・`commit` スキル・`git-workflow.md`・`docs-workflow.md`・
  spec へ一斉に波及し、コストが内容に見合わない。

- **flow-id 5-2 を廃止し、監視だけにする**: 手順が1つ減って見通しは良くなるが、監視は実行環境の
  機能に依存する（ローカルでは人手）。監視が動かないセッションでは検知がゼロになり、issue #46 で
  作った歯止めを失う。決定2のとおり最終ゲートとして残す。

- **GitHubの "Update branch"（`mcp__github__update_pull_request_branch`）で自動追従する**:
  APIひとつでbaseを取り込め、実装は最小で済む。しかし**gitが検知できない類型A（DDR番号の重複）を
  無言でマージしてしまう**（DDR 0029「背景」）。過去4件のコンフリクトはすべて類型Aであり、
  最も頻発する衝突をむしろ見えなくする。加えてマージメッセージが `Merge branch 'main' into ...`
  になり、「何をどう解消したか」が履歴から読めなくなる（DDR 0029 の却下案と同じ理由）。

- **PostToolUse / SessionStart hook で自動チェックする**: 「読まれなければ機能しない」問題を
  避けられるが、DDR 0029 が却下した理由がそのまま当てはまる。pushのたびに `git fetch` を伴う
  判定を挟むのはコストに見合わず、push検知hookはコマンド文字列の部分一致で誤発火する既知の問題を
  抱えている（`.claude/rules/git-workflow.md`「push検知hookの誤検知」）。監視が必要な頻度は
  「イベントが来たとき」であって「pushのたび」ではない。

- **CI（GitHub Actions）で、defaultブランチへのマージ時に全オープンPRを追従させる**: セッションに
  依存せず確実に動く唯一の案で、リポジトリにも残る。しかし (a) 類型Aの解消はファイル名の改番と
  複数ファイルの参照更新を伴い、CI上の機械的なマージでは実行できない、(b) このリポジトリは
  CIワークフローを一切持たず、本issueのために常時動く実行基盤を導入するのは範囲を大きく超える、
  (c) `git push` する権限をCIへ与えることになり、レビュー中のブランチが自動で書き換わる。
  将来アプリ本体を追加してCIを導入する時点で、再検討してよい。

- **常時rebase運用へ変更する**（作業ブランチを常に最新のdefaultブランチの上へ載せ替える）:
  そもそもコンフリクトが溜まりにくくなる。しかしDDR 0029 の決定5のとおり、作業ブランチは既に
  リモートへ反映済みで、レビューコメントが特定のコミットSHA・diffに紐づいている。履歴を書き換えると
  レビュアーのローカルチェックアウトとMR上の参照リンクが壊れる。`resolve-conflict` スキルの
  絶対ルール（rebase・force反映の禁止）とも正面から衝突する。

- **そもそも衝突しにくい構造へ変える**（DDR連番の廃止・`.claude/docs/README.md` のDDR一覧の自動
  生成・spec の changelog をファイル分割する等）: 根本解決ではある。連番の廃止は DDR 0029 が既に
  却下しており（既存DDRと相互参照の全面改番が必要）、状況は変わっていない。一覧の自動生成・
  changelogの分割は本issueの範囲外の構造変更で、いずれも「追従を監視する」という本issueの
  期待する動作を代替しない（衝突の頻度は下がるが、`main` が進むこと自体は止められない）。
  監視の仕組みを整えたうえで、頻度が問題であり続けるなら別issueとして扱う。

- **検知結果をキャッシュし、前回と差分があるときだけ判定する**: `check-base-conflicts.sh` の
  実行回数を減らせるが、1回あたりのコストは `git fetch` と `merge-tree` のみで、監視の頻度
  （イベント単位・1時間単位）では最適化する価値が無い。状態ファイルを増やすと、その破損時の
  自己回復ロジックまで必要になる（`.claude/rules/shell-script-style.md`「JSON操作」の実例）。

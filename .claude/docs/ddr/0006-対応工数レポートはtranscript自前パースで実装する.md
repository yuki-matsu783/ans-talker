# 0006. 対応工数レポートはtranscript JSONLの自前パースで実装する

## 背景

issue #15「作業にかかったトークンなどの情報をMRのコメントに記載する」への対応にあたり、
Claude Codeがトークン使用量をどこから取得できるか公式ドキュメント（code.claude.com/docs/en/hooks）
で調査した。

- `Stop` / `PostToolUse` 等のhookがstdin経由で受け取るJSONペイロードに、トークン数・コスト情報は
  **含まれない**（`session_id` / `transcript_path` / `cwd` / `tool_name` 等の共通フィールドのみ）。
- `transcript_path` が指すJSONLファイルには各assistantメッセージの `message.usage`
  （`input_tokens` / `output_tokens` / `cache_creation_input_tokens` / `cache_read_input_tokens`）と
  `message.model` が含まれることを実transcriptで確認した。ただしこのJSONL形式は
  **Claude Code非公開の内部フォーマットであり、将来のバージョンで変更されうる**旨が公式に
  明記されている。
- `claude -p --output-format json` は `total_cost_usd` を含む構造化出力を返すが、これは
  **新規に起動した非対話的セッションの結果**であり、現在進行中の対話セッションの使用量を
  取得する手段にはならない。

## 決定

**他に確実な取得手段が無いため、`transcript_path` のJSONLを自前でベストエフォートパースする方式を
採用する。** 非公開フォーマットへの依存によるリスクは、以下の設計で吸収する。

1. **失敗を握りつぶす**: パースは1行ごとに`try`/`catch`で行い、壊れた行はスキップする。
   集計処理全体も呼び出し元（`post-push-usage-report.ps1`）側で`try`/`catch`し、失敗しても
   git push自体をブロックしない（記録が0件になるだけ）。
2. **金額（USD）は算出しない**: モデル単価表を自前で保守する必要が生じ、かつ実際の請求額と
   ずれるリスクがあるため、トークン数（input/output/cache write/cache read）のみを報告する
   （issue #15の受け入れ条件「何をコメントするかが明確」は、トークン数という生の数値のみで
   十分満たせると判断した）。
3. **コメント本文に「目安として扱ってください」と明記する**: 非公開フォーマット依存の
   ベストエフォート集計であることを利用者に常に伝える。

### `entry.gitBranch` によるブランチフィルタ

transcript の各assistantメッセージには、実行時にチェックアウトされていたブランチ名が
`gitBranch` フィールドとして記録されていることを実機確認した（全assistantエントリでの
付与率100%を確認済み）。

当初の実装（セッション全体の累計を無条件にそのブランチの使用量として扱う）では、
同一セッション内で複数ブランチを跨いだ場合に他ブランチ分のトークンが混入するバグがあった
（issue #15対応中の実データで、無関係な旧ブランチ分が452,144トークン混入していたことを確認）。
`entry.gitBranch -eq $Branch` でフィルタしてから集計するよう修正し、このバグを解消した。

### `PostToolUse`（git push検知）単体で完結させ、`Stop` hookは使わない

`Stop` は1ターン完了時にしか発火しないため、ターン途中で `git push` が実行されると
（例: ブランチ作成・調査・実装・pushを1ターン内で行う場合の最初のpush）、そのターンで
既に消費したトークンが未記録のまま「記録漏れ」に見える問題があった。

当初は「`Stop`の代わりに別のhookで記録する」のではなく、`post-push-usage-report.ps1`
（`PostToolUse`, git push検知）自身が投稿直前に同じ集計処理（`Sync-UsageState`）を
呼んで状態を最新化してから投稿する方式を採用し、`Stop`は「ターン数のカウント」専用の役割
（`sinceLastPush.turns`を+1するだけ）として残していた。`transcript_path` は`PostToolUse`の
ペイロードにも含まれる共通フィールドであるため、これが可能だった。

しかしその後、**`Stop`を完全に廃止**した。理由は次の2点。

1. `post-push-usage-report.ps1` が投稿直前に呼ぶ `Sync-UsageState` だけで、トークン・ツール実行回数
   の集計は既に完結しており、`Stop`はターン数カウントのためだけに残っていた。
2. その`Stop`依存のターン数カウントは、**トークン集計で修正したのと同じ穴**（そのターンの`Stop`が
   まだ発火していない状態でpushすると過少カウントされる）を抱えたままだった。実際、修正前の
   自動投稿コメントは実データ（トークン数・ツール実行回数）があるにもかかわらず
   「対象ターン数: 0」と表示される不整合が確認された。

そこで、ターン数も**「assistant応答回数」**と読み替えた上で、トークン・ツール実行回数と全く同じ
「transcriptとの差分を`sinceLastPush`へ加算する」方式で`Sync-UsageState`内に統合した
（`entry.gitBranch -eq $Branch` のエントリ件数を、セッションの前回記録値
`sessions[$SessionId].lastAssistantCount` と比較して差分を加算）。厳密な「会話ターン数」とは
ずれうる（1ターン内でtool_use往復により複数のassistantメッセージが生成されるため）が、
`Stop`の発火有無に依存しない一貫した値になる。結果、`Stop` hook（`stop-usage-record.ps1`）と
`.claude/settings.json`の`hooks.Stop`設定は不要になり削除した。共通の集計ロジックは
`.claude/hooks/lib/UsageTracking.ps1` に残り、`post-push-usage-report.ps1` のみから呼ばれる。

## 却下した案

- **`claude -p --output-format json` を別プロセスで呼んで集計する**: 公式にサポートされた
  手段だが、新規の非対話的セッションを起動する形になるため、現在進行中の対話セッションの
  使用量を取得する用途には使えない。
- **SessionEndフックで1セッション1回だけ投稿する**: `SessionEnd` は既定1.5秒の共有予算しか無く
  （設定で最大60秒まで拡張可能）、ネットワーク呼び出し（`gh pr comment`）を含む処理には
  タイムアウトリスクがある。加えて「1セッション1回」では、1つの長時間セッションで複数回push
  した場合の粒度が粗すぎる（ユーザーとの合意事項「git push成功時に前回投稿からの差分を投稿」に
  合わない）ため見送った。
- **推定コスト(USD)の算出**: モデル単価表の保守コストと実請求額とのズレのリスクを理由に見送った
  （上記「決定」参照）。
- **状態ファイルの排他ロック**: 複数のClaude Codeセッションが同一ブランチへ同時に書き込む場合の
  レースコンディション対策として検討したが、単一開発者が同一作業ディレクトリで複数セッションを
  同時実行する運用は想定しにくく、実装コストに見合わないと判断し見送った。既知の制約として
  `dev-tools/docs/spec/issue-mr-workflow.md` に記録するに留める。

## 検討の経緯

ユーザーから当初「フックで記録できる主な情報」として、トークン/コスト・ツール実行・ファイル操作・
プロンプト内容・サブエージェント往復などの案が提示されたが、調査の結果Stopペイロード単体では
取得できないことが判明し、範囲を「モデル別トークン数＋ツール実行回数＋ターン数」に絞ることで
合意した（USD推定コスト・ファイルdiff・プロンプト本文・サブエージェント詳細往復は対象外）。
詳細な比較検討は `worklog/2026-08-16_groovy-zooming-balloon.md`（設計反映時に削除予定）を参照していたが、
削除後は本DDRが唯一の記録となる。

## 追記（issue #28, PR #29レビュー指摘）

外部調査（[Claude Code JSONL logs undercount tokens](https://gille.ai/en/blog/claude-code-jsonl-logs-undercount-tokens/)）
によると、transcript JSONLはストリーミング応答の開始時点で`usage.input_tokens`等に
プレースホルダー値（0または1）を書き込み、応答完了後もその値を実際のトークン数へ更新しない
ケースがあり、結果としてinput側で最大100〜174倍、output側で最大10〜17倍の過小カウントが
観測されたと報告されている（キャッシュ関連フィールドはAPIレスポンス初期段階で確定するため
影響を受けにくいとされる）。

本DDRの「決定」で述べた「非公開フォーマット依存によるリスクの吸収策」（失敗を握りつぶす・
目安として明記する）は、この具体的な過小カウント機序が判明する前から採用していた対策だが、
結果的にこの問題にも同じ形で対応できている（プレースホルダーのまま更新されない値であっても
パース自体は成功するため「失敗の握りつぶし」は効かないが、「目安として扱ってください」という
利用者への明示が実質的な対応になる）。回避策（ステータスバー等、他の情報源を使う）は
transcriptの自前パースという設計方針自体を変えることになるため、本DDRの決定を覆すものではないと
判断し、既知の制約として`dev-tools/docs/spec/issue-mr-workflow.md`の「未決定事項・懸念点」に
記録するに留めた。issue #28で追加した稼働時間（`activeSeconds`）は`.timestamp`の差分のみを
使うため、この過小カウント問題の影響を受けない。

## 追記（PR #29レビュー指摘: サブエージェント使用量とsession-logsコピー方式）

サブエージェント（`Task`/`Agent`ツール等で起動される別セッション）のトークン・ツール使用量が
レポートに反映されていない点、および集計対象を`~/.claude/projects`配下から直接読むのではなく
リポジトリ内へコピーしてから処理する方式に変えるべきという2点のレビュー指摘を受け、対応した。

**session-logsローカルコピー方式を採用した理由**: `~/.claude/projects`はユーザープロファイル配下の
非公開パスであり、本DDRの「決定」で述べた「非公開フォーマット依存によるリスク」と同種の性質
（将来の変更・ローテーション等で内容が失われうる揮発性）を持つ。`git push`検知のたびに
メイン・サブエージェント両方のtranscriptをリポジトリ内のgitignore対象ディレクトリ
（`.claude/session-logs/`）へコピーしておくことで、既存の状態ファイル（`.claude/usage-state/`）と
同じ場所に生ログのスナップショットが残り、調査・デバッグが行いやすくなる。集計処理自体
（`_usage_aggregate_transcript`）はコピー先のローカルファイルを読むだけに変更し、集計ロジック
本体は無改造とした。

**全件再パース＋スナップショット差分方式を維持し、行オフセットベースの差分パースへ踏み込まなかった
理由**: issue #28で導入した`activeSeconds`（gapベースのidle検出＋tail buffer）の単調非減少性の
証明は、「毎回全件を時系列で走査し直す」ことを前提にしている。オフセット方式（前回読んだ行数を
記録し新規追加分のみパースする）に変えると、前回の末尾の`prevTimestamp`や「セグメントが開いていたか
閉じていたか」という新しい状態を永続化する必要が生じ、既に検証済みの単調性証明が崩れるリスクが
大きいと判断した。本機能は`git push`時にしか起動しない低頻度処理であり、1セッション分のtranscript
サイズであれば全件再パースの性能コストは許容範囲と判断し、確実性を優先した。

**`agentId`単位のスナップショット・`agentType`単位の表示集約という二段設計を採用した理由**:
サブエージェントは`agentId`（起動ごとに一意）と`agentType`（`Explore`等、複数回起動されうる種別）の
2つの識別子を持つ。累計スナップショット（差分計算の基準）を`agentType`単位にしてしまうと、
複数の`agentId`が同じ`agentType`で並行・順次実行された場合に、どの`agentId`分がどこまで
カウント済みかを区別できず誤差が生じうる。`agentId`単位でスナップショットを保持することで、
既存の`sessions[<sessionId>]`と全く同じ「current - prevSnapshot（下限0）」ロジックがそのまま
安全に適用でき、二重計上・過小計上を避けられる。一方でレポート上は`agentId`ごとに行を分けると
冗長になるため、表示・`sinceLastPush`への集約は`agentType`単位で合算する。

**ネストしたサブエージェント（depth 2以降）を対象外とした理由**: `meta.json`の`spawnDepth`
フィールドから理論上ネストがありうることは分かったが、このリポジトリの実データでは`depth 1`のみ
観測され、ネスト時のディレクトリ構造・スキーマ自体を確認できなかった。検証できない構造への対応は
既知のバグを埋め込むリスクの方が大きいと判断し、明示的な既知の制約として
`dev-tools/docs/spec/issue-mr-workflow.md`に記録するに留めた。

## 追記（issue #34: agentType単位の表示集約をやめ、agentId単位表示へ変更）

上記「`agentId`単位のスナップショット・`agentType`単位の表示集約という二段設計」のうち、
**表示集約を`agentType`単位で合算する部分を廃止し、`agentId`単位（起動したagentごとに1行）へ
変更した**。スナップショット自体（累計差分計算の基準）が`agentId`単位である点は変更していない。

**変更理由**: 実際に複数の`agentId`を同じ`agentType`（例: `Explore`を複数回起動）で使う運用が
始まったところ、「合算されるとどのagentがどれだけ使ったか分からない」というフィードバックを受けた。
「レポート上は`agentId`ごとに行を分けると冗長になる」という当初の懸念よりも、内訳が見える
ことの価値の方が高いと判断した。合わせて、行ラベルとして`agentType`だけでは`Explore`が並んだ
場合に区別がつかないため、`meta.json`の`description`フィールド（サブエージェント起動時の
説明文。実データで存在を確認済み）も表示するようにした。

**同時に見つかったpush差分バグとの関係**: 本変更を検討する過程で、`_usage_merge_state`の戻り値が
`.agents`（`agentId`単位の累計スナップショットを保持するフィールド）を引き継いでおらず、
サブエージェント分の差分が常に前回全量のまま再送され続けるバグが見つかった（issue #34の主目的）。
本追記で述べる表示方式の変更とは独立した不具合だが、同じ`_usage_merge_agent_state`まわりの
コードを扱うため同じissue・同じ変更でまとめて対応した。詳細は
`dev-tools/docs/spec/issue-mr-workflow.md`「サブエージェントの使用量記録」節を参照。

## 追記（issue #37: 行オフセットベースの差分パースへ移行）

「利用したツール数が明らかにずれている」という利用者報告を受けて調査した結果、上記
「全件再パース＋スナップショット差分方式を維持し、行オフセットベースの差分パースへ踏み込まなかった
理由」で述べた判断を、`tools`/`tokens`/`turns`（assistant応答回数）については**覆した**
（`activeSeconds`については単調非減少性の前提が崩れるリスクを避けるため、この判断は維持し
既存方式のまま変更していない）。

**実データで確認した不具合**: 実transcript（`.claude/session-logs/`配下、当時のパス）をjqで調査した
結果、`assistant`行1178件に対し`uuid`固有数533件（約2.2倍）という重複が見つかった。例えば
uuid `febc42cc-4d0c-4d98-a145-f0cd73bbffb0`は4回出現し、うち3回は`gitBranch:
"feature-39-use-commit-skill-rule"`、最後の1回だけ`gitBranch:
"feature-45-commit-skill-skip-confirmation"`だった。同一セッションが複数回・複数ブランチに
わたってresumeされる際、Claude Code側が過去のtranscript行を「resume時点のgitBranch」で
再度書き出す（＝重複行が生まれる）ことに起因すると推測される。従来の「毎回全件を再パースし、
前回の累計との差分（引き算）を計上する」方式では、セッションが新しいブランチで初めてpushされた
際に前回スナップショット（`sessions[sessionId]`）が存在せず、蓄積済みの全件がその新ブランチの
初回差分としてまるごと計上されてしまっていた。

**却下した案: uuidベースの重複排除**（同一uuidの行は最初の出現＝元のブランチのものだけを残す）。
一度この案でPlanモードの承認を得ようとしたが、ユーザーから「あくまでparentuuidなので、重複が
あるのはおかしくない」という指摘により却下された。`uuid`は会話木のノード識別子
（`parentUuid`によるチェーン構造）であり、同一uuidが複数箇所に現れること自体を「異常」と
決めつけて排除するのは前提が誤っていた、という指摘だった。

**採用した方式**: issue本文が当初から提案していた、push断面ごとにtranscriptの「これまでに
処理済みの行数」を記録し、前回pushからの新規行のみを対象に集計する方式を採用した。
`usage/state/session-cursors/<sessionId>.json`に`lastLineCount`（空行を除いた行数で、前回までに
処理済みの行数）を**ブランチに紐付けず、セッション単位でグローバルに**記録し、push毎にカーソル
位置以降の新規行のみをtools/tokens/turns/skillCalls/agentCalls/askUserQuestionsの対象として
そのまま`sinceLastPush`へ加算する（引き算は不要）。この方式は、行の中身（重複かどうか・どの
`gitBranch`ラベルが「正しい」か）を一切詮索せず、「一度数えた範囲は二度と数え直さない」という
機械的な原則だけで、実データで見つかった不具合（新ブランチでの初回pushで過去分がまるごと
計上される）を解消できる。カーソルをセッション単位でグローバルに管理することで、セッションが
別ブランチへresumeされても、そのブランチでの新規行が無ければ状態は更新されない
（＝過去ブランチ分の再計上が起きない）。

**既知の限界（意図的に対応しないこと）**: この方式は「同じ行を同じ位置から二重に読むこと」は
確実に防ぐが、「resumeによってtranscript行が新しい物理位置に再度書き出された場合、その重複行
自体が新規行として計上される」ケースまでは防げない。内容の重複を判別して除外する仕組みは
意図的に持たない（uuidベースの重複排除が却下された経緯を踏まえ、行の中身を判断基準にしない
という設計方針を貫いた）。この限界は
`dev-tools/docs/spec/issue-mr-workflow.md`の「未決定事項・懸念点」に記録した。

**`activeSeconds`のみ従来方式を維持した理由**: 本追記の冒頭で述べた通り、gapベースのidle検出・
tail buffer計算の単調非減少性が「毎回全件を時系列で走査し直す」ことを前提にしており、新規行
diffだけでは前回pushの「暫定クローズした末尾セグメント」を正しく補正できないリスクが大きいため、
`activeSeconds`の算出だけは既存の全件再パース＋スナップショット差分方式（`sessions[sessionId].
lastActiveSeconds`との差分、下限0）を変更せず維持した。1回のpushで「新規行diffの集計」と
「全件再パースによる`activeSeconds`算出」の両方を行うハイブリッド構成になった。

**`usage/`ディレクトリへの移設**: 本issue対応中、`session-logs`/状態ファイルが`.claude/`配下
（`.claude/session-logs/`, `.claude/usage-state/`）にあるのは、`.claude/`がAIエージェント自体の
設定・ルール置き場という性格が強く筋が悪いという指摘を受け、プロジェクトルート直下の新規
`usage/`ディレクトリ（`usage/session-logs/`, `usage/state/`）へ移設した。旧ディレクトリは
いずれもgitignore対象（git管理外）のため、過去の蓄積状態の移行は行わず単純に使わなくなる形で
対応した（本issueでスキーマ自体も刷新するため引き継ぐ意味が無いと判断）。

**併せて追加した詳細テーブル**: 同issueの受け入れ条件として、skill呼び出し（`skill`/`args`）・
Agent呼び出し（`subagentType`/`description`/`prompt`）・ユーザーへの質問（`question`/`answer`）の
3種の詳細テーブルも実装した。これらもメインセッションのtranscriptの新規行のみを対象とし、
上記の新規行diff方式と同じ枠組みで集計する。詳細は
`dev-tools/docs/spec/issue-mr-workflow.md`「呼び出し・質問の詳細記録」節を参照。

## 追記（issue #37 続き: PR #47マージ前に発覚したjq argv長制限バグの修正）

上記「追記（issue #37: 行オフセットベースの差分パースへ移行）」の実装をDraft解除しレビュー待ち
まで進めた直後、ユーザーから「MRに対応工数レポートが出なくなっている」という報告を受けた。
PR #47はまだsquash mergeされておらず、不具合を含むコードは一切mainへ反映されていなかったため、
新しいissueを起票せず同じissue #37 / PR #47のブランチ上で追加調査・修正した。

**原因**: 新規行diff方式の実装（`_usage_read_new_lines`で新規行をパース済みJSON配列として
シェル変数へ切り出し、`_usage_aggregate_new_lines`へ`--argjson entries "$new_entries"`という形で
コマンドライン引数として渡す2関数構成）が、実transcriptに対しては構造的に破綻していた。
transcriptの各行にはtool_use/tool_resultの生の入出力（Read/Bashの出力、Editの差分等）がそのまま
含まれるため、新規行がわずか32件（約120KB）程度でもこの引数が肥大化し、Windowsのプロセス生成時の
コマンドライン長上限（実測でおよそ32KB程度）を超えて`jq`の起動自体が`Argument list too long`
（終了コード126）で失敗した。呼び出し元は`set -euo pipefail`のため、これによりログ投稿処理全体が
即座に中断し、握りつぶされて投稿が止まっていた。この不具合は、issue本文レベルの設計判断
（セッション横断カーソル＋新規行diffという方針そのもの）ではなく、**その実装がデータをどう
受け渡すか**という一段低いレイヤーの問題であり、当初のPlanモードでの比較検討・レビューでは
気づけなかった（合成フィクスチャによるテストのみでは巨大なペイロードを再現していなかったため）。

**対応**: `_usage_read_new_lines`と`_usage_aggregate_new_lines`を1関数に統合し、
`_usage_aggregate_transcript`が既に採用している安全なパターン（`jq -R -n ... "$transcript_path"`で
ファイルパスを渡し、jqの`inputs`でファイル内容を読ませる。中身をシェル変数やコマンドライン引数
として運ばない）に統一した。stdoutへ返る値は集計済みの小さいオブジェクトのみであり、
transcriptがどれだけ大きくても影響を受けない。一般的な注意事項として
`.claude/rules/shell-script-style.md`「JSON操作」節に追記した。

**併せて見つかった2件の関連バグ**:

1. **userメッセージの`message.content`が配列でなく文字列の場合に例外になるバグ**:
   `_usage_aggregate_new_lines`のuserエントリ処理は`message.content`がcontent-blockの配列である
   ことを前提に`.[]`でイテレートしていたが、人間が直接入力したシンプルなテキストメッセージでは
   `message.content`が単一の文字列のまま格納されることが実データで確認された（このバグの調査
   自体がこの発見のきっかけになった。ユーザー自身の「レポートが出なくなっている」という
   報告メッセージがまさにこの形で記録されていた）。配列の場合のみ中身を返すjqヘルパー
   `content_blocks`を追加して修正した。この修正は本来のバグ（argv長制限）とは独立した問題だが、
   実transcriptで動作確認する過程で連鎖的に発覚したため同じ修正セッションで対応した。
2. **状態ファイルが破損すると恒久的に集計不能になるバグ**: 実際に手元の状態ファイル
   （`usage/state/<branch>.json`）が0バイトに壊れた状態で、カーソル（`session-cursors/
   <sessionId>.json`の`lastLineCount`）だけが正常に進んでいる状況を確認した（上記argv長制限
   バグにより、ある時点の実行が中途半端に失敗した結果と推測される）。壊れた状態ファイルは
   次回`_usage_merge_state`の`--argjson existing`へ渡ると不正なJSONとして必ず失敗するため、
   **一度この状態になると、根本原因（argv長制限）を修正した後もその状態ファイルがある限り
   投稿できなくなる**という構造的な弱さがあった。`sync_usage_state`が状態ファイルを読む箇所へ、
   内容が空でなく有効なJSONであることを検証し、無効なら「状態なし」の既定値へフォールバックする
   自己回復ロジックを追加した。

**教訓**: 「セッション横断カーソル＋新規行diff」という方式そのものの正しさと、その実装が
実データ（特にサイズ・データ構造の多様性）に対して安全かどうかは別の検証軸である。合成
フィクスチャによる単体テストは個々のロジック分岐の正しさを検証できるが、実データでしか
顕在化しない性質（ペイロードサイズ、`message.content`の型のゆらぎ等）を網羅するには限界がある。
本バグ修正では、実際に手元にある本セッション自身のtranscriptに対して修正後の関数を直接
呼び出して確認する、という実データベースの検証を行ったことで発見に至った。以降、同種の
transcript処理ロジックを変更する際は、合成フィクスチャのテストに加えて実データでの動作確認を
行うことが望ましい。

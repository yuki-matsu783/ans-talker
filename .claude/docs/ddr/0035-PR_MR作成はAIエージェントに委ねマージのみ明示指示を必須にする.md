# 0035. PR/MR作成はAIエージェントに委ねマージのみ明示指示を必須にする

## 背景

「PR/MRを誰が作るか」について、2つのAIアセットが**逆のことを言っていた**（issue #41）。

- `.claude/skills/issue-mr-flow/SKILL.md` の flow-id 1-3 は、`start` サブコマンドがDraft MRを
  作成する前提で書かれており、担当は「エージェント」だった。
- `.claude/rules/git-workflow.md`「PR・マージ」節は「PR作成・レビュー依頼・マージは人間が実施する。
  AIエージェントは…`gh pr create` / `gh pr merge` 等のPR作成・マージ操作は、ユーザーから明示的に
  指示されない限り実行しない」としていた。

実運用も揺れていた。issue #22 のセッションでは flow-id 1-3 の時点でDraft PR #30を作成した一方、
issue #34 のセッションでは `git-workflow.md` を根拠にPRを作成せずリモートへの反映までで止め、後から
ユーザーの明示指示を受けてPR #40を作成している。**同じフロー定義を読んでいるのに、セッションごとに
到達点が変わる**状態であり、フローの再現性が損なわれていた。

Claude Code on the web のリモート実行環境では、ハーネス（実行基盤）のシステムプロンプトにも
「ユーザーが明示的に依頼しない限りPRを作成しない」旨の指示があり、リポジトリ側の記述と合わさって
「作らない」方向へ倒れやすいという事情もあった。

## 決定

**PR/MRの作成・更新（description更新・レビュー依頼・レビュー返信・Draft解除）はAIエージェントが
実施してよい。マージのみ、ユーザーの明示指示を必須とする。**

線を引く基準は担当者の役割分担ではなく、**その操作が取り消せるかどうか**に置いた。

| 操作 | 取り消し方 | `main` への影響 | 担当 |
|---|---|---|---|
| Draft PR/MRの作成 | クローズする | 無し | AIエージェント |
| description更新・レビュー返信 | 書き直す | 無し | AIエージェント |
| Draft解除（flow-id 5-3） | Draftへ戻す | 無し | AIエージェント |
| **マージ（flow-id 5-4）** | **revert（履歴は残る）** | **`main` の正史が変わる** | **人間**（明示指示があればAIが実行してよい） |

PR/MRの作成は、レビューを**始めるための場**を用意する操作にすぎない。作った時点では `main` は
1バイトも変わらず、間違って作ってもクローズすれば元に戻る。Draft状態であればレビュアーへの
通知も発生しない。一方マージは `main` を書き換える不可逆な操作であり、このリポジトリはsquash
mergeを採るため、戻すにも元のコミット粒度が失われた状態からのrevertになる。**人間の承認を要求する
価値があるのは後者だけ**であり、前者にまで都度の指示を求めると、フローの各所で人間の応答待ちが
発生するわりに得られる安全性が無い。

### ハーネスの制限とリポジトリ方針が衝突する場合

**ハーネス側の指示を優先する。** リポジトリ内のドキュメントでハーネスのシステムプロンプトを
上書きすることはできない。「リポジトリのフロー定義に従うことがユーザーの明示的な依頼にあたる」と
解釈してリポジトリ方針を優先させることもできるが、それは衝突の解釈をAIに都度委ねることであり、
issue #41 が問題にした「セッションごとに判断が変わる」状態へ逆戻りする。

そのうえで、**優先した先の振る舞いを決め打ちにする**ことで再現性を確保した。再現性の要点は
「必ずPRを作ること」ではなく「毎回同じ判断に到達すること」にある。制限のある環境での flow-id 1-3 は
次のいずれかに必ず落ちる。

1. ブランチ作成とリモートへの反映までは通常どおり行う。
2. Draft PR/MR作成の直前に `AskUserQuestion` で可否を1回だけ確認する。承認されれば、以降は
   通常の flow-id 1-3 とまったく同じ手順で作成する。
3. 応答を待てない非対話的セッションでは、PRを作成せずに止め、**「PRを作成していないこと」
   「作成するには明示指示が必要なこと」を最終応答へ明示する**。黙ってリモートへ反映しただけで
   終わることはしない。

この確認が要るのはPRの**新規作成**だけである。flow-id 5-3（Draft解除）・`describe`・`reply` は
既存PRの更新であり、ハーネスの指示の対象外として扱う。

## 却下した案

- **従来どおりPR作成も人間に寄せる（`git-workflow.md` 側へ統一する）**: `start` サブコマンドが
  Draft MRの作成まで行う設計（`new_draft_merge_request`・空コミットでの自動リトライ・
  `get_mr_for_branch` を前提とする `comments` / `reply` / `describe`）と噛み合わない。
  フェーズ2以降のレビュー往復はMRが存在することを前提に組まれているため、PR作成を人間の手番に
  すると、フローの2ステップ目で必ず人間待ちが挟まる。機構の作りに逆らって規約側を通す形になる。
- **Draft解除（flow-id 5-3）も明示指示を必須にする**: Draft解除は「レビューしてよい状態にする」
  という意思表示であって、`main` は変わらず、いつでもDraftへ戻せる。flow-id 5-2 のコンフリクト
  検知を通過した直後という位置づけからも、AIが続けて実施するのが自然と判断した。なお flow-id 5-3
  でAIが止まること自体は変えていないため、「解除まで自動・マージは人間」という境界は保たれる。
- **マージもAIに委ね、`--auto`（auto-merge）等で承認後に自動実行する**: 承認とマージのタイミングを
  分離できる利点はあるが、`main` を変える操作をAIの判断で走らせることになり、上記の「取り消せるか」
  という基準と正面から衝突する。squash mergeで粒度が失われる本リポジトリでは特に戻しにくい。
- **ハーネスの制限がある環境ではリポジトリ方針を優先し、フロー定義への準拠を「明示的な依頼」と
  みなす**: 上記のとおり、衝突の解釈をAIに委ねる形になり再現性が戻らない。加えて、ハーネスの
  指示はユーザーが選んだ実行基盤側の設定であり、リポジトリ内の記述より後から与えられる
  文脈でもある。
- **ハーネスの制限がある環境では毎回PRを作らないと決める（確認もしない）**: 判断は決定的になるが、
  対話可能なセッションでも一律にPRを作らないことになり、Claude Code on the web からフローを
  最後まで回せなくなる。1回の `AskUserQuestion` で済む話に対して失うものが大きい。

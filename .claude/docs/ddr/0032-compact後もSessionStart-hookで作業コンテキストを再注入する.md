# 0032. compact後もSessionStart hookで作業コンテキストを再注入する

issue #57。

## 背景

`/compact`（および自動compact）は会話履歴を要約するが、**何を残すかを指定できない**。作業継続に
必須の「現在地」（どのブランチで何をしているか、issue/PRは何番か、次に何をするか）が要約の精度
次第で失われ、compact直後のエージェントが誤った前提で作業を再開する事故が起こりうる。

一方 `.claude/settings.json` の `hooks.SessionStart` matcherは `startup|resume|clear` であり、
`compact` は**意図的に外されていた**。理由は当時のspec（`issue-mr-workflow.md`）に
「コンテキスト圧縮のたびに `gh` API呼び出しが走るのを避ける」と記録されている。

## 決定

### 1. matcherへ `compact` を追加する

`"startup|resume|clear|compact"` とする。`fork` は引き続き対象外。

当初の除外理由（`gh` API呼び出しのコスト）は、以下の理由により**再注入の価値に見合わない**と
判断した。

- compactの発生頻度は高くない（`.claude/settings.json` の `autoCompactWindow` は600000）。
  1回のcompactあたり `gh` 呼び出しは数回で、レート制限に対して無視できる。
- issue #34以降、`gh`/`glab` CLIが無い実行環境ではそもそもAPI呼び出しが発生しない
  （`get_vcs_access_mode` が `mcp` を返し、ローカル情報のみを注入する経路になる）。
- 失うもの（compact後に現在地を失ったまま作業が続く）のコストが、API呼び出し数回より大きい。

`fork` を追加しないのは、fork時は親セッションのコンテキストがそのまま引き継がれ、要約による
情報欠落が起きないため（issue #34以前からのスコープ外判断を維持する）。

### 2. 注入対象へ「HANDOFF.mdの『次にやること』節」と「ブランチ固有の作業ファイル一覧」を加える

変更前のhookは「ブランチ／issue／PR／未解決レビューコメント件数」の4項目に絞っており、
`HANDOFF.md` の内容や `get_branch_work_files` の一覧は「`resume` の役割」として**意図的に
含めていなかった**（spec「セッション開始時の自動コンテキスト注入」に記録あり）。

compactを対象に加えたことで、この線引きの前提が変わる。`resume` は人間・エージェントが明示的に
呼ぶ必要があるが、**compactはセッションの途中で自動的に起こり、その直後に誰かが `resume` を
呼んでくれる保証が無い**。「compact直後でも作業を続けられる最小限」は hook 側が持つ必要がある。

**採用した範囲（ファイルの中身は原則注入しない）**:

| 対象 | 注入するもの | 注入しないもの |
|---|---|---|
| `HANDOFF.md` | 「## 次にやること」節のみ（見出し行を含み、次の `## ` の手前まで） | フロー進捗状況の表・やったこと・判断を迷った内容・未解決の内容 |
| `plans/` `worklog/` `reports/` | **ファイル名の一覧のみ**（`get_branch_work_files`） | ファイルの中身 |

「次にやること」節だけを採ったのは、`HANDOFF.md` の中で**compact後に即座に必要で、かつ短い**
唯一の節だからである。「やったこと」「判断を迷った内容」は履歴であり、必要になった時点で
エージェントがファイルを読めばよい。実際、本リポジトリの `HANDOFF.md` は全文で十数KBに達する
ことがあり、全文注入は毎セッション・毎compactで支払うコストとして過大である。

作業ファイルを**名前だけ**にしたのも同じ理由による。名前が分かれば必要なものだけを読める。

**この拡張はcompact時だけでなく、すべての起動要因（startup/resume/clear/compact）で行う。**
起動要因ごとに注入内容を変えると、hookの出力が「どの経路で起動したか」に依存して分岐し、
検証すべき組み合わせが増える。得られる節約（startup時のHANDOFF読み取り1回）に見合わない。

### 3. 注入量がしきい値を超えた場合は、切り詰めずに警告文のみを追記する

- **しきい値: 8000バイト**（`CONTEXT_SIZE_WARN_BYTES` 環境変数で上書き可能）。
- **判定はバイト数**で行う。日本語はUTF-8で1文字3バイトのため、文字数で測ると実際の注入量と
  3倍ずれる。
- 超過時は `additionalContext` の**末尾へ指示文を追記**する。指示文には実測バイト数・しきい値・
  整理すべきファイル（`HANDOFF.md`・`plans/`）を含め、エージェントがユーザーへ警告できる形にする。

**しきい値8000バイトの根拠**: 日本語ではおよそ2,600文字（≒2,600トークン）に相当する。本リポジトリ
での実測注入量は1,222バイト（issue #57 実装時、MCP経路・HANDOFF抜粋込み）であり、しきい値は
その約6.5倍にあたる。「通常運用では絶対に鳴らないが、HANDOFF.mdや作業計画が整理されないまま
数倍に膨らんだ状態は確実に検知する」水準として選んだ。厳密な最適値ではないため、環境変数で
上書きできるようにしてある。

**「警告のみ」を採り「切り詰め」を採らなかった理由**: 切り詰めは、この機構が守ろうとしている
情報そのもの（現在地）を失う可能性がある。しかも失ったことがエージェント側からは分からないため、
**部分的な情報を完全な情報と誤認して作業する**という、警告を出さない場合より悪い失敗モードを
生む。注入量が膨らむ原因（`HANDOFF.md`・`plans/` の肥大化）はいずれもユーザーが管理できる
ファイルであり、機械的に切り詰めるより人間に整理させるほうが根本的である。

なお「範囲を設計時に絞る」（上記2の決定）と「実行時に切り詰める」は別物である。前者は
**何を注入するかを事前に決める**ことで予測可能だが、後者は**注入する内容が入力サイズ次第で
変わる**。前者のみを採用した。

## 却下した案

- **`PreCompact` hookを使う**。compactの直前に発火するが `additionalContext` をサポートせず、
  標準出力もコンテキストへ注入されない（issue本文で確認済み）。この用途には使えない。
- **compact専用の別スクリプトを用意する**。注入内容が起動要因ごとに分岐し、二重管理になる。
  上記2のとおり、全起動要因で同じ内容を注入する方針を採った。
- **`HANDOFF.md` 全文を注入する**。compact後に最も確実だが、毎セッション十数KBを支払うことに
  なる。「次にやること」節＋「全体はHANDOFF.mdを読むこと」という誘導で代替できる。
- **`plans/【*.md` の中身を注入する**。個別作業計画は数KB規模になることがあり、しかも
  compact直後に全文が必要な場面は限られる。ファイル名の提示に留めた。
- **しきい値超過時に切り詰める（truncate）／切り詰めたうえで警告する**。上記3の理由により却下。
- **注入をキャッシュしてcompact時のAPI呼び出しを省く**。状態ファイルの鮮度管理という新しい
  複雑さを持ち込むわりに、節約できるのがcompact1回あたり数回のAPI呼び出しに過ぎない。
  上記1のとおり、そもそもコストが問題にならないと判断した。

## 実装上の副次的な決定

`session-start.sh` 自身を単体テスト可能にするため、本体処理を `main()` へ
移し、末尾で `[ "${BASH_SOURCE[0]}" = "${0}" ]` の場合のみ `main` を呼ぶ構造にした。変更前は
トップレベルで `raw="$(cat)"` を実行していたため、テストから `source` するとstdin待ちで
ハングし、純粋関数だけを取り出して検証できなかった。

ロジックを `.claude/hooks/lib/` へ切り出す案もあったが、`lib/` は
`.claude/rules/directory-structure.md` の定義上「**複数**hookスクリプトで使い回す共通ロジック」の
置き場であり、今回の関数は `session-start.sh` 専用である。source時ガードのほうが、ファイル数を
増やさずに同じテスト可能性を得られる。

## 適用範囲外

`.gemini/settings.json` の SessionStart matcher は `startup|resume|clear` のまま変更していない。
Gemini CLI が `compact` というmatcher値を解釈するかを実機で確認できていないためで、未検証の
設定値を持ち込んで既存の動いている設定を壊さないという
[0018-gemini-settings.jsonのhooksはレビュー提示スニペットのhooksセクションのみ採用する.md](0018-gemini-settings.jsonのhooksはレビュー提示スニペットのhooksセクションのみ採用する.md)
と同じ判断による。`session-start.sh` 自体は `.gemini/` から `.claude/` へのローカルリンクで共有され
ているため、注入内容の拡張・しきい値警告はGemini CLI側でもそのまま効く（起動要因が
`startup|resume|clear` に限られる点だけが異なる）。

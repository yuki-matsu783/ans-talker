# 0053. Gemini経路のブランチ帰属は断面時点のブランチとし限界を明示する

## 背景

Claude Code の transcript は、各 assistant メッセージに**実行時の `gitBranch` を記録している**。
`UsageTracking.sh` はこれで絞り込むことで、同一セッションが複数ブランチを跨いだ場合でも他ブランチ
分のトークンが混入しないようにしている。

Gemini CLI のセッションログには、これに相当するフィールドが無い（issue #97 フェーズ2の調査）。
メッセージ単位でブランチも作業ディレクトリも記録されない。

唯一近いのが1行目のメタデータにある `directories` だが、これは**セッション単位のプロジェクト
ディレクトリ**であって、ブランチでもメッセージ単位のcwdでもない。

## 決定

**差分は、その断面を取った時点の `git branch --show-current` のブランチへまとめて計上する。**
メッセージ単位でのブランチ判定は行わない。

**そのうえで、限界をレポート本文へ明示する。** Gemini経路のレポートには次の一文を出す。

> Gemini CLIのセッションログにはブランチ情報が無いため、1つのセッション内でブランチを
> 切り替えた場合、切り替え前の作業分もこのブランチの数値に含まれます。

## 理由

- **他に判定材料が無い。** ログに記録されていない情報は、どうやっても後から復元できない。
  推定（ファイルのタイムスタンプと `git reflog` の突き合わせ等）は、精度が保証できないうえに
  「推定である」ことがレポートから読み取れなくなるため、かえって危険である。
- **限界を明示すれば、数値の読み方を読み手が調整できる。** 対応工数レポートは
  「レビューの合否判定には使用しない」目安の指標であり、誤差の性質が分かっていれば実用に足りる。
  黙って不正確な数値を出すことと、限界を添えて出すことの差は大きい。
- **これは「二重計上」とは別の話である。** 帰属先がずれることは許容するが、**同じ範囲を2つの
  ブランチへ二重に載せることは許容しない**。後者は前回累計をブランチ非依存に持つことで防いで
  いる（DDR 0050）。この2つを混同すると、「どうせ帰属は不正確だから」という理由で二重計上を
  見逃すことになる。

## 却下した案

| 案 | 却下理由 |
|---|---|
| 1行目のメタデータの `directories` からブランチを判定する | `directories` はプロジェクトのディレクトリであってブランチではない。同じワークツリーで複数ブランチを切り替える通常の運用では、常に同じ値になり判別に使えない |
| Gemini経路ではブランチ帰属を諦め、レポートをブランチ非依存にする | 対応工数レポートはMR（＝ブランチ）へ投稿するものであり、ブランチという単位を外すと投稿先が決まらない |
| メッセージの `timestamp` と `git reflog` を突き合わせてブランチを推定する | reflog はローカルにしか無く保持期間も設定依存。推定が外れたときにレポート上で区別できない |
| Gemini CLI 本体へブランチ記録の追加を提案し、それまで対応を保留する | 外部プロジェクトの変更に依存すると、issue #97 がいつまでも完了しない。限界付きでも今出せる数値に価値がある |

## 影響

- `_sync_usage_state_gemini` は `sync_usage_state` の引数として渡されたブランチをそのまま使う
  （メッセージ単位の絞り込みを行わない）。
- `build_usage_report_body` が、Gemini経路のときだけ上記の注記を出す
  （判定は `sinceLastPush` が `models` キーを持つか）。
- 仕様: `.claude/docs/spec/issue-mr-workflow.md`「対応工数レポート」節。

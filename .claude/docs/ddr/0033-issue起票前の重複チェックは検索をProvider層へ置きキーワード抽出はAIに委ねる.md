# 0033. issue起票前の重複チェックは検索をProvider層へ置きキーワード抽出はAIに委ねる

## 背景

`issue-create` スキル（`.claude/scripts/src/create-issue.sh`）でAIエージェントがissueを代行
起票する際、既存issueとの重複を検知する手順が無かった（issue #68）。

人間がGitHub/GitLabのUIから起票する場合は入力中に類似issueがサジェストされるが、
`create-issue.sh` 経由のAI代行ではそれが働かない。結果として、**本来重複を作りにくいはずの
AI経路のほうが重複を作りやすい**構造になっていた。`Provider.sh` のissue関連関数も
`get_issue`（番号指定の単体取得）と `new_issue`（作成）だけで、一覧取得・検索に相当する
関数が無かった。

## 決定

### 1. キーワード抽出はAI（スキル側）が行い、bashへは実装しない

`Provider.sh` に置くのは「**与えられたキーワードで検索し、結果を正規化・統合する**」ところまでと
する。どの語で検索するかは `issue-create` スキルの手順としてAIエージェントが決める。

理由は2つある。

- **bashで日本語のキーワード抽出はできない。** 形態素解析器を持たない以上、文字種
  （ひらがな・カタカナ・漢字）による分割に頼ることになるが、bashの1文字取り出し
  （`${text:i:1}`）も文字クラス（`[[ $c == [ぁ-ん] ]]`）も**ロケール依存**であり、git bashで
  `LANG` がUTF-8でない環境ではバイト単位の動作になる。しかも失敗しても**エラーにならず、
  検索の再現率が静かに下がるだけ**で誰も気づけない。
- **AIのほうが適任である。** `issue-create` スキルでは、AIが直前に自分でタイトルと4見出しを
  組み立てている。そのissue固有の語がどれか（機能名・関数名・ファイル名）と、汎用語
  （「追加」「修正」）やリポジトリ全体に頻出する語（`issue`・`ワークフロー`）がどれかを、
  文脈から判断できるのはAI側だけである。

再現性は、スキル側に**選ぶ語／選ばない語の指針**を明記することで担保する。

この判断の結果、issue #68の受け入れ条件にある「キーワード抽出の単体テスト」は**存在しない**。
同条件が用意していた「またはテスト不要と判断した理由が記録されている」に該当するものとして、
本DDRがその記録である。bash側に残る純粋ロジック（プロバイダごとのJSON正規化・複数結果の統合）
には単体テストを付けた（`tests/test_vcs_provider.sh`、9件）。

### 2. キーワードごとに1回ずつ検索し、結果をOR的に統合する

GitHub/GitLabのissue検索はいずれも複数語を**AND条件**として扱う。キーワードを並べて1回で
検索すると、語が増えるほどヒットしなくなる。重複チェックで欲しいのは**再現率**（見落とさない
こと）なので、1語ずつ検索して `merge_issue_search_results` で `number` による重複排除を
行いながら統合する。

キーワード数は `SEARCH_ISSUES_MAX_KEYWORDS=5` を上限とし、超過分は切り捨てる。CLI起動
（＝ネットワークI/O）の回数を有界にするためだが、**切り捨てを無言で行わず標準エラーへ通知する**。

`.claude/rules/shell-script-style.md`「ループ内で `jq` 等の外部コマンドを呼ばない」に反する形
（最大5回のCLI起動）だが、同規約は1ファイルあたり数十回・ファイル数に比例して増える規模を
対象にしたものである。ここは上限5回で、各回が検索そのもの（ネットワークI/O）であり、
起動回数の削減は再現率を犠牲にしてしか達成できないため、再現率を優先した。

### 3. closedのissueも対象に含める

過去に見送られた提案が同じ内容で再提出されるのを検知するため（`gh issue list --state all` /
`glab issue list --all`）。「既にcloseされている」という情報自体が、起票するかどうかの判断材料に
なる。このため、共通形式の `state` を `open`/`closed` に正規化して必ず返す（GitHub CLIは
`OPEN`/`CLOSED`、GitLabは `opened`/`closed` を返すため、そのままでは呼び出し側が両方の
表記を知っていないと判定できない）。

### 4. 重複かどうかの最終判断は人間が行う

AIは候補を提示するに留め、重複と断定して起票を中止しない。スキルの「してはいけないこと」に
明記した。似ているだけで粒度・観点が異なる別issueであることは珍しくなく、**誤って中止した場合、
ユーザーはそもそも候補を見ていないので取り返しがつかない**（提示だけしておけば、ユーザーが
「これは重複だ」と判断してやめるコストは小さい）。誤りの非対称性から、候補があっても
`AskUserQuestion` で「新規に起票する／既存issueへコメントする／やめる」を選ばせる形にした。

## 却下した案

| 案 | 却下理由 |
|---|---|
| ひらがなを区切り文字として漢字・カタカナ列を語として切り出すbash実装 | ロケール依存（`${text:i:1}` がバイト単位になりうる）。失敗してもエラーにならず再現率が静かに下がる |
| bashの文字クラス（`[[ $c == [ぁ-ん] ]]`）による判定 | 同上（`LC_COLLATE` 依存で範囲の解釈が環境により変わる） |
| 汎用語のストップワードリストを持つ | リストの保守が必要なうえ、「そのissue固有の語か」はリポジトリの文脈に依存するため固定リストでは決まらない |
| 全キーワードを1回のAND検索で渡す | 語が増えるほどヒットしなくなり、重複チェックとして機能しない |
| `create-issue.sh` 側で重複を検知したら起票を中止する | 重複かどうかの判断を機械に委ねることになる（上記「決定」4の非対称性） |
| `gh search issues` を使う | `--repo` の指定とPRの除外が必要。`gh issue list --search` はカレントリポジトリに限定され、そもそもPRを含まないため、同じ結果をより少ない指定で得られる |
| チェックを `issue-mr-flow` の `start` サブコマンド側へ置く | ブランチを作る時点では既にissueが存在しており、重複を防げない。起票の直前でなければ意味がない |

## MCP経路との差

`gh`/`glab` CLIが無い環境（Claude Code on the webのリモート実行環境。DDR 0027）では
`mcp__github__search_issues` へ読み替える。このMCPツールは**自然言語のセマンティック検索**で、
既に `is:issue` にスコープされているため、CLI経路のようにキーワードごとに呼び分ける必要が無く、
1回の `query` に複数キーワードを平文で並べればよい。対応表は
`.claude/skills/issue-mr-flow/SKILL.md`「`gh`/`glab` CLI不在時のMCPフォールバック」節に追加した。

CLI経路とMCP経路で検索の仕組み（キーワード一致 対 セマンティック検索）が異なるため、
**同じ入力でも候補の並びが一致しない**。重複チェックは候補をユーザーへ提示するためのもので、
一致した件数や順序に依存した自動判断は行わないため、この差は許容している。

## 実機検証の状況

本対応はCLIが存在しない実行環境で行ったため、CLI経路（`gh issue list --search` /
`glab issue list --search`）は**未検証**である。検証できたのは次の範囲。

- `require_vcs_cli` が `search_issues` に対して `mcp__github__search_issues` を名指しした
  メッセージを出して失敗すること
- 正規化・統合の純粋関数が、CLI出力形式を模したフィクスチャに対して期待どおり動くこと
  （`tests/test_vcs_provider.sh` で `passed=53 failures=0`）

CLI経路の実機確認は、`gh`/`glab` が使える環境での次回作業時に行う（specの
「未決定事項・懸念点」に記録）。

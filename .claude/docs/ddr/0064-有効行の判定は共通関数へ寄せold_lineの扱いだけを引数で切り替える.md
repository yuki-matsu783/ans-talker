# 0064. 有効行の判定は共通関数へ寄せ `old_line` の扱いだけを引数で切り替える

## 背景

issue #6 で、`answer-talker` が「受講者の未変更ファイル」についての指摘を出すようになった。
ところが、その指摘は**投稿されなかった**。`add_mr_inline_comments` が投稿前に有効行で
ふるい分けており、diffに現れないファイルの指摘はすべてサマリへ回るためである。
**「指摘が出る」ことと「レビュアーに届く」ことは別だった。**

この過程でGitLab側にも有効行の判定が必要になったが、判定は
`github_filter_findings_by_valid_lines` としてGitHub固有の位置にしか無かった
（DDR 0047）。
判定そのもの（hunkヘッダから範囲を作り、`line` が範囲に入るかを見る）はプロバイダに依存しない。

**実装中に一度壊した。** 共通化にあたって「`old_line` を持つ指摘も通す」という分岐を
プロバイダ非依存の位置へ置いたところ、GitHub経路からも通ってしまい、`line: null` を含む
コメントを作った。**GitHubのレビュー投稿は原子的で、1件でも不正な行が混ざるとそのMRの
インライン投稿が全件失敗する。** worklogには「GitHub側は `old_line` を使っていないため無害」と
書いていたが、これは確かめずに書いた誤りで、エージェント定義は「削除行は `old_line` のみ」と
明示している——**例外ではなく通常運転で出る形**だった。

## 決定

1. **有効行の判定をプロバイダ非依存の共通関数へ引き上げる。**
   `valid_ranges_from_patches`（`[{path, patch}]` → 範囲マップ）と
   `filter_findings_by_valid_lines`（findings → `{postable, summary}`）を `Provider.sh` に置く。
   `github_filter_findings_by_valid_lines` は削除し、統合する。

2. **プロバイダ実装が担うのは「入力の正規化」だけにする。**
   `github_valid_ranges_from_files_json`（`pulls/<n>/files` の `.patch` から）と、新設した
   `gitlab_valid_ranges_from_diffs_json`（`diffs` の `.diff` から）が、どちらも
   `[{path, patch}]` へ揃えてから共通関数へ渡す。

3. **`old_line` だけを持つ指摘の扱いは、第2引数 `allow_old_line` で切り替える。**

   | `allow_old_line` | 呼び出し元 | 挙動 |
   |---|---|---|
   | `true` | GitLab | インラインへ通す。`position` は `old_line` だけで成立する。ただし新側の `line` が有効行に無ければ**その `line` を落とし**、`old_line` だけで位置を決めさせる（両方入れると `line_code` が不正になる） |
   | `false`（既定） | GitHub | 新側の有効行が決まらない限り**サマリへ回す** |

   **既定を `false`（安全側）にする。** 引数を渡し忘れた呼び出しは、指摘がサマリへ回るだけで
   済む。逆にしていたら、渡し忘れがGitHubのインライン投稿を全件落とす。

4. **共通化の対象は判定ロジックであって、判定の答えではない。** 範囲マップは新ファイル側しか
   持たないため `old_line` は原理的に判定できず、**「判定できないものをどちらへ倒すか」の
   答えがプロバイダで正反対**になる。ここが唯一の差なので、唯一の引数にする。

5. **DDR 0047 は無効化しない。** 0047 が決めたのは「位置指定は投稿直前にプロバイダごとの制約へ
   合わせて縮退させる」「findings のスキーマはプロバイダ非依存に保つ」という方針であり、
   本DDRはそれを**維持したまま実装の置き場所を変えた**ものである。0047 の本文が当時の関数名で
   書かれているのは point-in-time の記録として正しい。

## 却下した案

- **GitHubのロジックをGitLab側へ複製する。** 共通化せずに済み、GitHubを壊す危険も無い。
  しかしhunkヘッダの解析という同一のロジックが2箇所に増え、`@@ -a,b +c @@`（`d` 省略）や
  純粋な削除hunkの扱いといった**気づきにくい分岐が二重管理**になる。片方だけ直る形の
  不整合を将来必ず生む。
- **`old_line` を持つ指摘を、GitLabでも一律サマリへ回す。** 分岐が無くなり最も単純だが、
  GitLabは `old_line` だけでインラインを付けられる。**プロバイダの能力を、共通化のために
  低いほうへ揃える**ことになり、削除行への指摘が届かなくなる。
- **`old_line` を `side: "LEFT"` の `line` へ写像して共通に扱う。** GitHubのレビューAPIは
  `side` を持つため一見きれいに見えるが、旧ファイル側の有効行を求めるには範囲マップを
  もう1つ（旧側）持つ必要があり、判定の入力が倍になる。得られるのは「GitHubでも削除行へ
  付けられる」ことだが、それは issue #6 が必要としたものではない。
- **プロバイダ名を引数に取り、共通関数の中で分岐する。** `allow_old_line` の代わりに
  `provider` を渡す案。プロバイダが増えるたびに共通関数を編集することになり、
  「プロバイダ非依存」を名乗りながら中身がディスパッチャになる。**引数は差そのもの
  （`old_line` を許すか）を表すべき**だと判断した。

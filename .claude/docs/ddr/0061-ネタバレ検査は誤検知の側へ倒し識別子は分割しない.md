# 0061. ネタバレ検査は誤検知の側へ倒し識別子は分割しない

## 背景

issue #1。`answer-talker` の中核要件は「**正解を見て、正解を書かない**」ことである。
サブエージェントには出力規約（正解のコード片・正解にしか存在しない識別子を書かない）を課すが、
**規約だけでは構造の転記を防げない**。「A/B/Cの3つに分ける」のような書き方は、コード片を1文字も
含まないまま正解の構造をそのまま渡してしまう。

そこで投稿直前に機械的な検査を挟む二段構えとした。ここで決める必要があったのが、
**検査の粒度と、誤検知（正当な指摘を落とす）と見逃し（転記を通す）のどちらへ倒すか**である。

## 決定

**誤検知の側へ倒す。** 正当な指摘を落としてでも、転記の見逃しを避ける。
（この向き自体は flow-id 3-4 のレビューで合意された。）

禁止語の作り方は次のとおり。

```
禁止語 = 正解ソースの識別子 − 受講者diffに現れる語 − 除外語（定数） − 3文字以下
```

findings本文を `[^A-Za-z0-9_]` で区切ってトークン化し、禁止語と**完全一致**するものがあれば
その指摘を落とす。

- **識別子は分割しない。** `filter_lines` を `filter` / `lines` に割って照合しない。
- **落とした件数と反応した語を必ず返す**（`{"kept":N,"dropped":M,"drops":[{"title":…,"words":[…]}]}`）。
  スキル側はこれを**必ず報告する**。
- `kept` が0なら投稿しない（空のレビューを投稿しない）。

**報告を義務にしているのは、この向きの失敗の仕方が「静かな無害化」だからである。** 誤検知へ倒した
検査が壊れると、エラーにはならず「指摘が落ちすぎて実質何も出ない」という形になる。可視化しないと
「今回は指摘が無かった」と読めてしまい、検査が効きすぎていることに気づけない。

仕様の詳細は
[.claude/docs/spec/answer-talker.md](../spec/answer-talker.md)「ネタバレ検査」節を正とする。

## 却下した案

- **見逃しの側へ倒す**（疑わしきは通す）。指摘の質を保てるという利点がある。しかし本スキルの
  中核要件は「正解を漏らさない」ことであり、**漏れた瞬間にその演習の価値が失われる**。
  失われたものは取り戻せない（提出済みのレビューコメントは削除できない）。一方、誤検知で落ちた
  指摘は会話への報告として残り、講師が判断して手で伝え直せる。**取り返しのつく側へ倒す**のが
  正しい。

- **識別子を分割して照合する**（`filter_lines` → `filter` / `lines` も禁止語に含める）。
  見逃しは確かに減る。しかし分割された断片は**一般語そのもの**であり、`filter` `lines` `format`
  `read` といった語は概念的な指摘の本文にごく自然に現れる。誤検知が爆発し、実質すべての指摘が
  落ちる。「誤検知へ倒す」と「何も出ない」は別物であり、機構として成立しない。
  誤検知へ倒す判断は**見逃しを許さないための最低限**であって、誤検知を無制限に増やしてよいという
  意味ではない。

- **除外語リストを設定ファイルへ外出しする。** 課題ごとに調整できて柔軟に見える。しかし調整の
  必要が生じるのは「正当な指摘が落ちる」ときであり、それは**報告（`drops` の反応語）を見れば
  分かる**。設定ファイルを増やすと、置き場所・読み込み失敗時の挙動・他リポジトリへ持っていく
  ときの扱いが新たな検討事項になる。まずはスクリプト内の定数（`ATR_STOPWORDS`）として持ち、
  実運用で不足が見えてから外出しを検討すればよい。

- **正解ファイルの行と findings 本文を行単位で照合する**（識別子ではなく行の一致を見る）。
  コード片の丸写しは確実に捕まえられる。しかし本スキルが本当に防ぎたいのは**言い換えられた
  構造の転記**であり、行単位の一致では素通りする。逆に、概念的な指摘が正解の1行と偶然一致する
  ことはほぼ無いため、**捕まえたいものを捕まえられず、負荷だけが増える**。

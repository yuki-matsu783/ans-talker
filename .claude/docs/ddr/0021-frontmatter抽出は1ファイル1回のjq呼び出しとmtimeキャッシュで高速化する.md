# 0021. frontmatter抽出は1ファイル1回のjq呼び出しとmtimeキャッシュで高速化する

issue #11。仕様は [.claude/docs/spec/extract-frontmatter.md](../spec/extract-frontmatter.md) を参照。

## 背景

`.claude/scripts/src/extract-frontmatter.sh` のリポジトリルート一括実行（`extract-frontmatter.sh .`）
が2分でタイムアウトし完走しなかった。`.claude/rules/markdown-frontmatter.md` は「frontmatterを
更新したら再生成する」運用を定めているが、それが実質的に回せない状態だった。実際、コミット済みの
`index.jsonl` は陳腐化しており（削除済みファイルのエントリが残る、そもそも生成されていない
ディレクトリがある）、再生成が遅すぎることの帰結が観測できていた。

加えて、走査中に `index.jsonl` を直接truncateして1行ずつ追記していたため、**中断すると既存の
`index.jsonl` が不完全な状態で壊れた**（issue #9対応時に `.claude/docs/ddr/index.jsonl` が
18行→14行に破損）。

**原因は実測で特定した。git bash（MSYS）の外部プロセス起動が約95ms/回と重い**
（`jq -nc '1'` を50回実行して4.73秒 = 94.6ms/回）。旧実装はfrontmatterのキー・配列要素ごとに
`jq` を呼んでおり、1ファイルあたり約30回のプロセス起動が発生していた。
43ファイル × 約30回 × 95ms ≒ 2分となり、報告された症状と一致した。
**支配要因はアルゴリズムではなくプロセス起動回数**である。

## 決定

以下の3点を組み合わせて対処する。frontmatterの解析ロジック（行の正規表現・値の分類・`yq` 優先パス）
と `index.jsonl` の出力フォーマットは**一切変更しない**（「生成内容が現行実装と同一」が
issue #11 の受け入れ条件であるため）。

1. **jq呼び出しを1ファイル1回へ集約する。** 解析結果を中間表現（`種別 キー 値` の3要素を1組とする
   シェル配列）へ溜め、`jq --args` へ一度だけ渡して `reduce range(0; length; 3)` で畳み込む。
   `concept_id`/`directory`/`mtime` を含む最終行の組み立ても同じ呼び出しに統合する。
   引数長上限（実測でおよそ32KB）に達しうる場合は、一時ファイル＋`--rawfile` の経路へ自動的に
   フォールバックする。あわせて `realpath`・`dirname`・`date`・`stat`・`tr` の起動と、解析
   ホットパスのコマンド置換 `$(...)` も排除する（コマンド置換もサブシェルをforkするため同じコストを持つ）。
2. **mtimeキャッシュによる差分スキップ。** 既存 `index.jsonl` から `concept_id` → 行/mtime を読み、
   mtimeが一致する行はそのまま再利用する。`--force` で無効化できるほか、**スクリプト自身のmtimeが
   `index.jsonl` より新しい場合は自動的に無効化**する（解析ロジックを変えたのに古い行が残る事故の防止）。
3. **原子的更新。** 全走査の完了後に一時ファイルへ書き `mv -f` で差し替え、`trap ... EXIT INT TERM`
   で中断時の一時ファイルを削除する。内容が同一なら書き換えない。

結果: ルート指定が 136秒 → **9.6〜11.8秒**（全再生成）/ **1.5〜2.4秒**（差分なし）、
`.claude/docs/ddr` 単体が 46.4秒 → **3.0秒**。改修前の出力とバイト単位で完全一致することを
ゴールデンファイル比較で確認し、`SIGINT` による強制中断でも既存 `index.jsonl` がすべて
保持されることを実機で確認した。

## 却下した案

### 1. `yq` を必須の外部依存にする

`yq` があればフルYAML文法に対応でき、自前パーサーを捨てられて実装も単純になる。しかし、
「`yq` を新規の必須外部依存にはしない」という本スクリプト新設時からの方針を覆すことになり、
クローン直後に動かない環境が生まれる。**また、これは今回の問題を解決しない**: `yq` 経路でも
プロセス起動は1ファイルあたり1回までしか減らず、決定1と同じ水準にしかならない。
`yq` は引き続き「あれば使う」優先パスのままとする。

### 2. 全ファイルを1回のjq呼び出しで処理する

プロセス起動回数は理論上の最小（実行あたり1回）になる。しかし、frontmatterの行解析ロジックごと
jq側へ移植する必要があり、**「生成内容が現行実装と同一」という受け入れ条件に対して回帰リスクが
大きすぎる**。決定1の「1ファイル1回」でもルート約10秒・差分なし約2秒に到達しており、追加の
リスクに見合う改善幅が無い。

### 3. 純bashでJSONエスケープし `jq` を完全に排除する

プロセス起動を0回にできるが、制御文字・非ASCII・サロゲートペア等を含む**正しいJSONエスケープを
自前で保証する必要がある**。エスケープの誤りは「出力が現行実装と一致しない」という形で受け入れ条件を
直接破る。エスケープの正しさを外部実装（jq）に委ねられる価値の方が、残る数百ms〜数秒の短縮より大きい。

### 4. markdownが無くなったディレクトリの `index.jsonl` をスクリプトが自動削除する

`plans/*.md` を全削除した場合、`plans/index.jsonl` は「markdownが直下に存在するディレクトリ」と
いう出力対象の条件から外れ、陳腐化したまま残る。これをスクリプト側で自動削除する案は、
**スコープ外のファイルを消しうる**（誤ったディレクトリを指定した実行が破壊的になる）ため却下した。
`index.jsonl` の削除は運用手順側で担保する
（`.claude/skills/issue-mr-flow/SKILL.md` の flow-id 5-1）。

## 補足: 既知バグの結論

specの未決定事項にあった「対象を絞った個別実行がスコープ外のディレクトリの `index.jsonl` に影響し、
重複行が生じる」（issue #43）は、issue #11 の検証で**改修前・改修後のいずれでも再現しなかった**。
観測されていた差分の正体は「gitのcheckout/mergeによる `mtime` の更新」と「削除済みファイルの
陳腐化エントリの除去」であり、スコープ外への影響ではなかったと考えられる。詳細はspecの
未決定事項の該当項目を参照。

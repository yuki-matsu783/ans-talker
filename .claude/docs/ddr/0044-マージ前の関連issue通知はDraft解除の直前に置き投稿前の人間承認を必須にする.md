# 0044. マージ前の関連issue通知はDraft解除の直前に置き投稿前の人間承認を必須にする

## 背景

issue #86「マージ前に今回のMRが影響する関連issueを特定し通知するステップを追加する」。

MRがマージされても、その変更によって**前提が変わる・一部が解決される・記述が矛盾する**他のissueには
何も残らない。後続タスクの担当者は、着手して初めて「issueに書かれた現状がもう成立していない」ことに
気づく。このリポジトリは機構自身をissueで育てており、`.claude/skills/issue-mr-flow/SKILL.md` や
`Provider.sh` のように**多数のissueが同じファイルを対象にする**構造のため、この取りこぼしが起きやすい。

道具の面でも次の3つが欠けていた。

- **任意のissueへコメントする関数が無い。** `add_mr_comment` は宛先がPR/MRで、GitHub実装が
  `gh pr comment` のため他のissueへは投げられない。
- **差分を起点に影響先を探す手順が無い。** `search_issues`（issue #68）は起票前の重複チェック用に
  追加したもので、この用途は想定されていなかった。
- **フェーズ5（5-1〜5-4）に該当ステップが無い。**

## 決定

1. **フェーズ5へ flow-id 5-3「関連issueの特定・通知」を新設し、位置は 5-2（コンフリクト解消）と
   旧5-3（Draft解除）の間とする。** 旧5-3→5-4、旧5-4（マージ）→5-5へ繰り下げ、全40→41ステップ。
   issue #46 が 5-2 を挿入したときと同じ扱いである。
2. **投稿の前に `AskUserQuestion` で「投稿先issue」と「コメント本文」の承認を得る。承認なしに
   外部へ投稿しない。** 質問には本文そのものを含め、「投稿してよいか」だけを聞く形にしない。
3. **`Provider.sh` へ `add_issue_comment <issue番号> <bodyFile>` を新設する**（`add_mr_comment` の
   流用ではなく別関数）。本文はファイル経由とする。
4. **影響先が無ければスキップしてよい。** ただし「影響先なし」と判断した事実は `HANDOFF.md` へ残す。
5. **候補の特定は「AIがキーワード抽出 → `search_issues` で検索 → AIが3類型（前提が変わる／一部が
   解決される／記述が矛盾する）で判定」とする。** キーワード抽出をProvider層へ持ち込まない点は
   DDR 0033 の判断を踏襲する。

## 理由

### なぜDraft解除の直前（マージ前）なのか

- **通知の内容が確定するのが、この時点だから。** フェーズ2〜4は計画・実装・設計反映がレビュー往復で
  何度も書き換わる。途中で通知すると、その後の往復で内容が変わったときに**古い通知が相手のissueに
  残り続ける**。5-2を終えた時点の差分は、以降 5-4（Draft解除）・5-5（マージ）でしか変わらない。
- **5-1（片付け）より後に置く必要がある。** 5-1で `plans/` `worklog/` `reports/` を削除するため、
  通知の根拠を「マージされる差分」に一致させるには、その削除も含んだ状態で差分を見るのが正しい。
- **5-2（コンフリクト解消）より後に置く必要がある。** コンフリクト解消でdefaultブランチを取り込むと
  差分の内容が変わる。解消前に通知すると、通知した内容とマージされる内容がずれる。

### なぜ投稿前の人間承認を必須にするのか

- **他人のissueへの投稿は、このリポジトリの外側から見える副作用である。** PR/MRの作成・description
  更新・Draft解除は「取り消せる／`main` を変えない」ため都度の明示指示を不要とした（DDR 0035）が、
  他のissueへのコメントは**通知が飛んだ時点で相手の作業文脈に割り込む**。クローズしても既読は
  取り消せず、`main` を変えないという基準でも救えない。DDR 0035 の線引き（取り消せるか）を
  そのまま当てはめても承認側に倒れる。
- **誤検知のコストが非対称である。** 通知漏れは後続タスクが自力で気づけばよいが、無関係なissueへの
  誤通知が続くと、**通知そのものが読まれなくなる**。仕組みが自壊するのは後者だけである。
- **「影響がある」の判定は本質的にAIの解釈である。** `search_issues` はキーワード一致しか返さず、
  3類型のどれに当たるかは差分と相手のissue本文を突き合わせた解釈になる。解釈を人間が1回見る場所を
  設けておくことで、判定基準そのものを運用の中で調整できる。

### なぜ `add_mr_comment` を流用せず別関数にするのか

- GitHub実装が `gh pr comment` であり、**PR以外へは投げられない**。CLI経路では流用が物理的に不可能。
- MCP経路では両者とも `mcp__github__add_issue_comment` に収束するが、`issue_number` へ渡す値の意味が
  **PR番号か通知先issue番号か**で異なる。1つの関数名に2つの宛先を持たせると、MCPフォールバック対応表で
  この違いを表現できない。
- 既存の呼び出し元（`post-push-usage-report.sh` の対応工数レポート）の挙動を1バイトも変えずに済む。

## 却下した案

- **マージ後に通知する（マージイベントを起点にする）**: 通知内容が確定した後に投げられるため一見
  正しい。しかし本リポジトリはCIワークフローを持たず（DDR 0039の却下案と同じ理由）、マージ後は
  AIエージェントのセッションが既に終わっていることが多い。「マージしたら通知が飛ぶ」を成立させるには
  常時動く実行基盤が要り、issue #86 の範囲を大きく超える。**マージの直前は、セッションが確実に
  生きている最後の時点**である。

- **人間の承認なしに自動投稿する**: フローの固定費（`AskUserQuestion` 1回）が減る。しかし上記の
  とおり誤通知のコストが非対称で、しかも投稿は取り消しても既読を戻せない。DDR 0035 が明示指示を
  必須にしたマージと同じく、**不可逆性を持つ操作**として扱う。

- **専用サブコマンド（`/issue-mr-flow notify` 等）として実装する**: `start` / `comments` / `reply` /
  `describe` / `sync` / `resume` の6サブコマンドと並ぶ形になり、一見きれいに収まる。しかし
  サブコマンドは「フローの複数箇所から繰り返し呼ばれる操作」に与えてきた区分であり
  （`comments` は 2-4・2-9・3-4・3-9・4-4・4-9 から呼ばれる）、この通知は**フロー中で1回しか
  実行しない**。5-2（コンフリクト解消）が `resolve-conflict` スキルを呼ぶだけでサブコマンドを
  持たないのと同じ扱いに揃えた。

- **`add_mr_comment` を「宛先種別」引数付きに拡張する**（`add_mr_comment <n> <file> [issue|pr]`）:
  関数を増やさずに済む。しかし既存の全呼び出し元が第3引数を省略する形になり、**既定値がPRである
  ことを読み手が関数名から判断できない**（名前が `add_mr_comment` のままなので、issue宛の呼び出しが
  名前と矛盾する）。GitHub実装側では結局 `gh pr comment` と `gh issue comment` に分岐するため、
  実装量も減らない。

- **本文をコマンド引数で受け取る**（`add_issue_comment <n> "<本文>"`）: 一時ファイルの後始末が
  不要になる。しかし通知本文には差分の説明が入り、`git` と `push` が連続する語が地の文へ紛れ込むと
  push検知hookが誤発火する（`.claude/rules/git-workflow.md`「push検知hookの誤検知」で実際に3回
  発生している）。`set_mr_description` / `add_mr_comment` がファイル経由である理由と同じであり、
  同じインターフェースに揃える。

- **候補の特定を機械的に行う**（差分に含まれるファイルパスで `search_issues` を引き、ヒットした
  ものを全件通知する）: AIの解釈を挟まないぶん再現性が高い。しかし `.claude/skills/issue-mr-flow/
  SKILL.md` のように**ほぼ全issueが触るファイル**があり、パス一致では候補が絞れない。逆に日本語の
  概念語（「Draft解除」「対応工数」等）はパスに現れない。DDR 0033 が「日本語主体のissueから意味の
  ある語を選ぶには形態素解析が要る」としてキーワード抽出をAIへ委ねたのと同じ構造である。

- **通知先をopenのissueに限る**: closedのissueへ通知しても読まれないことが多く、候補が絞れる。
  しかし「その決定が今回の変更で覆る」ケース（`status: superseded` を付けるべきDDRの元issue等）を
  取りこぼす。`search_issues` が closed を含めて返す仕様（issue #68）をそのまま活かし、
  **絞り込みは3類型の判定と人間の承認に委ねる**。

# 0056. 作業開始時のベースブランチ追従確認は専用スクリプトで検知しユーザー確認を挟む

## 背景

issue #67「作業開始・再開時にベースブランチの最新を取り込めているか確認するステップをフローへ
追加する」。

featureブランチで作業を開始・再開する時点で、ベースブランチ（既定 `main`）の最新が取り込まれて
いるかを確認する手段が無かった。`sync_branch()`（`Provider.sh`）は `git fetch origin` と作業
ブランチの `pull --ff-only` のみで、ベースブランチとの差を見ない。実例として、issue #60 対応中の
セッションで、ローカルの `origin/main` が10コミット古いまま作業していた（未取得分に
`.claude/rules/shell-script-style.md` へのルール追記が含まれており、作業中のルール判断に
影響しうる状態だった）。

**「衝突しないこと」と「最新であること」は別である。** このリポジトリには既に、DDR 0029
（flow-id 5-2・issue #46）とDDR 0039（PR作成後の追従監視・issue #88）という2つの機構があるが、
どちらも判定軸が `hasConflict` である。ベースブランチ側でルール・仕様だけが追記された場合、
テキストコンフリクトもDDR番号の重複も起きないため、これらは偽のままになる。

## 決定

1. **専用の検知スクリプト `.claude/scripts/src/check-base-sync.sh` を新設する。** 作業ツリーを
   変更せず、判定結果のJSONを1つ出力するだけにする。
2. **取り込むかどうかは `AskUserQuestion` でユーザーへ確認する。AIエージェントは無断で
   マージ・リベースしない。**
3. **flow-idは増やさない。** `start`（既存ブランチ検出時）・`resume`・`sync` の手順の一部として
   `.claude/skills/issue-mr-flow/SKILL.md` に節を立てる。
4. **fetchの失敗を握りつぶさず、`fetchOk` として出力へ含める。**

仕様は `.claude/docs/spec/check-base-sync.md` が正。

## 却下した案

### 案A: `sync_branch()` を拡張し、ベースブランチを自動でマージする

追従漏れが構造的に起きなくなる点は魅力的だが、次の2点で却下した。

- **issueの受け入れ条件が「無断で取り込まないこと」を明示的に求めている。** 取り込みは作業ツリーと
  コミット履歴を変える操作であり、レビュー中のブランチで勝手に走ると、レビュアーが見ている差分が
  足元から変わる。
- `sync_branch` は `start` / `sync` / `resume` の3経路から呼ばれる**低レベル関数**であり、
  「ブランチを最新化する」という名前から想像できない副作用（ベースブランチのマージ）を
  持たせるべきではない。

### 案B: `check-base-conflicts.sh` へ behind 判定を相乗りさせる

新規ファイルが増えない点は利点だが、却下した。

- **判定軸が違う。** あちらの責務は「衝突するか」であり、出力JSONも `hasConflict` を頂点とする
  構造になっている。別軸のキー（`isBehind`）を足すと、**呼び出し側が `hasConflict` だけを見て
  安心する現在の使い方**と噛み合わず、「衝突は無い＝問題無い」という読み方が温存される。
- 実行タイミングも違う（あちらはマージ依頼の直前、こちらは作業の開始・再開時）。同じスクリプトに
  すると、どちらの目的で呼んでいるのかが呼び出し側から読み取れなくなる。

**3つの機構は代替関係ではなく補完関係**であり、判定軸ごとにスクリプトを分けたまま並べる形を採った。

### 案C: スクリプトを新設せず、SKILL.mdの手順へ `git rev-list` の1行を直書きする

最も軽い案で、`git rev-list --left-right --count origin/<base>...HEAD` の1行を手順書に書けば
behind の値そのものは得られる。却下した理由は次の2点。

- **判定の信頼性を手順書では表現しきれない。** `fetchOk` / `isShallow` / `hasCommonHistory` の
  3キーは、いずれも「その値をどう組み立てるか」に条件分岐を伴う。とりわけ merge-base の有無は、
  先に判定しておかないと3ドット記法のdiffが終了コード128で落ちる（`rev-list` の方は成功して
  しまうため気づけない）。手順書に書き下すと、実行するAIエージェントが毎回この分岐を再現する
  ことになり、再現性が落ちる。
- **このリポジトリの既定路線に反する。** `cleanup-task.sh`・`update-handoff-progress.sh`・
  `check-base-conflicts.sh` はいずれも「手順書に書くのではなくスクリプト化し、手順書からは
  呼ぶだけにする」形を採っている。スクリプト化すれば単体テストで退行を防げる。

## `fetchOk` を出す理由（`check-base-conflicts.sh` と揃えなかった点）

`check-base-conflicts.sh` は fetch を `git fetch origin "$base" >/dev/null 2>&1 || true` として
失敗を握りつぶしている。本スクリプトは**同じ形にしなかった**。

- あちらのコンフリクト検知は **flow-id 5-2 で必ずもう一度通る**ため、fetch漏れによる取りこぼしは
  後段で拾われる。
- 一方**本スクリプトは検知そのものが目的**であり、後段に同じ検知が無い。fetchに失敗して古い
  `origin/<base>` を読むと `isBehind: false` を返し、**呼び出し側からは「遅れていない」と
  区別がつかない**。誤検知の向きが安全側でない（遅れているのに0件と報告する）。
- そこで終了コードを `fetchOk` としてJSONへ出し、`isShallow` / `hasCommonHistory` と同じ
  「判定の信頼性を呼び出し側が識別できるようにする」枠で扱うことにした。`--no-fetch` 指定時は
  `false` ではなく `null` にして、「失敗した」と「そもそも試していない」を区別する。

この判断は、フェーズ2の敵対的レビュー（`.claude/skills/adversarial-review/SKILL.md`）の指摘に
よるものである。当初は「既存スクリプトと同じにする」としていた。

## flow-idを増やさない理由

DDR 0039（PR作成後のdefaultブランチ追従）と同じ扱いにした。追従確認は `start` / `resume` /
`sync` という**サブコマンドの手順の一部**であって、フローの新しい段ではない。flow-idを増やすと
`HANDOFF.md` の進捗表・`update-handoff-progress.sh` のループ範囲テーブル・各所のステップ数の
記述をすべて更新することになり、変更の規模が実態に合わない。

## 取り込み方に rebase を選択肢として出さない理由

遅れがあった場合の `AskUserQuestion` の選択肢は「merge して取り込む」「今は取り込まない」の
**2つに限り、`rebase で取り込む` は出さない**。`.claude/skills/resolve-conflict/SKILL.md` の
「絶対ルール」が「`git rebase` は使わない。`git merge` で取り込む」と無条件に定めており、
作業ブランチは既にリモートへ反映済みであるため履歴の書き換えは他の作業者のチェックアウトと
MR上の参照リンクを壊す。

**当初は「非推奨」と注記したうえで3つ目の選択肢として並べる設計にしていたが、これは採らなかった。**
選択肢に並んでいる時点で選べてしまい、選ばれた場合にAIエージェントは「ユーザーが明示的に選んだ」
という理由で、常時適用ルール（`.claude/rules/git-workflow.md`）が禁じている操作を実行することに
なる。どちらを優先するかがどこにも書かれておらず、判断がセッションごとにぶれる
（この機構が issue #41 等でくり返し避けてきた形である）。フェーズ3・フェーズ4の敵対的レビューで
同じ指摘が独立に挙がったため、選択肢そのものを落とし、理由は地の文の注記として残す形へ改めた。

なお、issue #67 の対応中に **`.claude/rules/` 配下には `rebase` の語が1件も無い**ことが分かった
（方針を書いていたのは `resolve-conflict` スキルだけだった）。同じ作業で
`.claude/rules/git-workflow.md` へも方針を1行置いた。

## 影響

- `.claude/skills/issue-mr-flow/SKILL.md` に「作業開始・再開時のベースブランチ追従確認」節が増え、
  `start` / `resume` / `sync` から参照される。
- `.claude/agents/issue-mr-resume.md` の現在地サマリに「ベースブランチとの差分」が加わる。
  同エージェントは**検知結果の報告のみ**を行い、確認・取り込みは呼び出し元の役割とする。
- `Provider.sh` は変更しない。

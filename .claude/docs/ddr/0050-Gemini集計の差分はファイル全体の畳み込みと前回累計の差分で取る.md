# 0050. Gemini集計の差分はファイル全体の畳み込みと前回累計の差分で取る

## 背景

issue #97 で、Gemini CLIのセッションログ（`~/.gemini/tmp/<hash>/chats/*.jsonl`）を対応工数
レポートの集計対象に加えることになった。

Claude Code の transcript に対しては、issue #37 で確立した**行カーソル方式**を使っている
（`usage/state/session-cursors/<sessionId>.json` の `lastLineCount` 以降の新規行だけを集計し、
一度数えた範囲は二度と数え直さない）。同じ追記型JSONLなので同じ方式が使えそうに見える。

しかし調査（issue #97 フェーズ2）で、Gemini CLI v0.39.0 以降のセッションログには次の性質が
あることが確認された。

- **同じ `id` のメッセージが複数行にわたって再送される**（トークンの後埋め、ツールの `status`
  遷移）。
- `{"$set": {...}}` レコードが `messages` を含む場合、**全メッセージがまとめて再送される**。
- `{"$rewindTo": "<messageId>"}` レコードが `/rewind` の記録として現れる。

## 決定

**毎回ファイル全体を `id` 単位で畳み込んで累計スナップショットを作り、状態が持つ前回累計との
差分を計上する。** 行カーソル（`lastLineCount`）は差分計算に使わない。

あわせて次の3つを決めた。

| 項目 | 決定 |
|---|---|
| 前回累計の置き場所 | **`usage/state/gemini-totals/<sessionId>.json`（ブランチ非依存）** |
| セッションログの消失・縮小 | 1指標でも差分が負なら `needsReset` を立て、前回累計を今回のスナップショットで**必ず**上書きする。負値は0へクランプするので `sinceLastPush` は減らない |
| 早期リターンの判定 | **クランプ前（raw）の差分**がすべて0のときだけ状態を書かずに返す（`diffAllZero`）。`needsReset` が立っているときは早期リターンしない |
| `_usage_append_push_index` | **Gemini経路では呼ばない** |

## 理由

### 行カーソル方式は二重計上する

行カーソルが成立するのは「N行目までを数えた」という事実が「その内容を数えた」と同義である
場合に限る。Gemini CLIのログでは同じメッセージが後の行で再送されるため、**新しい行を足すと
同じメッセージのトークン・ツール実行を何度も数える**。issue #97 の受け入れ条件
「同じ範囲を二重計上しない」に真っ向から反する。

畳み込み方式なら、何行増えていようと畳み込み後の状態は「そのセッションの現在の累計」に収束
するため、差分は常に正しい増分になる。

### 前回累計をブランチ別の状態ファイルに置くと、issue #37 の不具合を作り直す

当初の設計では前回累計を `usage/state/<safeBranch>.json` の
`sessions[<sessionId>].lastGeminiTotals` に置いていた。これは敵対的レビューで指摘されて改めた。

同じセッションのままブランチAで数回断面を取り、その後ブランチBで初めて断面を取ると、Bの状態
ファイルには当該sessionIdの前回累計が存在しない。差分＝スナップショット全量となり、**Aで計上
済みの範囲がまるごとBの初回差分として再計上される**。これは issue #37 が
「セッションが新しいブランチで初めてpushされた際に前回スナップショットが存在せず、蓄積済みの
全件がその新ブランチの初回差分として計上されてしまう不具合」として記録し、カーソルを
セッション単位へグローバル化することで直した問題そのものである。

ブランチ帰属の不正確さ（0053 で扱う）は許容するが、**同じ範囲を2つのブランチへ二重に載せる
ことは許容しない**。この2つは別の話である。

### クランプ後の差分で早期リターンを判定すると、消失時に計上が永久に止まる

セッションファイルが消失・作り直しで縮小した直後は、**全指標の差分が負→クランプ後すべて0**に
なる。「差分がすべて0なら書かずに返す」を**クランプ後**の値で判定すると、この経路が引っかかり、
前回累計が古い（大きい）値のまま残る。以後、新しいセッションの累計が旧累計を超えるまで毎回
「差分0・書き込みなし」が続き、Gemini分の工数が無言で欠落し続ける。

`needsReset` と `diffAllZero` を**クランプ前の差分**から求め、両者を排他にすることでこれを
避けている。

### `push-index.jsonl` の `from`/`to` は行番号としての意味を失う

`_usage_append_push_index` が記録する `main: {from, to}` は「空行を除いた行番号の範囲」であり、
「この範囲を今回数えた」という意味を持つ。Gemini経路では行番号が「まだ数えていない量」を表さ
ないため、同じキーへ別の意味の値（畳み込み後のメッセージ数など）を入れると、`push-index.jsonl`
を読む側が両者を区別できない。**意味を保てないなら記録しない**方を選んだ。

## 却下した案

| 案 | 却下理由 |
|---|---|
| Claude Code と同じ行カーソル方式を使う | 同一idの再送により二重計上する（上記） |
| 計上済みの `id` の集合を状態に持ち、未計上のidだけ足す | id集合はセッションが伸びるほど際限なく肥大化し、状態ファイルへ書き戻すコストも増える。畳み込みなら状態は指標ごとの数値だけで済む |
| 前回累計を `usage/state/<branch>.json` に持つ | ブランチ切り替えで全累計を再計上する（上記） |
| 前回累計を既存の `session-cursors/<sessionId>.json` へ相乗りさせる | あのファイルは `lastLineCount`（行カーソル）の置き場であり、本DDRで「使わない」と決めた対象そのもの。同じファイルに別の意味の値を同居させると、読み手が「結局カーソルを使っているのか」と誤読する |
| 切り詰め（ログの部分的な削除）に個別対応する | 畳み込み方式は本質的に耐性を持つ（累計が一致すれば差分0）。負値による消失検知だけで足りる |
| `push-index.jsonl` へ「畳み込み後のメッセージ数」を `from`/`to` として記録する | キーの意味が経路によって変わり、読む側が区別できない |

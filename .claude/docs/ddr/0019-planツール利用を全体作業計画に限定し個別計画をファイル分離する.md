# 0019. planツールの利用を全体作業計画に限定し、個別作業計画はファイル分離する

## 背景

issue #9 で「planツールの利用箇所がまちまちで挙動が安定しない」という課題が報告された。実際、
計画の作られ方に3系統が混在していた。

- planツールで計画を立てる（ハーネスが提示するパスへ書く）
- `plans/` 配下に新しい計画ファイルを直接作る
- planツールで作成したファイルを後から `Edit` で更新する

根本原因は、**Claude Code / Gemini CLI がセッションごとに1つのplanファイルしか割り当てない**仕様に
対し、当時の33ステップフローが flow-id 4（調査計画）と flow-id 15（作業計画）の**2回**Planモードを
使う設計だったこと。この構造的衝突に対し、これまでは回避策を積み増してきた
（`plan-mode-safety.md` 規則6、`archive-reentrant-plan.sh`、[DDR 0009](0009-Planモードre-entry時はgit checkout復元でなくarchiveスクリプトで対処する.md)）。

## 決定

**planツールの利用を「全体作業計画」の作成のみに限定し、以降のフェーズ別計画は
`plans/【種別】タスク内容.md` という個別ファイルへ分離する。**

| 種類 | 作り方 | ファイル名 | 単位 |
|---|---|---|---|
| **全体作業計画** | planツール（Planモード） | ハーネス提示パス `plans/<自動命名>.md` | **issue（ブランチ）につき1回** |
| **個別作業計画** | **planツールを使わない**（Write/Edit） | `plans/【種別】タスク内容.md` | フェーズごと |

- タスク種別は `【調査】` `【設計】` `【実装】` `【テスト】` `【設計反映】` `【AIアセット改善】`
  の6種。複数併記を認め、併記するか分けるかは「合意を1回で取るか、フェーズごとに分けて取るか」で
  判断する（迷ったら分ける）。
- 全体フローは33→**35ステップ**（先頭に全体作業計画の作成・合意を追加し、旧flow-id N≧4 を
  新N+2 へスライド）。
- worklogは `日付_<全体計画名>_<個別計画名>_push<N>.md`、reportsは
  `日付_<全体計画名>_<内容を簡潔に>.html` へ命名変更。reportsは調査結果専用ではなく、設計・実装・
  AIアセット反映等の報告にも使える位置づけへ拡張した（将来の拡張性を持たせるため）。

### 「セッションにつき1回」ではなく「issue（ブランチ）につき1回」とした理由

当初は「planツールはセッション冒頭の1回のみ」と考えたが、**新しいセッションではハーネスが新しい
planファイルパスを提示する**ため、この規定ではセッションを跨ぐたびに全体作業計画が増えてしまう。
そこで判定基準を「**現在のブランチに既に全体作業計画があればPlanモードを利用しない**」とした。
既存の有無は `get_branch_work_files` の結果から機械的に判定できる（`plans/【*.md` に一致しない
ものが全体作業計画）。`.claude/settings.json` の `"defaultMode": "plan"` により新セッションは必ず
Planモードで始まるが、それは新規作成の理由にならない旨も明記した。

### 囲み文字にASCIIの `[]` ではなく全角 `【】` を採用した理由

issue本文では `[タスク種別]タスク内容.md` と提案されていたが、実機検証の結果、**ASCIIの角括弧は
bashのglobで文字クラスとして解釈される**ことが分かった。

| パターン | 結果 |
|---|---|
| `plans/[調査]*.md`（未クォート） | ❌ マッチせず、パターン文字列がそのまま返る |
| `plans/【調査】*.md`（未クォート） | ✅ 正常にマッチ |
| `plans/*【テスト】*.md`（併記中の種別） | ✅ 正常にマッチ |
| `plans/【*.md`（個別計画のみ抽出） | ✅ 全体作業計画と機械的に区別できる |

全角文字はglob特殊文字ではないため、**クォート忘れという落とし穴自体が構造的に消える**。
PR #10 のレビューでこの方針が採用された。`（）`（全角丸括弧）も同様に動作するが、文中の補足表現
としても使われるため種別ラベルとしての識別性が劣ると判断し `【】` を採用した。

## DDR 0009（re-entry対策）を廃止した経緯

DDR 0009 が定めた `archive-reentrant-plan.sh` による退避方式と、`plan-mode-safety.md` 規則6を
廃止した（スクリプトは削除。DDR 0009 の本文は不変のまま残す）。

判断の根拠は2つある。

1. **planツールの利用が1回に限定されたことで、同一セッションで別々の計画をplanツールで作る場面
   自体が無くなった。** 回避策が対象としていた状況が発生しない。
2. **調査により、そもそも現行フローでこの制約が実害になっていなかったことが判明した。**
   DDR 0014相当のissue #43（移植元のDDR 0002。本テンプレートには未同梱） 以降、「調査計画・調査結果・
   作業計画は別ファイルに分けず既存の `plans/<plan名>.md` に章立てで含める」運用になっていたため、
   flow-id 4 と 15 は**そもそも同じファイルへの追記**であり、ハーネス提示パスと追記先が一致していた。
   `archive-reentrant-plan.sh` が本当に必要なのは「同一セッションで**別タスク**の計画を新規に立てる」
   場合に限られていた。

なお、**「ハーネスが再突入時に同じパスを提示し続ける」という DDR 0009 の観測自体は、issue #9 の
調査時点でも有効であることを実地確認済み**である（本対応のセッションで2回目の `EnterPlanMode` を
実行し、1回目と同じパスが提示されることを確認した）。本決定はこの制約を回避するのではなく、
**制約に触れない運用へ変えた**ものである。

### 付随して定めた運用: DDRのfrontmatterは後から更新してよい

DDR 0009 を廃止するにあたり、「DDRは一度マージしたら変更しない」という運用のままでは、**0009
自体を直接開いた人が、その決定が既に無効であることに気づけない**という問題が浮かんだ
（`.claude/docs/README.md` の一覧に注記を足しても、ファイルを直接参照した場合には目に入らない）。

そこで **DDRの本文は従来どおり不変とする一方、YAML frontmatterのみは後から更新してよい**ことにした。

```yaml
status: superseded
superseded_by: "0019"
```

- `status` の値は `superseded`（後続DDRで置き換え）/ `deprecated`（置き換え先なく廃止）とし、
  有効なDDRにはキー自体を書かない。**`disabled` のような独自語彙ではなくADRで一般的な語彙を
  採用した**（読み手が初見でも意味を推測でき、外部ツールとも揃うため）。
- **`description` は書き換えない**。`description` は「そのDDRが何を決めたか」の要約であり、
  `index.jsonl` を通じて一覧・検索から参照される。無効化の情報で上書きすると元の決定内容が
  読み取れなくなるため、無効化の事実は専用キーで表現して両方の情報を残す。
- frontmatterは `extract-frontmatter.sh` により `index.jsonl` へ取り込まれるため、この方式なら
  **AIエージェントが機械的に「このDDRは無効」と判別できる**。

規約は `.claude/rules/markdown-frontmatter.md`「DDRのstatus」、運用は
`.claude/rules/docs-workflow.md` のドキュメント運用表に記載した。

## 付随して修正した既存バグ（`core.quotepath`）

日本語を含むファイル名を導入するにあたり、**`get_branch_work_files`（`Provider.sh`）が
`core.quotepath` に未対応**であることが判明した。gitは既定（`core.quotepath=true`）で非ASCII文字を
含むパスを8進エスケープ＋ダブルクォートで出力するため、そのままでは戻り値が人間にもスクリプトにも
使えない文字列になり、`resume` / `issue-mr-resume` が機能しなくなる。

```
"plans/\343\200\220\350\252\277\346\237\273\343\200\221検証用ダミー.md"   ← 既定
plans/【調査】検証用ダミー.md                                            ← -c core.quotepath=false
```

`git diff --name-only` / `git status --porcelain` に `-c core.quotepath=false` を追加して解消した。
なお `git ls-files -z` のようなNUL区切り出力は元から影響を受けない（`extract-frontmatter.sh` が
その実装例であり、同一リポジトリ内に安全な前例があった）。

## 却下した案

- **個別作業計画を `plans/` とは別のディレクトリ（例 `plans/tasks/`）へ置く**:
  ハーネスが自動生成するファイルと同居させない案。`plans/【*.md` というglobで機械的に区別できる
  ことが実機検証で確認できたため、ディレクトリを分ける必要はないと判断した。ディレクトリを増やすと
  `.mrworkflow.json`・`get_branch_work_files`・`.gitignore` 等への波及が増える。
- **全体作業計画を承認後に固定名のファイルへコピー／リネームする**:
  ハーネス提示パスを使い捨てにする案。issue #9 が問題視した「planツールで作成したファイルを後から
  Editで更新する」という混乱を別の形で持ち込むことになるため見送った。
- **worklog / reports を個別計画ごとに分ける**: 追跡性は上がるが、worklogは「push単位」の記録で
  あり個別計画とは粒度が異なる。命名に全体計画名と個別計画名の両方を含める形
  （`日付_<全体計画名>_<個別計画名>_push<N>.md`）で、どちらの単位からも辿れるようにした。

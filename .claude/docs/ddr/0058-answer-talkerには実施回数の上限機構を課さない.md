# 0058. answer-talkerには実施回数の上限機構を課さない

## 背景

issue #1。`answer-talker` は `adversarial-review` と多くを共有する（専任サブエージェント・
findings JSONスキーマ・確度×重大度の選別表・`add_mr_inline_comments` による投稿）。
そこで「どこまでを共通化し、どこから固有にするか」を決める必要があり、その最大の論点が
**実施回数の上限機構**（`.claude/scripts/src/adversarial-review-count.sh`。各フェーズ最大3回を
機械的に強制する）を `answer-talker` にも課すかであった。

素朴に考えれば、同じくAIがMRへコメントを投稿する機構なのだから同じ歯止めを掛けるべきに見える。

## 決定

**課さない。** 上限機構は `adversarial-review` 固有のものとして残し、`answer-talker` からは
呼び出さない。

上限が存在する理由は「同じ機構だから」ではなく、**非対話モードでAIが人間の介在なくレビュー →
修正 → 再レビューを回しうる**ことへの対策である。`answer-talker` はその前提を満たさない。

- **人間が引数付きで明示的に呼ぶ。** `/answer-talker <MR番号> --reference <正解の場所>` は、
  MR番号と正解ソースの場所という**人間しか知らない情報**を要求する。AIが自律的にループを
  回せる形になっていない。
- **`issue-mr-flow` のフェーズ番号を持たない。** 上限は「各フェーズ最大3回」という単位で
  数えるが、`answer-talker` はフローに載らない（flow-idを1つも増やさない）。数える単位が無い。
- **対象が実行者のブランチと無関係である。** 上限のカウントはブランチ単位の状態として保持される
  が、`answer-talker` は引数で受けた他人のMR（別リポジトリでもよい）を対象にする。
  **実行者のブランチ状態と対象MRが結びつかない**ため、カウントを置く場所そのものが無い。

埋め尽くしへの歯止めは、別の2つで担保する。

- **投稿前の承認1回**（`AskUserQuestion`）。レビューを実行する前に人間が1回だけ許可する。
- **1回あたりの投稿上限10件**。超える場合は重大度の高い順に10件へ絞り、残りは会話での報告へ回す。
  受講者が一度に扱える量を超えると、結局どれも読まれないため。

仕様の詳細は
[.claude/docs/spec/answer-talker.md](../spec/answer-talker.md)「投稿の選別と上限」「承認モデル」節を正とする。

## 却下した案

- **`adversarial-review-count.sh` をそのまま流用し、`answer-talker` にも各フェーズ最大3回を
  課す。** 一貫性という点では魅力があり、変更も小さい。しかし上記のとおり**カウントの単位
  （フェーズ）とカウントの置き場所（ブランチ）がどちらも成立しない**。無理に成立させようとすると、
  「実行者のブランチに、対象MRとは無関係なカウンタが溜まる」という意味の無い状態が生まれる。
  さらに実害として、**同じ演習で複数の受講者のMRを続けてレビューすると3人目で止まる**。
  歯止めとして機能する前に、正当な用途を阻害する。

- **対象MRごとにカウントする新しい上限機構を作る**（ブランチ単位ではなくMR単位で数える）。
  カウントの置き場所の問題は解ける。しかし演習では、受講者が修正してからもう一度レビューを
  依頼する往復が**正常な使い方**であり、そこに上限を設ける理由が無い。上限は「AIが暴走しうる」
  経路を塞ぐためのものであって、人間が明示的に呼ぶ回数を制限するためのものではない。
  機構を増やす分だけ、状態ファイルの置き場所・後片付け・他リポジトリを対象にしたときの
  振る舞いといった検討事項が増える。

- **上限を設けない代わりに、投稿件数の上限（10件）も外す。** 承認が1回ある以上、件数は人間が
  見て判断すればよいという考え方。しかし承認はレビュー**実行前**に行うため、承認の時点では
  何件出るか分からない。件数の上限は承認とは別の役割（受講者が読める量に収める）を持つので、
  どちらか一方では代替できない。

# 0047. インラインコメントの位置指定はプロバイダごとの制約に合わせて縮退させる

## 背景

issue #77 のフェーズ2（調査）とフェーズ3の実機検証で判明した制約に対する決定である。
flow-id 4-3のレビューで「実機で試さないと分からない制約であり、仕様の記述だけでは
『なぜこう実装したか』が後から読み取れない」として、DDRへ残すことになった。

敵対的レビューは指摘（findings）をMRのインラインコメントとして投稿する。ところが「どの行へ
付けられるか」はプロバイダごとに強い制約があり、**findings をそのままAPIへ渡すことはできない**。

- **GitHubのレビュー投稿はアトミックである。** `pulls/<n>/reviews` へ `comments[]` を渡す形は、
  1件でも不正な行を指定すると**レビュー全体が422で失敗する**。部分的な成功は無い。
  コメントを付けられるのは `pulls/<n>/files` の `.patch` のhunkヘッダ `@@ -a,b +c,d @@` が示す
  新ファイル側の範囲内（追加行・コンテキスト行）に限られる。
- **提出済みのGitHubレビューは削除できない**（個々のコメントは削除できる）。
- **GitLabの `discussions` は、行の種類ごとに指定するキーが決まっている。** 追加行は `new_line`
  のみ、削除行は `old_line` のみ、コンテキスト行は両方。違反すると
  `400 Bad request - Note {:line_code=>["must be a valid line code"]}` になる。
- 敵対的レビューでは、**特定の行を指せない指摘**（設計の一貫性・命名・観点の漏れ・テストの欠落
  など、ファイル全体にかかるもの）が一定の割合を占める。

フェーズ2のレビュー（flow-id 2-9）では「ファイル単位の指摘は1行目に書けばよい」と合意していたが、
**既存ファイルの部分変更では1行目がdiffに含まれない**ため、そのままでは成立しなかった。

## 決定

1. **位置指定は、投稿の直前にプロバイダごとの制約へ合わせて縮退させる。** findings のスキーマは
   プロバイダ非依存のまま（`path` / `line` / `old_line` / `old_path` / `side`）とし、変換は
   `github_filter_findings_by_valid_lines` / `gitlab_build_discussion_body` が担う。呼び出し側
   （スキル・サブエージェント）にプロバイダ差を意識させない。

2. **GitHubの有効行は、hunkヘッダから「範囲」（`[開始, 終了]`）として求める。** 行を1つずつ
   列挙しないのは、jqへ渡すデータ量を差分の大きさではなく hunk 数に比例させるため
   （`.claude/rules/shell-script-style.md`「大きなJSONを `--argjson` 等でjqへ渡さない」）。
   `d` を省略した `@@ -a,b +c @@` は1行、純粋な削除hunk（`d` が0）は新ファイル側に行を持たない
   ため除外する。

3. **`line` を持たない finding は、そのファイルの有効行の最小値へ寄せる。** 新規追加ファイルは
   hunkが `@@ -0,0 +1,N @@` になるため、これは1行目に一致する。「1行目」という当初の合意を、
   「既存ファイルの部分変更では1行目がdiffに無い」という制約に合わせて一般化したものである。

4. **有効行を持たないファイル（diffに現れない・`patch` が省略された）の指摘は、レビュー本文
   （サマリ）へ回す。** これは特別扱いのコードではなく、有効行の集合が空であることから自動的に
   そうなる。戻り値 `{"posted":N,"summarized":M}` で件数を返す。

5. **GitLabは行の種類ごとにキーを出し分ける。** `line` があれば `new_line`、`old_line` があれば
   `old_line` を付け、両方あれば両方付ける。`old_path` / `new_path` はGitLabが常に要求するため、
   片方しか無い場合は同じ値で埋める。この規則はサブエージェント定義にも表として書き、
   findings を作る側から誤らないようにする。

6. **取り返しがつかない前提に立ち、絞り込みを投稿前に置く。** 提出済みレビューを削除できない以上、
   事後の取り消しは設計の前提にできない。確度×重大度による投稿／報告の振り分けと、1回あたりの
   投稿上限（10件）を**投稿前**に効かせる。

仕様の詳細は [.claude/docs/spec/adversarial-review.md](../spec/adversarial-review.md)
「GitHubの投稿」「GitLabの投稿」を正とする。

## 却下した案

- **`line` 未指定を1行目（`line: 1`）に固定する。** 実装が最も簡単で、フェーズ2の合意そのままでも
  ある。しかし**既存ファイルの部分変更では1行目がdiffに含まれないことが多く**、GitHubのレビューは
  アトミックなため、1件でもそれが混ざるとレビュー全体が422で落ちる。「ファイル全体への指摘が
  1件あるだけで、その回のレビューが丸ごと投稿されない」という壊れ方をするため採れない。

- **位置が確定しない finding は投稿しない（捨てる）。** 実装は単純で、APIの制約も踏まない。
  しかしファイル単位の指摘（設計の一貫性・命名・観点の漏れ・テストの欠落）は、敵対的レビューで
  **最も価値のある部類**である。行を指せないという技術的な理由でそれを落とすと、機構の目的自体を
  損なう。サマリへ回して必ず人間の目に触れる形にした。

- **GitLabで `new_line` と `old_line` を常に両方送る。** 分岐が消えて実装が単純になる。しかし
  追加行・削除行に対してこれを行うと `400 Bad request - Note {:line_code=>["must be a valid
  line code"]}` で失敗する（実機で確認）。GitLabは1件ずつ独立したリクエストのため全体が落ちる
  ことはないが、その指摘だけが黙ってサマリへ回るという分かりにくい欠落になる。

- **1件ずつ投稿し、失敗したものだけ捨てる（GitHubでも事前検証しない）。** 有効行の算出が要らず、
  `pulls/<n>/files` の取得も省ける。しかしGitHubは1レビューに複数コメントを含める形でしか
  まとめられず、1件1レビューにすると**レビュアーへの通知が指摘の数だけ飛ぶ**。まとめて1回に
  するために事前検証が必要になる。

- **有効行を「行の列挙」で持つ。** 範囲の包含判定を書かずに済み、単純な集合の所属判定になる。
  しかし差分が大きいほど列挙が線形に増え、jqへ渡す際に
  `jq: Argument list too long`（Windowsのコマンドライン長上限、実測でおよそ32KB）へ容易に達する。
  この失敗は**コマンドの起動自体が失敗する**ため、エラーメッセージを見ないまま「急に動かなく
  なった」としか気づけないことがある。範囲で持てば入力量は hunk 数に比例するに留まる。

- **findings をコマンドライン引数（`--argjson`）でjqへ渡す。** 一時ファイルが不要になる。
  しかし findings は指摘の件数と本文の長さに応じて可変長であり、上と同じ引数長の問題を踏む。
  加えて、コマンド文字列に指摘本文が乗ると、hookの部分一致検知（`git` と `commit`/`push` の
  連続）を誤って発火させうる。**findings は必ずファイル経由で渡す**設計にした。

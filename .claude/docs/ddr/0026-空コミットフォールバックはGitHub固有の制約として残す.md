# 0026. 空コミットフォールバックはGitHub固有の制約として残す

## 背景

[0005-DraftPR作成失敗時は空コミットで自動リトライする.md](0005-DraftPR作成失敗時は空コミットで自動リトライする.md)
で、「`gh pr create` / `glab mr create` は baseとの差分が無いブランチに対して呼ぶと失敗する」
という前提のもと、失敗時に空コミットを1つ積んで1回だけ自動リトライする仕組みを入れた。

この前提のうち**GitLab側は実機確認されていなかった**。当時このリポジトリのremoteはGitHubのみで、
`Gitlab.sh`（当時は`Gitlab.ps1`）は全関数が`【未検証】`と明記されたままだったためである。

issue #48（issue #45の実機検証から派生）で、ローカルにGitLab CE 18.5.4（Docker）を立てて
`Gitlab.sh`の全13関数を実機実行したところ、**GitLabでは差分ゼロでもMR作成が成功する**ことが
分かった。同じセッション内でGitHub側の挙動も観測でき、両者を直接比較できた。

| プロバイダ | targetブランチと同一SHA（差分ゼロ）のブランチでのPR/MR作成 |
|---|---|
| GitHub（`gh pr create`） | **失敗する**（`No commits between main and feature-48-...`）。フォールバックが動作した |
| GitLab CE 18.5.4（`glab mr create`） | **成功する**。フォールバックに到達しない |

GitHub側は本issueのブランチ作成時に実際にフォールバックが発動した。GitLab側は検証用リポジトリで
`main`と同一SHAのブランチ（`feature-2-reverify`）を作り、`gitlab_new_draft_merge_request`を
呼んで確認した（標準エラー出力にフォールバックのメッセージが現れないことをもって、分岐に
到達していないと判定した）。

## 決定

**`gitlab_new_draft_merge_request` のフォールバック分岐は削除せず残す。** ただし、
「baseとの差分が無いブランチでは`glab mr create`が失敗する既知の制約」という**断定的なコメントは
撤回**し、次の内容へ書き換える。

- 差分ゼロで失敗するのは `gh pr create`（GitHub）側の制約であること。
- GitLab CE 18.5.4では差分ゼロでもMR作成が成功し、この分岐には到達しないこと。
- したがってGitLabにおいては「通常到達しない安全網」であること。
- 実機確認できたのは18.5.4の1バージョンのみであること。

DDR 0005 は**本文・frontmatterとも変更しない**。GitHubについては決定内容が現在も有効であり、
`status: superseded` にも `deprecated` にも当たらないため。本DDRは0005を置き換えるものではなく、
**その適用範囲をプロバイダ単位で限定する追記的な決定**である。

## 却下した案

- **GitLab側のフォールバック分岐を削除する**: 実測に素直に従うならこちらだが、確認できたのは
  CE 18.5.4という1バージョン・1構成のみである。他バージョン、あるいはMR作成を制限する
  プロジェクト設定下で`glab mr create`が失敗した場合、削除してしまうとフロー全体（flow-id 1-3）が
  止まる。分岐を残すコストは「到達しないコードが数行残る」ことだけであり、非対称に小さい。
- **`get_provider` の判定結果でフォールバックの有無を出し分ける**: GitLabでは呼ばない、と
  明示的に書く案。実害の無い安全網のために分岐を増やすことになり、`Github.sh`/`Gitlab.sh`へ
  プロバイダ判定を持ち込む（`Provider.sh`の責務との重複）点でも筋が悪い。そもそも
  `get_provider`はself-hostedのGitLab URLを判定できない未修正の不具合（issue #45）を抱えており、
  これに依存を増やす判断は避けた。
- **`echo` のメッセージ文言もあわせて修正する**: フォールバック発動時に出力する
  「baseとの差分が無いことによる既知の制約です」という文言も、GitHub由来の前提のままである。
  ただしissue #48のレビューで「①はコメントの修正のみ」と合意しており、コードの変更は行わなかった。
  GitLabでは到達しない分岐のメッセージであり実害が無いため、次に同ファイルへ手を入れる機会に
  まとめて直せばよいと判断した。

# 0049. ドキュメント探索はfrontmatterインデックス検索を第一手段にする

## 背景

issue #7で、リポジトリ内の各markdownへOKF風のYAML frontmatter（`type` / `title` /
`description` / `tags` / `keywords`）を付与し、issue #11・#36を経て
`.claude/scripts/src/extract-frontmatter.sh` が**ディレクトリごとに** `index.jsonl` を
生成する形に落ち着いた。`.claude/docs/spec/extract-frontmatter.md` はこれを
「将来的な検索・ツール連携の基盤」と位置づけていた。

しかし実際には、**結合された単一のインデックスも、検索の入口も存在しなかった**。そのため
AIエージェントが「コンフリクトについてのDDRはどれか」「specの一覧が欲しい」といった探索を
するたびに `grep` / `find` による全文探索を行っており、インデックスは生成されるだけで
使われていなかった（issue #38）。

## 決定

**リポジトリ内のドキュメントを探す場面では、`grep` / `find` による全文探索より先に
frontmatterインデックスの検索を使う**ことを共通ルール（`AGENTS.md`）に明記し、その入口を
次の2層で用意する。

| 層 | 実体 | 役割 |
|---|---|---|
| スクリプト | `.claude/scripts/src/search-frontmatter.sh` | index.jsonlの最新化・結合・絞り込み・並び替え・整形 |
| スキル | `.claude/skills/doc-search/SKILL.md` | いつ使うか（grepとの使い分け）・使い方・オプションで表現できないケース向けのjqレシピ |

スクリプト単体では「探索のたびに能動的に使う」動機づけにならないため、**判断基準を
スキルの `description` に載せてスキル選択の対象にする**ことを合わせて行う（`description` は
Claude Codeがスキル選択に使う実キーである。`.claude/rules/markdown-frontmatter.md`）。

## 理由

- **全文探索は「そのファイルが何のドキュメントか」に答えない。** `grep` はヒットした行を返す
  ため、結局ファイルを開いて種別・主題を判断することになる。さらに、他ファイルからの参照
  リンクや変更履歴中の言及も同じ重みで混ざる。frontmatterは1レコードで種別・要約・タグを
  持つため、話題ベースの問いにはこちらが直接答えられる。
- **既にインデックスは存在し、鮮度も担保されている。** SessionStart hookがセッション開始の
  たびに再生成し（DDR 0025）、検索スクリプト自身も実行のたびに最新化する。新たに維持コストを
  払う必要が無い。
- **「先にインデックス、外れたらgrep」は失敗しても安いフォールバックである。** インデックス
  検索は数百ms程度で、0件だった場合に `grep` へ落ちても損失は小さい。逆順（常にgrep）は、
  当たった場合でも読むべきファイルを絞り込めない。

## 却下した案

### 案1: 結合済みの単一 `index.jsonl` をリポジトリルートへ生成し、検索は各自がjqで書く

`extract-frontmatter.sh` に「全ディレクトリ分を結合した1ファイル」の出力を足し、検索用の
スクリプトは作らない案。

**却下理由**: (1) 生成物が二重になり、ディレクトリごとの `index.jsonl` と結合版のどちらが正か
という問題を新たに作る。(2) 検索のたびにjqのフィルタを書き起こすことになり、「大文字小文字を
無視するか」「タグは完全一致か部分一致か」といった判断が毎回変わる（再現性が下がる）。
(3) `.gemini/` のリンクによる二重ヒットのような**このリポジトリ固有の落とし穴**を、
利用者ごとに踏み直すことになる。結合はスクリプトの実行時に行い、生成物としては残さない形を採った。

### 案2: スクリプトを作らず、スキル（SKILL.md）にjqのワンライナー集だけを置く

**却下理由**: index.jsonlの最新化・列挙・除外・重複排除まで含めると、ワンライナーとして
書ける長さを超える。実際、`.gemini/` の除外と `unique_by(.concept_id)` を落とすと同じ
ドキュメントが二重に出る。**手順が長いほど「今回は省略してgrepでいいか」となり、方針が
形骸化する**ため、1コマンドで完結させることを優先した。jqレシピはスキル側に残し、
スクリプトのオプションで表現しない領域（タグのAND・集計・規約違反の洗い出し）を担わせている。

### 案3: `--tag` を複数指定したときの意味をAND（すべてのタグを持つ）にする

タグでの絞り込みは「複数タグをすべて持つもの」を求める場面が多い、という想定に基づく案。

**却下理由**: `--type` はORが自然（「ddrかspec」）で、`--tag` だけANDにすると
**オプションごとに結合規則が変わり、覚えられない**。「同じオプションの繰り返しはOR、
異なるオプション同士はAND」という1文で説明しきれることを優先した。タグのANDは
`--format jsonl | jq` のレシピとしてスキルに載せている。

### 案4: 本文もインデックスに含めて全文検索できるようにする

**却下理由**: issueの目的は「ドキュメントを探す」ことであり、本文検索は既に `grep` / `rg` が
十分に担っている。本文を含めるとインデックスがリポジトリ全体の複製に近い大きさになり、
`extract-frontmatter.sh` のmtimeキャッシュによる高速化（DDR 0021）の前提も崩れる。
**役割を「ドキュメント単位の属性検索」に限定し、本文検索はgrepへ委ねる**という分担を明示した。

## 影響

- `AGENTS.md` に、ドキュメント探索の第一手段を定めるルールを1項目追加する。
- 既存のスクリプト・生成物（`extract-frontmatter.sh` / `index.jsonl` の形式）は変更しない。
  新しいスクリプトは読み取り専用の利用者として振る舞う。
- 仕様の詳細は `.claude/docs/spec/search-frontmatter.md` を正とする。

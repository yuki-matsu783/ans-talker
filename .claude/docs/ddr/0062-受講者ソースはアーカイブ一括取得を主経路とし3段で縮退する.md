# 0062. 受講者ソースはアーカイブ一括取得を主経路とし3段で縮退する

## 背景

issue #6。`answer-talker` は正解ソースを `reference.root` 配下として全ファイル渡す一方、
受講者側は差分のhunkしか渡していなかった。このスキルの観点（責務の分割単位・層と依存の向き）は
リポジトリ全体の構造に関する判断であり、hunkだけでは「今回変更していないファイルに責務が
置かれている」形が見えない。**受講者のソースコード全体を渡す**必要があった。

受講者のMRは別リポジトリにあり、ワーキングツリーがローカルに存在しない。issue本文には
案A（MRのheadを shallow clone）と案B（APIでファイル全文を取得）が候補として書かれていたが、
**どちらが成立するかは未確認**であり、issue #1 の時点では「ローカルGitLabへ `git` で到達
できなかった」という記録も残っていた。

フェーズ2の調査で、この前提が2つとも動いた。

- **`git` は到達できた。** 到達不可は環境の制約ではなく資格情報の供給方法の問題で、
  `GIT_ASKPASS` にCLIのトークンを渡すと非公開リポジトリからでもMR headを取得でき、
  `headSha` と一致した。**案Aは技術的には成立する。**
- **計画に無かった第3の方式が見つかった。** GitHub `repos/{owner}/{repo}/tarball/{ref}` と
  GitLab `projects/:id/repository/archive.tar.gz?sha=` は、**1回の呼び出しでツリー全体**を返す。

実測は次のとおり（GitHub / GitLab）。

| 方式 | 呼び出し回数 | 実測 | `.git` |
|---|---|---|---|
| 案A: shallow clone | 1回 | 両プロバイダで成功 | **同梱される** |
| 案B: ファイル単位API（ツリー全体） | **ファイル数分** | 50ファイルで34〜51秒 | 無し |
| **案B-d: アーカイブ一括** | **1回** | **1122ms / 2044ms** | **無し** |

## 決定

1. **アーカイブ一括取得を主経路（段1）とする。`git clone` は採らない。**
   決め手は速度ではなく、**追加作業が2つ要らない**ことである。cloneは `.git` を同梱するため
   除去が必須で（同梱したままではコミットメッセージから正解の意図が読めてしまう）、さらに
   資格情報の供給（`GIT_ASKPASS`）・clone URLの組み立て・非対話化が要る。アーカイブは
   `gh api` / `glab api` にそのまま乗り、これらが**設計から丸ごと消える**。

2. **縮退は3段とする。** 段1（アーカイブ一括）→ 段2（ファイル単位API）→ 段3（hunkのみ）。
   段3は issue #6 以前の状態であり、**失敗ではない**。終了コード0で `degraded:true` を返し、
   呼び出し側は処理を続ける（縮退の表現方法はDDR 0063）。

3. **段2を `git clone`（案A）ではなく、段1と同じAPI基盤に置く。** 2つの経路が同じ土台に
   乗るため、上で消えた4つの作業が段2でも要らない。加えて `gh`/`glab` CLI不在時（MCP経路）でも
   同じ考え方で組み立て直せる——cloneを段に持つと、この経路に対応する手段が無い。

4. **リポジトリサイズが取得できない場合は段1を試す**（`reason` に `size-unknown` を併記する）。
   サイズ判定は「大きすぎるリポジトリで段1を避ける」ためにあるので、**サイズが分からないことを
   理由に段2へ落とすと、上限のための判定が可用性を下げる方向に働く**。

5. **縮退したときの `reason` は「直接の原因」を先に置く。** 段1・段2の両方が失敗したときに
   `size-unknown` をそのまま返すと、人間への報告が「サイズ不明」になり調査が別方向を向く。
   `fetch-failed/size-unknown` のように、原因を主・経緯を従として併記する。

## 却下した案

- **案A（shallow clone）を主経路にする。** 技術的には成立するが、`.git` の除去と資格情報の
  供給という2つの追加作業を恒久的に抱える。前者は忘れると**ネタバレ経路になる**——正解に
  近づける過程のコミットメッセージが読めてしまい、このスキルが最も避けたい失敗そのものである。
  「動く」ことと「安全側の既定になっている」ことは別だと判断した。
- **案B-a（`matched` のファイルだけ取得する）。** issue本文が挙げていた案だが、
  **issue #6 の目的を達成しない**。`matched` は受講者の**変更**ファイルから作られるため、
  「今回変更していないファイルに責務が置かれている」形は最初から取得対象に入らない。
  hunkの代わりに全文が手に入るだけで、見える範囲は広がらない。
- **案B-b（ツリー全体をファイル単位APIで取得する）を主経路にする。** 目的は達成するが、
  呼び出し回数がファイル数に比例し、50ファイルで34〜51秒かかる。演習リポジトリが小さい前提に
  依存した設計であり、段2（上限つきのフォールバック）としてなら妥当でも主経路には置けない。
- **案B-c（拡張子・サイズで絞ってから取得する）。** 絞り込みの規則が課題ごとに変わり、
  **絞りすぎたときに「そのファイルは存在しない」と区別がつかない**。不在を根拠にした指摘が
  出る形になるため採らない。
- **縮退を2段（段1 → hunkのみ）にする。** 段2を持たない案も検討したが、`mcp` 経路と
  「アーカイブだけが失敗する」ケースの受け皿が無くなる。段1と同じAPI基盤にしたことで段2の
  追加コストが小さくなったため、3段を維持した。

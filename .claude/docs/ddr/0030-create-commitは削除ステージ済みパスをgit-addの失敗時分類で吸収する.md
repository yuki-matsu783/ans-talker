# 0030. create-commitは削除ステージ済みパスをgit addの失敗時分類で吸収する

## 背景

`.claude/scripts/src/create-commit.sh` は `commit` スキル専用のコミット実行ラッパーであり、
このリポジトリで**唯一の正規コミット経路**である（DDR 0012）。issue #60は「削除済みファイルを
引数に取れない」として、次の書き換えを提案していた。

```bash
# 現行
git add -- "${files[@]}"
# issueの提案
git add -A -- "${files[@]}"
```

`plans/` `worklog/` `reports/` を削除する flow-id 5-1 は全タスクが必ず通る工程であり、
issue #36・#55 の 5-1 では、その場で「先に削除をステージし、削除以外だけをラッパーへ渡す」という
2段構えの回避策を毎回編み出していた。この回避策はスキルにも仕様にも書かれておらず、
**実行して失敗して初めて気づく**ため再発率が高い、という問題意識があった。

## 決定

**`git add` をまず従来どおり実行し、失敗したときだけ渡されたパスを分類して回復する。**

```bash
if ! add_error="$(git add -- "${files[@]}" 2>&1)"; then
  classify_files "${files[@]}"   # ADD / SKIP / UNKNOWN
  # UNKNOWN があれば何もせず終了1、SKIP があれば通知して残りだけ再試行
fi
```

| 分類 | 条件 | 挙動 |
|---|---|---|
| ADD | worktree に存在する、または index にマッチする | `git add` へ渡し直す |
| SKIP | worktree にも index にも無いが HEAD にはある（削除がステージ済み） | 1行通知し、そのままコミットに含める |
| UNKNOWN | いずれにも無い | 何もステージせず終了コード1 |

分類はパス文字列の一致ではなく、pathspecごとに git 自身へ問い合わせる。仕様の詳細は
[create-commit.md](../spec/create-commit.md) を参照。

### 前提の訂正

実装に入る前に一時リポジトリ4本・36ケースを実測した結果（git 2.39.2.windows.1 / git bash）、
**issue本文の前提そのものが再現しなかった**。

- 追跡済みファイルを削除しただけのパスは、現行の `git add -- <path>` で**そのまま成功する**
- pathspecは worktree だけでなく **index に対しても**照合されるため、worktreeから消えていても
  indexにあるパスは一致する
- 真の失敗条件は「worktree にも index にもエントリが無いパス」であり、その代表例が
  **`git rm` で削除を先にステージしたパスを再度渡すこと**——すなわち issue が回避策として
  挙げていた手順そのものだった

つまり、直すべき対象は「削除済みパスを渡せないこと」ではなく「回避策を使うと失敗すること」だった。

## 却下した案

### 1. `git add -A -- "${files[@]}"`（issue本文の提案）

- **症状を直さない。** 削除がステージ済みのパスは `-A` を付けても pathspec 不一致で失敗する。
  実測で確認済み
- **副作用がある。** `git add --`（パス指定なし）は何もしないが、`git add -A --` は
  **リポジトリ全体**をステージする。ラッパーは `--` 以降1件以上を必須にしているため直ちに
  問題にはならないが、`-A` を持ち込むと「パス指定が空になったら全体をステージする」という
  性質が常に隣にある状態になる。commitスキルの絶対ルール（`git add .` / `git add -A` は
  使わない）を**ラッパー側でも構造的に不可能にする**という設計意図と正面から衝突する
- 実測に基づき、issueの提案をそのまま実装しない判断をユーザーと合意した

### 2. 常に分類してから `git add` へ渡す（実装の当初案）

採用案と同じ3分類を、失敗の有無にかかわらず毎回行う案。実装して検証した結果、
**現行動作からの機能後退**であることが判明したため作り直した。

- 分類をパス文字列で行うため、**ディレクトリごと削除された `reports/` をディレクトリ指定で
  渡すと UNKNOWN になる**（`git ls-files -- reports` が返すのは `reports/xxx.html` であって
  `reports` ではない）。現行コードはこれを成功させる
- 正常系でもパスの数だけ外部コマンドを起動する（git bashの起動コストは約95ms/回）
- 教訓として、**新しい判定ロジックを挟むときは、判定単位（パス文字列 対 pathspec）が元の実装と
  同じかを疑う**必要がある

### 3. 回避策を明文化するだけ（コード変更なし）

2段構えの手順をスキル・ルールへ書けば再発は減るが、**正規経路だけでコミットが完結しない**という
本質は残る。加えて、その回避策は上記のとおり「削除を先にステージしたパスを再度渡すと失敗する」
という別の失敗を誘発しており、明文化する対象として適切でなかった。

### 4. UNKNOWNのエラーメッセージに想定原因を列挙する

「未追跡のまま削除された／綴り誤り／8進エスケープ表記」といった推測をメッセージに書く案。
実際には別の原因だったときに誤誘導になるため、メッセージは事実だけを述べ、原因の解説は
spec へ集約することにした（レビューでの判断）。

## 影響

- 削除を含むコミットが、ラッパーへパスを並べるだけで完結する。2段構えの回避策は不要になった
- 既に削除がステージされたパスを渡しても冪等に扱われるため、**回避策を使ってしまった場合でも
  失敗しなくなった**（回避策の存在を知らないエージェントにも、知っているエージェントにも耐える）
- 正常系のコードパスは変更していないため、既存の使い方への影響は無い
- 本PRの flow-id 5-1（`plans/` `worklog/` `reports/` の片付け）コミット自体が、この修正の
  実地検証になる

# 0003. レビュースレッド解決は自動化せず、完了合図後に再確認する

## 背景

issue駆動MRワークフロー支援（PR #4）に、レビューコメントへの返信機能（`Add-MrThreadReply`）と
対応済みスレッドの除外フィルタ（`Get-MrUnresolvedComments -IncludeResolved`）を追加する際、
「対応が完了したレビューコメントに返信する」機能をどう設計するかが論点になった。

## 決定

### 1. `Add-MrThreadReply` はスレッドの解決（resolved）を行わない

GitHub/GitLabともスレッドの解決（GitHubの `resolveReviewThread` mutation、GitLabの
discussion `resolved` 更新）はAPIとして可能だが、`Add-MrThreadReply` では呼び出さない。
「対応内容を返信する」ことと「レビュアーが指摘を確認して解決マークを付ける」ことは別の意思決定であり、
後者はレビュアー（人間）の判断に委ねるべきという方針をユーザーから明示された。

### 2. 人間からの完了合図を受けても、そのまま次工程に進まず再確認する

`.claude/skills/issue-mr-flow/SKILL.md` に「レビュー完了合図の確認」節を設け、人間から
「レビューOK」等の合図を受けた場合でも、`Get-MrUnresolvedComments -IncludeResolved` で
全スレッドを再取得し、`unresolved` が残っていないか確認してから次のステップに進む運用にした。
残っていれば、その旨を人間に伝えて再確認を取る。

これは(1)の帰結でもある。AIが解決マークを付けない以上、「返信した」ことと「スレッドが実際に
解決された」ことは独立事象であり、人間の発言（完了合図）だけを根拠に進めると、レビュアーが
GitHub/GitLab上で解決操作をし忘れたまま次工程（設計反映・AIアセット改善）に進んでしまう
リスクがある。

実地検証: PR #4で「レビューはオッケー」という完了合図を受けた直後に再取得したところ、
3スレッドとも `unresolved` のままだった（返信はしていたが、レビュアーがGitHub上で
「Resolve conversation」を押す前だった）。このプロセスが無ければ気づかずに次工程へ
進んでいたと考えられる。

## 却下した案

- `Add-MrThreadReply` の内部で返信と同時にスレッドを解決する案: 実装は容易（GraphQL
  mutationを1つ追加するだけ）だったが、「対応した（＝返信した）」と「レビュアーが妥当と
  認めて解決した」を混同することになるため不採用。ユーザーからも明示的に「resolvedは
  レビュアー側が実施するので不要」との指示を受けた。
- 人間の完了合図をそのまま信用し、再確認なしで次工程へ進む案（当初の実装）: 実地検証で
  「口頭ではOKでも実際のスレッドは未解決のまま」というケースが実際に発生したため、
  再確認ステップを追加する方針に変更した。

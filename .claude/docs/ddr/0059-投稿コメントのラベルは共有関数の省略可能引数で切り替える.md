# 0059. 投稿コメントのラベルは共有関数の省略可能引数で切り替える

## 背景

issue #1。`answer-talker` は投稿経路を `adversarial-review` と共有する
（`add_mr_inline_comments` → `github_add_mr_inline_comments` / `gitlab_add_mr_inline_comments` →
`format_findings_summary` / `github_build_review_payload` / `gitlab_build_discussion_body`）。

実装後の実投稿で確認したところ、コメント本文が **`Claude Codeより（敵対的レビュー）:`** に
なっていた。これら5つの関数が文言をハードコードしていたためである。

演習の受講者にとってこの表示は誤りである。`answer-talker` は欠陥を探すレビューではなく、
設計の考え方を正解と同じ方向へ向けるためのレビューであり、「敵対的レビュー」と名乗ると
受け取り方そのものが変わってしまう。

この問題は個別作業計画の「実装中に設計の誤りが見つかった場合は、勝手に変えず結果mdへ
『設計との差分』として記録し、レビューで諮る」に従い、2案を提示して判断を仰いだ。

## 決定

**共有関数へ省略可能なラベル引数を足す。** 既定値は従来の文言 `敵対的レビュー` とし、
`answer-talker` からは `演習レビュー` を渡す。

- 対象は5関数。`format_findings_summary`（第1引数）／`github_build_review_payload`（第2引数）／
  `gitlab_build_discussion_body`（第3引数）／`github_add_mr_inline_comments` ・
  `gitlab_add_mr_inline_comments` ・ `add_mr_inline_comments`（いずれも第3引数）。
- **既定値を従来の文言にすることで、既存呼び出しは1つも変更せずに済む。** `adversarial-review`
  側は引数を渡さないまま従来どおり動く（GitHub・GitLab双方で既定の出力が従来と一致することを
  実機で確認済み）。
- `answer-talker` の `SKILL.md` には**ラベルを省略しないこと**を手順9の注意と
  「してはいけないこと」の両方へ明記する。省略すると受講者に誤解される表示になるため。

ラベル文言は当初 `演習レビュー（正解照合）` を検討したが、本文が
`Claude Codeより（演習レビュー（正解照合））:` と二重括弧になり読みづらいため `演習レビュー` とした。

実装上の注意として、**jqの変数名に `label` を使わない**。`label` はjqの予約語
（`label $out | …` 構文）であり、`--arg label` は `syntax error, unexpected label` になる。
実装では `$reviewLabel` を使っている。

仕様の詳細は
[.claude/docs/spec/answer-talker.md](../spec/answer-talker.md)「影響範囲」節を正とする。

## 却下した案

- **`answer-talker` 専用の投稿処理を持つ。** 共有関数に一切手を入れずに済み、`adversarial-review`
  への影響がゼロであることが一目で分かる。しかし**同じ投稿ロジックが2つになる**。インライン
  コメントの投稿は、行番号を指定できない指摘をサマリへ回す振り分け・GitHubのpending review
  （`create` → `add_comment_to_pending_review` → `submit_pending`）・GitLabのdiscussion
  （`position` の組み立て）と、プロバイダごとに込み入っている。ここが二重化すると、
  **片方だけが直される**事故が避けられない（本リポジトリはGitHub/GitLabの差異吸収を
  `Provider.sh` 1箇所へ寄せる設計を採っており、その方針とも食い違う）。
  違いは表示される語1つだけであり、そのために実装を分ける理由が無い。

- **文言を無条件に変える**（`Claude Codeより（AIレビュー）:` のような中立な語へ統一する）。
  引数を増やさずに済み、両スキルとも正しく読める。しかし `adversarial-review` の投稿は
  「敵対的レビュー」という名前と結びついて運用されており（`.claude/skills/adversarial-review/`、
  spec、`HANDOFF.md` の記載）、表示だけを中立化すると**どのスキルが投稿したのか分からなくなる**。
  レビューコメントの出どころが追えなくなるのは、レビューの独立性を保つうえで損である。

- **呼び出し側で本文を組み立ててから渡す**（共有関数はラベルを一切持たず、完成した本文を受け取る）。
  最も柔軟だが、本文の組み立て（重大度・確度・カテゴリの整形）まで呼び出し側へ露出することになり、
  スキルごとに書式がずれる。書式の統一こそが共有関数の価値なので、本末転倒になる。

# 0043. 全体作業計画には調査・反映の枠を必ず残し省略判断は各フェーズ直前で行う

## 背景

issue #92「全体作業計画には調査フェーズ・反映フェーズを必ず含めるルールを追加する」。

`.claude/skills/issue-mr-flow/SKILL.md` の flow-id 1-4 と「計画の2階層構造」節は、全体作業計画の
**作り方**（planツールで作る・issueにつき1回・既にあれば作らない）は規定していたが、**中身**
（どのフェーズを節として置くか）を規定していなかった。`.claude/rules/docs-workflow.md` の
進捗記号 `[-]` も「フェーズ単位・ループ範囲単位でまとめて実施しない場合に使う」という**粒度**の
規定にとどまり、**いつ `[-]` を決めてよいか**が無かった。

その結果、着手直後（1-4）の見立てだけでフェーズ2〈調査〉・フェーズ4〈反映〉を落とせてしまう。
実例として issue #39 対応時のHANDOFF.mdは、着手時点で flow-id 1-4/1-5 とフェーズ2の全行が
`[-]` になっていた。**計画に節が無いと、後から必要だと分かっても拾い直す先が無い**（フェーズを
省いた計画は、省いた事実も理由も残らない）。

同時に、逆方向の失敗もありうる。「1-4 で調査の要否を正しく判断するために、その場でコードベースを
読み込む」という進め方は、フェーズ2の個別調査と作業が重複するうえ、1-4 側の調査結果は個別調査
計画のレビュー（2-3〜2-4）を経ないため、レビュー可能な形で残らない。

## 決定

1. **全体作業計画（flow-id 1-4）には、フェーズ2〈調査〉とフェーズ4〈反映〉を必ず節として置く。**
   「今回は調査不要」「反映するものは無い」と先回りして判断し、節ごと落とした形で組み立てない。
2. **全体作業計画のための事前調査は軽めでよい。** issue本文と関連しそうなファイルの所在・見出し
   レベルの確認までで足りる。本格的な調査はフェーズ2（flow-id 2-1〜2-10）で行う。事前調査が
   軽くても困らないのは、フェーズ2の枠を必ず残しているからである。
3. **反映は枠だけ置く。** 何を spec/ddr・AIアセットへ反映するかは作業が終わるまで決まらないため、
   1-4 では「反映対象は flow-id 4-1 で洗い出す」と書くにとどめる。
4. **省略してよいと判断できる最初のタイミングを固定する。** フェーズ2は flow-id 2-1（個別調査
   計画を作る段）、フェーズ4は flow-id 4-1（個別反映計画を作る段）。進捗記号 `[-]` を使ってよい
   のもこのタイミング以降とする。フェーズ4は 4-1 で反映対象を洗い出すところまでは必ず通り、
   洗い出した結果が空だったときに限りそこから先をスキップしてよい。

記載場所は `.claude/skills/issue-mr-flow/SKILL.md`「全体作業計画に必ず含めるフェーズ」を正とし、
`.claude/rules/docs-workflow.md` は `[-]` のタイミング規定と同節への参照を持つ。

## 却下案

### (a) 省略を一切認めず、全フェーズを必ず実施する

`[-]` の運用そのものをやめれば「先回りして落とす」問題は消える。しかし、誤字修正に近い小さな
タスクでも調査フェーズのレビュー往復を強制することになり、フローの固定費（5フェーズ40ステップ）が
本体の作業量を上回る。issueの分割判断で「1件が極小なら分割しない」としているのと同じ理由で採らない。

### (b) 1-4 で調査を尽くしてからフェーズ2の要否を決める

判断の精度は上がるが、フェーズ2と同じ調査を2回行うことになる。しかも 1-4 側の結果は個別調査計画の
レビューを経ないため、レビュー可能な形で残らない。「枠を残す」ことで判断を後ろへ倒せるなら、
1-4 の判断精度を上げる必要そのものが無い。

### (c) `[-]` の運用は変えず、SKILL.mdに注意書きだけを足す

「先回りして省略しないこと」とだけ書いても、**いつなら省略してよいか**が無いままなので、
判断がセッションごとにぶれる。省略してよい最初のタイミング（2-1・4-1）を表として固定し、
`docs-workflow.md` の `[-]` の説明と対にすることで、記号の運用と計画の書き方を1つの規則へ揃えた。

### (d) 判断基準を `docs-workflow.md` 側に書く

`[-]` の説明がある場所へまとめて書く案。しかし全体作業計画の**中身**はフロー定義の一部であり、
`.claude/skills/issue-mr-flow/SKILL.md` が唯一のフロー定義であるという原則に反する。
既存の「issueが大きすぎる場合の分割提案」と同じく、判断基準はSKILL.md、参照は各ルールという
形に揃えた。

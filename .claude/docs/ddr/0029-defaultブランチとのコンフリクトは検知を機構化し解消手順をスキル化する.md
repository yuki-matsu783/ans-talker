# 0029. defaultブランチとのコンフリクトは検知を機構化し解消手順をスキル化する

## 背景

issue #46「マージ依頼前にdefaultブランチとのコンフリクトを検知・解消するフローを整備する」。

`.claude/skills/issue-mr-flow/SKILL.md` のマージ依頼フロー（旧 flow-id 5-2）には、defaultブランチと
のコンフリクト有無を確認するステップが無かった。コンフリクトに気づくのは人間がマージ操作を試みた
後になりがちで、解消手順も定義されていなかったため、都度その場の判断で解消されていた。

調査の結果、**過去の発生は issueに挙げられた2件（PR #29, #37）ではなく4件**あり、
**4件すべてでDDR番号が衝突していた**ことが分かった（PR #29, #37, #49, #52）。しかも、
このうちDDR番号の衝突は**gitがコンフリクトとして報告しない**。両ブランチが追加するDDRは
`0027-A.md` と `0027-B.md` のように**ファイル名が異なる**ため、gitは何の問題も無く両方を
マージし、同じ連番のDDRが2つ並ぶ。実際に PR #52 の両親コミットで検証したところ、
`git merge-tree` は `.claude/docs/README.md` と `tests/test_vcs_provider.sh` のコンフリクトは
報告するが、DDR 0027の重複については一言も報告しなかった。

つまり**「`git merge` を試してコンフリクトが出るか見る」という素朴な確認方法では、
このリポジトリで最も頻発している衝突を検知できない**。

## 決定

1. **検知は専用スクリプトで機構化する**（`.claude/scripts/src/check-base-conflicts.sh`）。
   `git merge-tree --write-tree` によるテキストコンフリクト判定に加えて、**DDR番号の重複を
   直接調べる**。両ブランチのツリーからDDRファイルを列挙し、先頭4桁の連番でグルーピングして
   相異なるパスが2つ以上ある番号を報告する。判定結果はJSONで返し、コンフリクトの有無は
   終了コードではなく `hasConflict` フィールドで表す（呼び出し元が `set -e` 配下でも
   「コンフリクトがある」という正常な結果で停止しないため）。

2. **検知は作業ツリーを変更しない方法で行う**。`git merge` を実行して `git merge --abort` で
   戻す方式は、途中で中断された場合にマージ途中のままリポジトリが残る。`merge-tree --write-tree`
   はインデックス・作業ツリーに一切触れないため、「確認だけしたい」という用途に合う。

3. **解消手順は独立したスキル（`resolve-conflict`）として文書化する**。issue-mr-flowのフロー定義に
   直接書き込まず分離したのは、(a) コンフリクト解消はマージ依頼時に限らず任意のタイミングで
   必要になりうる、(b) issue-mr-flow/SKILL.md は既に420行あり、フロー定義に専念させたい、
   という2点による（`commit` スキル・`issue-create` スキルを分離しているのと同じ考え方）。

4. **flow-id 5-2として新しいステップを挿入し、以降を繰り下げる**（旧5-2→5-3、旧5-3→5-4。
   全39→40ステップ）。「Draft解除の直前に必ず通る位置」に置くことを優先し、既存ステップへの
   追記ではなく独立したflow-idにした。flow-idはHANDOFF.mdの進捗表・`commit` スキル・
   `git-workflow.md`・`docs-workflow.md` から参照されているため、それらも合わせて更新した。

5. **取り込みは `git merge` で行い、`git rebase` は使わない**。作業ブランチは既にリモートへ
   反映済みで、MR/PRのレビューコメントが特定のコミットSHA・diffに紐づいている。履歴を書き換えると
   レビュアーのローカルチェックアウトとMR上の参照リンクの両方が壊れる。squash mergeでmainへ入るのは
   1コミットなので、途中のmergeコミットがmainの履歴を汚すこともない。過去4件の実績もすべてmergeである。

6. **解消時はユーザーの承認を必ず取る**（`AskUserQuestion`）。コンフリクト解消は「どちらの意図を
   残すか」という設計判断を含むため、検知だけを自動化し、解消の実行は人間の承認の後ろに置く。

7. **DDR番号の改番方向は「defaultブランチ側を正とし、作業ブランチ側を繰り下げる」**。mainは共有の
   正史であり、既にマージされた番号を動かすと他のブランチ・既存の相互参照が壊れる。過去4件の実績も
   すべてこの方向（0026 / 0027 / 0028 へ繰り下げ）。

## 却下した案

- **push検知hookで毎回自動チェックする**: `post-push-usage-report.sh` と同じ仕組みに相乗りすれば
  「読まれなければ機能しない」問題を避けられる。しかしコンフリクトはマージ依頼の直前にだけ
  確認できればよく、pushのたびに `git fetch` を伴う判定を挟むのはコストに見合わない。加えて、
  push検知hookは**コマンド文字列の部分一致で誤発火する**という既知の問題を抱えており
  （`.claude/rules/git-workflow.md`「push検知hookの誤検知」）、その上に判定を積み増すと
  誤発火のたびに不要なfetchが走る。flow-id 5-2という「必ず通る手順」として明示する方式を採った。

- **検知スクリプトを作らず、スキルの手順に `git merge --no-commit` と書くだけにする**: 実装は
  最小で済むが、**DDR番号の重複を検知できない**（上記「背景」）。過去4件すべてがこの形である以上、
  最も頻発するケースを取りこぼす対策では意味がない。DDR 0012（コミットは`commit`スキル経由を
  機構的に強制する）・DDR 0027（CLI不在時はMCPへ機構的に誘導する）と同じく、
  「その場の判断に委ねない」ための実行可能な仕組みを置く方針とした。

- **DDR番号を連番ではなくタイムスタンプ・UUIDにして衝突自体を無くす**: 根本解決ではあるが、
  既存28件のDDRと、それらを相互参照している多数のドキュメントの番号をすべて振り直す必要がある。
  DDRは「本文を一度マージしたら変更しない」運用（`.claude/rules/docs-workflow.md`）であり、
  過去の記録を大量に書き換えることになる。issue #46の範囲を大きく超えるため採らなかった。
  なお `.claude/docs/README.md` には「移植元のDDRのうち0001・0002・0008・0015は持ち込んでいない
  （連番に欠番がある）」と既に記されており、連番の欠番自体は許容されている。将来、衝突の頻度が
  改番コストに見合わなくなった時点で再検討してよい。

- **コンフリクトを検知したら自動で解消まで行う**: AIエージェントが完結できて手数は減るが、
  類型C（同じドキュメントの近接行を両ブランチが変更）・類型E（同じロジックの競合）は
  「どちらの意図を残すか」という設計判断であり、無言で決めると片方の変更が失われる。issue #46の
  期待する動作も「AskUserQuestionでユーザーに確認したうえで」と明記している。

- **`git merge --no-commit` を使わず、gitの自動マージコミットに任せる**: コンフリクトが無い部分は
  gitがそのままコミットできるが、メッセージが `Merge branch 'main' into ...` になり、
  **何をどう解消したかが履歴から読み取れない**。過去4件の実績はいずれも
  `chore: mainをマージしDDR番号を0028へ繰り下げてissue #45の変更と統合` のような説明的な
  日本語メッセージであり、これを維持する。

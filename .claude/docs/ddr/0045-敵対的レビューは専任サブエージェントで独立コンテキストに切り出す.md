# 0045. 敵対的レビューは専任サブエージェントで独立コンテキストに切り出す

## 背景

issue #77「MRへの敵対的レビューを行うスキル・専任サブエージェントを追加する」。

このリポジトリのレビュー（flow-id 2-3/2-8/3-3/3-8/4-3/4-8）は人間の負荷に全面的に依存している。
AIエージェント自身に確認させる案は自然に思いつくが、**自分が書いたものを自分で読み返す構図では、
追認する方向へ働きやすい**。実装の意図を知っている以上、「そう書いた理由があるはずだ」という
補完が入り、独立した検証にならない。

組み込みの `/code-review` は汎用のバグ探しであり、このリポジトリ固有の落とし穴（`plans/` の粒度、
spec/DDR/rules の二重管理、point-in-time記録の破壊、DDR番号の衝突、shellの既知の罠）を見ない。
本issue以前、`.claude/agents/` には読み取り専用の `issue-mr-resume` しか無く、レビューを担う
スキルもサブエージェントも存在しなかった。

## 決定

1. **敵対的レビューを、読み取り専用の専任サブエージェント（`.claude/agents/adversarial-reviewer.md`、
   `model: opus`）へ切り出す。** ツールは `Read, Grep, Glob, Bash` のみとし、Write/Editを持たせない。

2. **サブエージェントへ渡すのは3つだけにする** — レビュー対象（diffまたはファイルパス一覧）、
   マージ済みの観点表、フェーズ番号と対象の種別。**「なぜそう実装したか」の経緯は渡さない。**
   `git log` 等でコミットメッセージや過去の議論を読むことも禁じる。観点表を自分で探しに行くことも
   禁じ、対象範囲の判断は呼び出し元の1箇所へ寄せる。

3. **サブエージェントは findings JSON を返すだけで、投稿は行わない。** 投稿は呼び出し元
   （`.claude/skills/adversarial-review/SKILL.md`）の責務とし、**承認の所在を1箇所へ集約する**。

4. **対話セッションでは、AIエージェントからの自律起動を禁止する。** 人間が `/adversarial-review` を
   呼んだときだけ実行する。持ちかけることは構わないが、返事を待たずに実行してはならない。
   **非対話セッション（`AUTOMATION=1`）でのみ自律起動を許す。** `AUTOMATION` は実行環境が自動で
   設定するものではなく運用側が明示的に設定する片方向の契約であるため、「未設定＝対話モード」を
   既定とし、判定を誤ったときに「勝手に動く」側ではなく「動かない」側へ倒す。

5. **投稿の可否は、レビュー実行の前に1回だけ確認する（`AskUserQuestion`）。指摘ごとの個別承認は
   求めない。**

6. **実施回数は各フェーズ最大3回とし、AIの自制ではなくスクリプト
   （`.claude/scripts/src/adversarial-review-count.sh`）で強制する。** 加算は「レビュー実行の直後・
   投稿の前」に、**投稿の成否に関わらず**行う。上限を環境変数等で緩める口は用意しない。

7. **全体フロー表には含めない。** flow-idを持たない任意の補助手順として、
   commit・pushの直後から人間のレビューまでの間に挟む。

仕様の詳細は [.claude/docs/spec/adversarial-review.md](../spec/adversarial-review.md) を正とする。

## 却下した案

- **組み込みの `/code-review` の拡張で済ませる。** 追加の機構を持たずに済み、学習コストも無い。
  しかし `/code-review` はコードの正しさを対象とする汎用のレビューであり、このリポジトリの運用
  規約・ドキュメント整合（`plans/` の粒度、spec/DDR/rules の二重管理、point-in-time記録の破壊）を
  観点として持たせる口が無い。指摘をMRへインラインコメントとして投稿する経路も無い。**併用は
  推奨する**（`/code-review` で拾えるバグは本スキルでも拾えるが、逆は成り立たない）が、代替には
  ならない。

- **メインエージェントが自己レビューする（サブエージェントを作らない）。** 実装が最も簡単で、
  コンテキストの受け渡しも要らない。しかしこれは本issueが解こうとしている問題そのものである。
  実装した本人の文脈が残ったままでは、指摘が「そう書いた理由」に吸収されて出てこない。
  独立コンテキストであること自体が機構の中身であり、ここを削ると残るのは投稿処理だけになる。

- **指摘ごとに個別承認を取る。** 誤検知をMRへ出さずに済み、慎重に見える。しかしGitHubの提出済み
  レビューは削除できないため「投稿してから取り消す」前提の設計にはできず、承認を細かくしても
  取り返しがつく訳ではない。むしろ指摘の数だけ確認が発生して人間の負荷を増やし、**人間の負荷を
  下げる**という目的と逆行する。承認は投稿前の1点へ集約し、誤検知の抑制は確度×重大度による
  選別（投稿／報告の振り分け）で行う。

- **全体フローの必須ステップにする（flow-idを与える）。** レビューが必ず行われることを保証でき、
  進捗表にも載る。しかし敵対的レビューはサブエージェントの起動を伴い、実行時間とトークンを
  相応に消費する。誤字修正のような小さな変更でも必ず通る手順にすると、**フロー全体の固定費を
  押し上げる**。加えて、必須にすると「対話セッションではAIから自律起動しない」という決定4と
  矛盾する（必須ステップをAIが飛ばせないなら、AIが起動することになる）。任意の補助に留めた。

- **実施回数の上限をスキル本文の記述だけで担保する。** スクリプトを1つ増やさずに済む。しかし
  非対話モードでは「レビュー → 修正 → 再レビュー」が人間の介在なく回りうるため、**AIエージェント
  自身が守るルールでは歯止めにならない**。同じ理由で、上限を環境変数で緩められるようにもしない。

- **`model: sonnet` にする（`issue-mr-resume` に揃える）。** コストは下がる。しかし
  `issue-mr-resume` は「決まった情報を集めて報告する」役割であるのに対し、敵対的レビューは
  「書かれていないことを欠落として見つける」役割で、要求される推論の深さが違う。浅い確認では
  敵対的レビューとして成立しないため `opus` を選んだ。

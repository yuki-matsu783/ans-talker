# 0046. レビュー観点はディレクトリごとのREVIEW-POINTSへ外だしする

## 背景

issue #77 のflow-id 3-4（作業計画のレビュー）で決まった。

当初の計画では、敵対的レビューの観点を `.claude/skills/adversarial-review/SKILL.md` の中に表として
書く想定だった（「diff全体」「`plans/` の個別計画」「設計反映」の3対象それぞれに観点を並べる形）。

しかしこの形には次の問題がある。

- **観点は対象ディレクトリごとに異なる。** `.claude/scripts/` 配下ならshellの既知の罠、`plans/`
  配下なら種別 `【】` の妥当性と分割判断、`.claude/docs/` 配下ならspec/DDRの二重管理と
  point-in-time記録の破壊、というように、見るべきものがまるで違う。
- **スキル本文に書くと、「スキルの更新」と「観点の更新」が同じ変更単位になる。** 観点は運用しながら
  増えていくもので、更新頻度が手順そのものより高い。同じファイルに置くと、観点を1つ足すたびに
  スキルの手順を含むファイルが変更され、レビューの焦点がぼやける。
- 観点の一覧は、**敵対的レビュー以外（人間のレビュー、組み込み `/code-review` の補助）でも使える**。
  スキル本文に埋め込むと、その用途で参照できない。

## 決定

1. **レビュー観点を `REVIEW-POINTS.md` として各ディレクトリ直下へ置く。** frontmatterの
   `type` は新設の `review-points`。

2. **1つの `REVIEW-POINTS.md` は、そのディレクトリ配下すべて（孫以下を含む）に適用される。**
   収集は、レビュー対象ファイルのあるディレクトリからリポジトリルートまで**祖先を遡って**行い、
   1つへマージする。出力順は**浅い → 深い**（一般 → 具体）とし、由来が分かるよう
   `## <観点表のパス>` の見出しを挟む。

3. **複数の対象ファイルは1回の呼び出しへまとめて渡し、各祖先チェーンの和集合を取る。**
   同じ観点表は1回だけ出力する（ファイルごとに呼ぶと同じ観点表が重複するため）。

4. **観点表が1つも見つからない場合はエラーにしない**（何も出力せず終了コード0）。観点表が無くても
   レビュー自体は一般的な観点で行えるため。その事実は報告に含め、観点表を追加すべきディレクトリの
   発見につなげる。

5. **収集・適用は `review-points` スキル（`.claude/skills/review-points/SKILL.md`）として単独でも
   使えるようにする。** 敵対的レビューはその利用者の1つに過ぎない。

6. **観点の中身をスキル本文・サブエージェント定義へ書かない。** `adversarial-review/SKILL.md` が
   持つのは「対象の決め方」と「観点表の集め方」だけで、何を観るかは `REVIEW-POINTS.md` が持つ。

7. **この仕組みを別issueへ切り出さず、issue #77 に含める。** 観点表が無いと「何を観るか」が定義
   できず、敵対的レビューだけを先にマージしても実用にならないため（依存が強く、単独マージの価値が
   薄い）。

仕様の詳細は [.claude/docs/spec/adversarial-review.md](../spec/adversarial-review.md)
「レビュー観点（REVIEW-POINTS.md）」を正とする。

## 却下した案

- **スキル本文へ直書きする（当初案）。** ファイルが増えず、スキルを読めば観点も分かる。しかし上記
  「背景」のとおり、観点の更新とスキルの更新が同じ変更単位になり、ディレクトリごとに異なる観点を
  表現する手段が無い。敵対的レビュー以外から参照することもできない。

- **単一の巨大な観点表を1ファイルで持つ**（例: `.claude/rules/review-points.md` 1つ）。
  収集ロジックが要らず実装が最も簡単。しかしレビュー対象が `plans/` の計画1ファイルだけの場合
  でも、shellの罠もspec/DDRの規約も含んだ全文をサブエージェントへ渡すことになる。**観点は
  「下限であって上限ではない」**という運用のため、無関係な観点を大量に渡すと、注意が散り、
  適用すべき観点の優先度が下がる。ディレクトリ階層は、対象と観点の対応を表す既にある構造で
  あり、それを使わない理由が無い。

- **`.claude/rules/` の既存ファイルをそのまま観点として読ませる。** 新しいファイル種別を増やさずに
  済み、二重管理も起きない。しかし `.claude/rules/` はAIエージェントの**行動規約**であって
  レビューの**チェックリスト**ではない。粒度も文体も違い（「こう書く」と「こうなっていないか」）、
  そのまま渡すと指摘へ変換する負荷がサブエージェント側に乗る。加えて `.claude/rules/` は
  セッション開始時に常時読み込まれるため、レビュー用に絞って渡すという制御ができない。
  `REVIEW-POINTS.md` からは `.claude/rules/` を参照する形にして、内容の二重管理は避けている。

- **ディレクトリを遡らず、対象ファイルと同じディレクトリの観点表だけを使う。** 実装が単純になる。
  しかしリポジトリ全体に効く観点（日本語で応答する、hook誤検知語を連続させない、削除される
  ファイルを恒久参照しない）を、全ディレクトリの観点表へ複製することになり、まさに二重管理が
  起きる。祖先方向へ遡る形にすれば、一般的な観点は上位に1回だけ書けばよい。

- **観点表が見つからないときにエラーで止める。** 観点表の置き忘れに気づける。しかし観点表は
  段階的に増やしていくもので、未整備のディレクトリでレビュー自体が動かなくなるのは過剰である。
  一般的な観点でレビューを続け、観点表が無かった事実を報告する形にした。

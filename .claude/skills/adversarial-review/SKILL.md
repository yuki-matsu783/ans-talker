# adversarial-review スキル

独立コンテキストの専任サブエージェント（`.claude/agents/adversarial-reviewer.md`）に、
**意図的に欠陥を探させる**レビューを実施し、指摘をMRへインラインコメントとして投稿する
（issue #77）。

AIが自分の書いたものを自分で確認しても、追認する方向に働きやすく独立した検証にならない。
実装した本人の文脈を渡さないサブエージェントへ切り出すことで、これを構造的に避ける。

## 組み込みの `/code-review` との棲み分け

| | `/code-review`（組み込み） | 本スキル |
|---|---|---|
| 対象 | コードの正しさ（バグ探し）全般 | コードに加え、**このリポジトリの運用規約・ドキュメント整合**（`plans/` の粒度、spec/DDR/rulesの二重管理、point-in-time記録の破壊、shellの既知の罠） |
| 観点の出どころ | 汎用 | **ディレクトリごとの `REVIEW-POINTS.md`**（`review-points` スキル） |
| 結果 | 会話への報告 | **MRへのインラインコメント投稿**＋報告 |
| 起動 | 人間が任意に | 対話セッションでは**人間のみ**。非対話セッションではAIも可 |

併用してよい。`/code-review` で拾えるバグは本スキルでも拾えるが、逆は成り立たない。

## 実行モードの判断（起動ポリシー・絶対ルール）

非対話かどうかは環境変数ではなく、**AIエージェント自身が実行環境の性質（人間とのレビュー往復が
成立するか）から判断する。** 判断に迷う場合は対話モード（起動禁止）を既定とする。判定を誤った
ときに「勝手に動く」側ではなく「動かない」側へ倒すためである。

- **対話モードでは、AIエージェントは本スキルを自律的に起動してはならない。** 人間が
  `/adversarial-review` と明示的に呼んだときだけ実行する。「レビューしておきましょうか」と
  持ちかけることは構わないが、返事を待たずに実行しない。
- **非対話モードでのみ、AIエージェントは自律的に起動してよい。** 人間のレビュー往復
  （flow-id 3-3/3-8 等）が成立しない環境で、レビューの空白を埋めるための例外である。
- どちらのモードでも、**投稿の可否は手順3で確認する**。

## 手順1: 実施回数の上限を確認する

```bash
bash .claude/scripts/src/adversarial-review-count.sh get <phase>
```

`<phase>` は issue-mr-flow のフェーズ番号（2/3/4）。**各フェーズ最大3回**で、上限に達している
場合は**レビューを実行せずに打ち切る**。非対話モードでは「レビュー → 修正 → 再レビュー」が
人間の介在なく回りうるため、AIの自制ではなくスクリプトで強制する。

打ち切った場合は、その事実（フェーズ・実施済み回数）を報告し、`HANDOFF.md` の「やったこと」にも
残す。意図的にやり直したい場合の `reset` は**人間の判断**で実行してもらう（AIから提案しない）。

カウンタの加算は手順5（レビュー実行の直後）で行う。**投稿の成否に関わらず加算する**
（失敗を口実に無限リトライできないようにするため）。

## 手順2: レビュー対象を判別し、観点表を収集する

### 2-a. 対象を決める

現在のflow-idから自動判別する。曖昧なら `AskUserQuestion` で選ばせる
（非対話モードでは既定として「diff全体」を採る）。

| 対象 | 判別 | ファイルの列挙 |
|---|---|---|
| diff全体 | flow-id 3-7 / 4-7 の直後 | `git diff --name-only origin/<base>...HEAD` |
| `plans/` の個別計画 | flow-id 2-2 / 3-2 / 4-2 の直後 | 該当する `plans/【*.md` |
| 設計反映 | flow-id 4-7 の直後 | `.claude/docs/spec/` `.claude/docs/ddr/` `.claude/rules/` の変更ファイル |

削除されたファイルは対象から外す。

### 2-b. 観点表を集める

```bash
bash .claude/scripts/src/collect-review-points.sh <対象ファイルパス...>
```

`review-points` スキル（`.claude/skills/review-points/SKILL.md`）の手順に従う。
**対象ファイルは1回の呼び出しへまとめて渡す**（ファイルごとに呼ぶと同じ観点表が重複する）。

**観点の中身をこのSKILL.mdへ書かないこと。** 本スキルが持つのは「対象の決め方」と
「観点表の集め方」だけで、何を観るかは `REVIEW-POINTS.md` 側が持つ。観点を足したくなったら、
このファイルではなく該当ディレクトリの `REVIEW-POINTS.md` を編集する。

## 手順3: 投稿の可否を確認する（承認モデル）

レビューを実行する**前**に、`AskUserQuestion` で1回だけ確認する。

- `指摘をMRへインラインコメントとして投稿する (Recommended)`
- `投稿せず、この会話で報告するだけにする`
- `レビュー自体をやめる`

**承認後は、指摘ごとの個別承認を求めない。** GitHubの提出済みレビューは削除できないため、
「投稿してから取り消す」前提の設計にできない。だからこそ承認は投稿前に1回へ集約する。

非対話モードでは確認できないため、**既定は「報告するだけ」ではなく「投稿する」**とする
（非対話環境では会話への報告が誰にも読まれないため）。

## 手順4: サブエージェントへレビューさせる

Agentツールで `adversarial-reviewer` サブエージェントを起動し、次の3つだけを渡す。

1. レビュー対象（diffの内容、またはファイルパス一覧）
2. 手順2-bで集めた**マージ済みの観点表**
3. フェーズ番号と対象の種別

**「なぜそう実装したか」の経緯・設計判断の背景を渡さないこと。** 渡すと実装者の文脈に
引きずられ、追認するレビューになる。サブエージェント側から観点表を探しに行かせないのも
同じ理由で、対象範囲の判断を呼び出し元の1箇所へ寄せるためである。

サブエージェントは findings JSON を返す（スキーマは `.claude/agents/adversarial-reviewer.md`）。

## 手順5: 実施回数を加算する

```bash
bash .claude/scripts/src/adversarial-review-count.sh increment <phase>
```

**レビューを実行した直後、投稿の前に**行う。上限に達していればここで終了コード1が返るので、
投稿せずに打ち切って報告する。

## 手順6: 投稿する指摘を選別する

findings を、**確度（`confidence`）と重大度（`severity`）**で振り分ける。

| 確度 \ 重大度 | blocker | major | minor | nit |
|---|---|---|---|---|
| high | 投稿 | 投稿 | 投稿 | 報告 |
| medium | 投稿 | 投稿 | 報告 | 報告 |
| low | 報告 | 報告 | 報告 | 報告 |

- **「投稿」** = インラインコメントとしてMRへ出す。**「報告」** = この会話（非対話モードでは
  worklog）にのみ書き、MRへは出さない。
- **1回あたりの投稿上限は10件**。超える場合は重大度の高い順に10件へ絞り、残りは報告へ回す。
  レビュアーが一度に扱える量を超えると、結局どれも読まれないため。
- 投稿する findings だけを集めた JSON を一時ファイルへ書き出す（次の手順で使う）。

## 手順7: MRへ投稿する

```bash
source .claude/scripts/src/vcs/Provider.sh
add_mr_inline_comments <MR番号> <findings JSONファイル>
```

MR番号は `get_mr_for_branch "$(git branch --show-current)"` で取得する。

- **findingsは必ずファイル経由で渡す**（jqの引数長上限と、コマンド文字列へのhook誤検知語の
  混入を避けるため。`.claude/rules/shell-script-style.md`）。
- 戻り値は `{"posted":N,"summarized":M}`。`summarized` は、対象がdiffに含まれず行を指定
  できなかったためサマリへ回った件数。サマリの出し方はプロバイダで異なり、GitHubは
  **レビュー本文**へ載せ、GitLabは**別コメント**として投稿する。
- **GitLabでは、サマリが指摘を1件でも含む場合はスレッド（`discussions`）で投稿される。**
  インラインの指摘と同じくレビュアーが解決でき、`reply` サブコマンドで返信できる。0件のとき
  （全件をインラインで示せたとき）だけ、解決を要さない通知として単発コメントになる。
- GitHubでは**1回のレビューにまとめて**投稿される（レビュアーへの通知が1回で済む）。
  投稿は原子的で、1件でも不正な行があると全件失敗するが、`add_mr_inline_comments` が
  投稿前に有効行を検証して振り分けるため、呼び出し側でこの制約を意識する必要はない。
- **`line` を持たない finding（ファイル全体にかかる指摘）はサマリへ回らず、そのファイルの
  diff上で最初に現れる有効行へインラインで付く**（新規追加ファイルでは1行目に一致する）。

## 手順8: 結果を報告する

- 投稿件数・サマリへ回った件数・報告のみに留めた件数。
- 報告のみの指摘は、この会話に**内容を書き出す**（MRを見ても残らないため）。
- 打ち切った場合はその理由（上限到達）。
- 観点表が空だった場合はその事実（観点表を追加すべきディレクトリの発見につながる）。

## `gh`/`glab` CLI不在時（`get_vcs_access_mode` が `mcp`）の読み替え

```bash
source .claude/scripts/src/vcs/Provider.sh
get_vcs_access_mode   # → cli / mcp
```

`mcp` の場合、手順7を次のように読み替える（GitHubのみ。GitLabは対象外）。

1. `get_repo_slug | jq -r '.owner, .repo'` で `owner` / `repo` を得る。
2. `mcp__github__pull_request_review_write` を `method="create"` で呼び、pending review を作る。
3. 指摘ごとに `method="add_comment_to_pending_review"`（`path` / `line` / `side` / `body`）で追加する。
4. **必ず `method="submit_pending"`（`event="COMMENT"`）まで実行する。** pending のまま放置すると、
   次回の `create` が失敗し続ける。
5. 途中で失敗した場合は `method="delete_pending"` で片付けてから、原因を報告する。

WebFetchツール・curlへはフォールバックしない（DDR 0020, DDR 0027）。

## してはいけないこと

- **対話セッションで、人間の明示的な指示なしに本スキルを起動すること。**
- 手順1（実施回数の確認）を飛ばすこと。
- 上限に達しているのにレビューを実行すること、`reset` をAIの判断で実行すること。
- 観点の中身をこのSKILL.mdへ書き足すこと（`REVIEW-POINTS.md` へ書く）。
- サブエージェントへ実装の経緯・設計意図を渡すこと。
- スレッドの解決（resolve）操作を行うこと（レビュアー側の操作）。
- 指摘が0件のときに、水増しして投稿すること。

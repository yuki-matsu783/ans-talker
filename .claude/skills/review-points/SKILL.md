# review-points スキル

レビュー観点を**スキル本文へ直書きせず、ディレクトリごとの `REVIEW-POINTS.md` として外だしする**
ための仕組み（issue #77）。このSKILL.mdが持つのは「観点表の集め方・使い方」だけで、
**観点の中身は一切持たない**。観点の追加・修正は `REVIEW-POINTS.md` の編集だけで完結する。

## 観点表の適用範囲

`REVIEW-POINTS.md` は各ディレクトリ直下に置き、**そのディレクトリ配下すべて**（孫以下を含む）の
ファイルに適用される。

- `.claude/REVIEW-POINTS.md` は `.claude/scripts/src/vcs/Github.sh` のレビューにも効く。
- 一方、`plans/` 配下のファイルには効かない（祖先ではないため）。
- ルート直下の `REVIEW-POINTS.md` はすべてのファイルに効く。

現在の構成では ルート・`.claude/`・`plans/`・`reports/` の4箇所に置いている。

## 実行フロー

### 手順1: レビュー対象ファイルを列挙する

「何をレビューするか」によって対象が変わる。代表的な決め方は次のとおり。

| レビュー対象 | 列挙方法 |
|---|---|
| defaultブランチとの差分全体 | `git diff --name-only origin/main...HEAD` |
| 前回pushからの差分 | `git diff --name-only <前回push時のSHA>..HEAD` |
| 特定の計画・ドキュメント | パスを直接指定する |

削除されたファイルは観点表の収集対象から外してよい（レビューする中身が無いため）。

### 手順2: 観点表を収集する

```bash
bash .claude/scripts/src/collect-review-points.sh <ファイルパス...>
```

- 各ファイルの祖先ディレクトリを遡り、存在する `REVIEW-POINTS.md` を集めて連結した
  markdownを標準出力へ返す。複数ファイルを渡した場合は**和集合**で、同じ観点表は1回だけ出る。
- 出力順は**浅い → 深い**（一般 → 具体）。由来が分かるよう `## <観点表のパス>` の見出しが挟まる。
- 対象ファイルが多い場合も、**1回の呼び出しへまとめて渡す**（ファイルごとに呼ぶと同じ観点表が
  何度も出力され、重複を自分で除く必要が生じる）。

### 手順3: 観点を適用する

得られた観点を**上から順に1つずつ**、レビュー対象へ突き合わせる。観点ごとに次のいずれかを
判断する。

- **該当する箇所がある** → その箇所（ファイル・行）と、なぜ観点に反するのかを具体的に示す。
- **該当しない** → 触れない（「問題ありませんでした」を観点の数だけ並べない）。
- **観点の対象範囲外** → 触れない（例: markdownしか変更していないのにbashの罠の観点を無理に当てる）。

**観点表に無い問題を見つけた場合も報告してよい。** 観点表は「最低限これは観る」という下限で
あって、レビューの上限ではない。

### 手順4: 観点表が空だった場合

出力が空（＝祖先に `REVIEW-POINTS.md` が1つも無い）でも**エラーではない**。その場合は
一般的な観点（正しさ・可読性・テストの有無等）でレビューし、**観点表が無かった事実を報告に
書き添える**（観点表を追加すべきディレクトリの発見につながるため）。

## 観点表を書き足すとき

- **具体的に、照合できる形で書く。** 「読みやすいか」ではなく「ループ内で外部コマンドを
  起動していないか」のように、対象を見れば真偽が決まる形にする。
- **過去に実際に踏んだ失敗を優先して書く。** 一般論はAIも人間も既に知っているが、
  このリポジトリ固有の罠は明文化しないと繰り返される。
- **他のルールファイルの内容を丸写ししない。** 要点と参照先（`.claude/rules/*.md`・
  `.claude/docs/spec/*.md`・issue番号）を書き、詳細はそちらへ委ねる。
- frontmatterは `type: review-points` とする（`.claude/rules/markdown-frontmatter.md`）。

## してはいけないこと

- 観点の中身をこのSKILL.mdや呼び出し元のスキルへ書き写すこと（二重管理になる）。
- 対象ファイルの祖先でない観点表を、念のため適用すること（適用範囲の定義が壊れる）。
- 観点表が無いことを理由にレビューを中止すること。
